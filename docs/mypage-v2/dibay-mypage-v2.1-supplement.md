## 4. D1 사진 경로 완전 차단 설계

### 4.1 공격 경로와 차단 계층

| 경로 | 지금 | 차단 계층 |
|---|---|---|
| ① 앱 API 로 남의 사진 주소를 내 프로필에 저장 | 가능(주소 검사 없음, 서비스 롤로 저장) | **L1 API 검사** |
| ② 회원 로그인 토큰으로 DB 에 직접 남의 사진 주소 저장 | 가능(F07 계약상 직접 수정 허용 + 값 검사 없음) | **L2 DB 트리거** |
| ③ 사진 교체 시 서버가 "이전 사진"을 서비스 롤로 삭제 → 이전 값이 남의 사진이면 남의 파일 삭제 | 가능(경로 소유 검사 없음) | **L3 삭제 대상 검사** + L1·L2 로 애초에 남의 주소가 저장되지 않음 |
| ④ 회원이 저장소에서 직접 남의 파일 삭제 | **불가**(운영 확인: `post-images` 회원 권한 = 본인 폴더 업로드만) | **L4 저장소 권한 유지** |
| ⑤ 외부 임의 주소·임의 경로·`..` 경로 | 가능 | L1·L2 |

### 4.2 허용 값 (L1·L2 공통 규칙, 한 곳에서 정의)

회원이 **바꿀 때** 허용되는 `avatar_url`:
1. 빈 값(NULL)
2. 기본 그림 `/samarket-default-avatar.svg`
3. 본인 프로필 폴더 사진: `https://<운영 Supabase 호스트>/storage/v1/object/public/post-images/<본인 uid>/profile/<uuid>.(jpg|jpeg|png|webp)` — 쿼리·`..`·추가 경로 없음, 대소문자 정규화 후 정확 일치

허용 외 모든 값 거부. **값이 바뀌지 않으면 검사하지 않음** → 기존 구글 50명·카카오 7명 사진 그대로 유지.
서버 신뢰 경로(서비스 롤)는 트리거 검사 제외 → 소셜 로그인 가입 시 서버가 넣는 구글·카카오 사진, 관리자 조치 정상 동작.
회원 토큰으로 프로필 행을 **처음 만드는** 폴백 경로(서비스 롤 없을 때 `/auth/callback` 등)는 3개 값 + **본인 로그인 계정 정보에 있는 소셜 사진 주소와 정확히 같은 값**만 허용.
운영 Supabase 호스트는 코드에 박지 않고 DB 의 기존 플랫폼 설정 테이블(또는 함수 상수 1곳)에 둔다 — 구현 시 기존 설정 테이블 사용 가능 여부 확인.

| 계층 | 구현 | 파일/객체 |
