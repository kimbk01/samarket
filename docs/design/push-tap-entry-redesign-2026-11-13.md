## 2. 1차 설계의 잘못 (장애 원인 포함)

1. **공용 웹 코드가 Android 전용 플러그인을 비동기로 기다렸다.** iOS Capacitor 브리지는 없는 플러그인 호출에 응답하지 않는다(`CapacitorBridge.swift:479` — 로그 후 return). 조회가 끝나지 않아 iOS 스플래시가 풀리지 않았다.
2. **상한 없는 기다림.** 하드락 H2-3 「상한 없는 await 금지」를 어겼다. 「응답이 없으면 네이티브 고장 판정이 푼다」고 적었으나, 확인한 iOS 시뮬 설치본 1.2(23)은 75초 넘게 풀리지 않았다(고장 판정이 그 빌드에 없음). 실제 iPhone 설치본(1.2(27)·(30))에서 15초 고장 판정이 동작했는지는 NOT_PROVEN.
3. **시험이 가짜였다.** iOS 를 「오류로 응답」으로 흉내 내 통과했다. 실제 동작(무응답)을 시험하지 않았다.
4. **실기가 한 플랫폼뿐.** Android 만 확인하고 자동 병합을 걸었다.
5. **범위 초과.** E 는 원인 미확정(0단계 측정 불가)인데 Android 전 화면의 뒤로 처리(INAPP-07)를 바꿨다. 결함 하나에 비해 영향이 전 화면이었다.
6. **분기 다수 결합.** 알림 수신자의 10여 개 종료 분기마다 「보류 해제」를 넣는 구조 — 하나라도 빠지면 스플래시가 남는 깨지기 쉬운 설계였다.

## 3. 재설계

### A — 알림 목적지가 있는 시작에서 홈 노출 (원인 확정)

**결정: 네이티브가 이미 알고 있는 목적지를 동기로 알려 주고, 웹은 기다리지 않는다.**
- 근거(실측 11-10 20:17): Android 는 웹 문서 로드 **전**(16.372s, `pending_route_saved`)에 알림 목적지를 저장한다. 웹은 그 값을 **동기**로 읽을 수 있으면 기다릴 필요가 없다.
- 변경 1 (Android 네이티브): `DibayBootJsBridge`(이미 `addJavascriptInterface` 로 노출, MainActivity 1804행)에 동기 메서드 1개 — 보관된 알림 목적지 경로 반환(없으면 빈 문자열). 통화 경로는 빈 문자열.
- 변경 2 (웹): 스플래시 해제 두 곳(P3 서버 본문 첫 그림·첫 목적지 그림)에서 `window.DibayBootBridge?.<메서드>` 를 **동기로 1회** 읽는다.
  - 값이 있고 지금 경로가 그 목적지가 아니면 해제하지 않는다 → 목적지 경로가 그려질 때 기존 첫 목적지 신호(`MarkInitialDestinationVisualReadyOnce`, 경로 바뀔 때마다 실행)가 해제.
  - 메서드가 없음(iOS·웹·구버전 Android 설치본) → 지금과 똑같이 동작. **기다림 0, 비동기 호출 0** → iOS 멈춤 같은 무응답 위험이 구조적으로 없다.
- 목적지로 끝내 가지 못하는 경우(로그인 필요·다른 계정·안전하지 않은 경로): 1차처럼 분기마다 해제를 넣지 않는다. 대신 **해제 보류는 「목적지 경로로 이동이 시작될 때까지」가 아니라 「알림 수신자가 목적지를 처리했다는 단일 신호 1개」**로 끝낸다 — 수신자 `navigate()` 진입부 1곳에서 「처리 시작」을 기록하고, 이동이 아닌 결과(시트·버림)는 그 함수의 단일 종료 지점에서 해제. 분기 전수 삽입 금지.
- 하드락 대조: 해제 권한 2개 유지(H1-1), 표시 타이머 없음(H1-2), 상한 없는 await 없음(H2-3 — 동기 읽기). 「네이티브가 `/` 밖으로 loadUrl 금지」 계약은 지킨다(목적지를 직접 열지 않음).
- 배포 구분: **네이티브**(Android 빌드 필요). 설치본 39 이하는 메서드가 없어 지금 동작 그대로 — 개선은 새 빌드 설치 후에만 나타난다. Owner 일괄 빌드 대상.
- iOS: 같은 결함이 있는지 **먼저 실측**(실기 iPhone 에서 앱 종료 → 알림 탭 녹화). 있으면 iOS 네이티브에 같은 동기 값 제공을 별도 설계. 실측 전 iOS 변경 없음.
- 검증(전부 통과 전 병합 금지): 웹 시험 — 메서드 없음/빈 값/목적지 값 3경우 + **iOS 처럼 브리지 자체가 없는 경우**. 실기 — Android 새 빌드(종료 상태 알림 탭: 홈 0프레임, 아이콘 시작 회귀), **iOS 시뮬·iPhone 아이콘 시작 회귀(시작 화면이 2초 안에 걷힘)**.

### E — 알림 연속 진입 후 시스템 뒤로 무반응 (원인 미확정)

**결정: 이번에는 고치지 않는다. 원인 측정부터.**
- 운영 앱은 웹뷰 디버그가 꺼져 있고 개발 앱은 지워져 `canGoBack` 을 잴 수 없다.
- 측정 방법(Owner 승인 필요): 디버그 가능한 Android 빌드 1회 설치 → 결함 E 재현 → 네이티브 `webView.canGoBack()`·`copyBackForwardList()` 와 웹 `history.length`·`navigation.canGoBack` 을 같은 순간 기록.
- 측정 결과로 원인이 확정되면, 「알림 이동 1건」에 한정한 수정안(전 화면 뒤로 처리 변경 금지)을 따로 설계·승인.

### C — 새 배포 직후 재로드
- 수정하지 않는다(H3-1 Owner 결정). FAIL 기록만 유지.
