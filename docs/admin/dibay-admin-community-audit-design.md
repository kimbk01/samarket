## A-2. 데이터·API·권한 흐름 (확인된 실제 구조)

```
[앱 작성자] ── /api/community/* (proxy 회원 정책 게이트) ─┐
     └─ ⚠ PostgREST 직접 (RLS update_own·delete_own, 38컬럼 UPDATE 권한) ─┤
                                                                  ▼
[Admin 화면] ─ fetch ─ /api/admin/community/** ─ requireAdminApiUser/isRouteAdmin (관리자 여부만)
                                       └ service role ─ community_posts / comments / reports / topics / sections
                                       └ appendAuditLog (게시글·댓글·신고 PATCH 만, void)
[Admin 제재]  /api/admin/users/[id]/moderation ─ requireAdminPermission("users") ─ profiles.status + user_moderation_events
[Admin 포인트] /api/admin/points/adjust ─ "point" ─ point_ledger (행위자 없음)
[Admin 충전]  /api/admin/point-charges/[id] ─ "point" ─ RPC approve_user_point_charge_request (FOR UPDATE, 원자적)
[Admin 홍보]  /api/admin/community-promotion-orders/[id] ─ requireAdminApiUser ─ point_promotion_orders(domain=community)
[Admin 문의]  /api/admin/support/cases ─ isRouteAdmin ─ support_cases (커뮤니티 참조 유형 없음)
```

### 원인 정리

1. **배달·채팅에서 확정한 공통 기준이 커뮤니티에 아직 적용되지 않았다.** R1(확인 등급·화면 상태·결과 배너·상태 라벨·returnTo)·B-1(권한 키)이 커뮤니티 화면·API 에서 사용 0건. 설계상 진행 순서(R3 거래 → R4 커뮤니티)대로 남아 있던 영역.
2. **DB 보호선이 앱 API 에만 있다.** 작성자 수정·삭제는 API 가 막는다고 가정했으나 RLS·컬럼 권한이 그대로 열려 있음 (C-01).
3. **업무 단계가 상태로 분리되지 않았다.** 「신고 처리 = 상태 메모」, 「조치 = 다른 화면」, 「제재 = 계정 정지」뿐이라 그 사이(신고 인정·콘텐츠 숨김·커뮤니티 제한)가 기록되지 않음.
4. **금전 화면이 공통 화면에만 있고 커뮤니티 맥락(어떤 게시물·어떤 신고)과 연결되지 않았다.**

# C-0. 화면 공통 표준 (커뮤니티 UI/UX/CTA SSOT)

배달 R1 기준을 그대로 쓰고, 커뮤니티 전용 라벨·조치표만 추가한다. 모든 커뮤니티 화면은 아래 3가지 틀 중 하나로만 만든다.

## C-0-1. 화면 틀 3종

| 틀 | 쓰는 곳 | 고정 구성 (위→아래) |
|---|---|---|
| **목록 화면** | 신고·게시글·댓글·모임·작성자·제한·홍보·포인트·충전·문의·기록 | ① 제목 + 설명 1줄(업무 목적만) ② 상태 탭(건수 표시) ③ 필터 줄: 검색 · 기간(PHT, 오늘/7일/30일/직접) · 상세 필터(접기) · 필터 초기화 ④ 일괄 처리 줄(선택 시에만) ⑤ 표 ⑥ 서버 페이지네이션(50건, 총 건수) |

공통 규칙
- 목록 → 상세 → 복귀 시 필터·탭·페이지 유지 (`withAdminReturnTo`, URL 쿼리).
- 시각: 목록은 「상대 시간 + 마우스 올리면 PHT 절대 시각」, 상세·기록은 PHT 절대 시각 (`YYYY-MM-DD HH:mm PHT`). 날짜 경계는 서버에서 `manilaTodayRangeUtc` 계열 단일 헬퍼로 `[from,to)`.
- 화면 상태 4종: `AdminLoadingState / AdminEmptyState / AdminErrorState(다시 시도) / AdminForbiddenState`. 원시 오류는 `adminOperatorErrorMessage` 로 변환, 원문은 기술 정보로.
- 결과: `AdminResultBanner` (성공·부분 성공 n/m·실패 + 사유). alert 금지.
- 저장 실패 시 입력값 유지. 동시 수정 충돌(409) 시 「다른 관리자가 먼저 변경했습니다 — 최신 내용으로 다시 불러왔습니다」.
- 금액·포인트: 천 단위 구분 + 단위(P, ₱). 상태 배지: `lib/admin/status-labels/community.ts` 단일 정의.
- 태블릿 가로·세로: 표는 열 우선순위로 접고 가로 스크롤 금지, 시트 하단 버튼 고정.

## C-0-2. 버튼(CTA) 표준표 — 모든 커뮤니티 조치

등급: **L0** 즉시 · **L1** 확인창 · **L2** 확인창 + 사유 필수(선택지 + 자유 입력) · **L3** L2 + 대상명 재입력 + 최고 관리자 또는 해당 권한 키

> v2: 아래 「권한 키」 열의 `community` 는 **신규 키가 아니라 기존 키 묶음의 별칭**이다 — 콘텐츠·카테고리·공지·모임·설정 = `boards`, 신고·경고·활동 제한 = `reports`, 문의 = `boards`. 정확한 대응은 §E-1.

## C-0-3. 상태 구분 SSOT (서로 다른 상태 — 섞지 않는다)

```
신고 접수(open) → 검토 중(reviewing) → ┬ 신고 기각(dismissed)                     … 콘텐츠·회원 변화 없음
                                       └ 신고 인정(resolved) ─ 선택 조치 ┬ 콘텐츠 숨김/삭제   (community_posts/comments.status)
                                                                          ├ 경고/커뮤니티 활동 제한 (제한 원장 · 커뮤니티 API 만 차단)
                                                                          └ 계정 정지/차단     (profiles.status · 플랫폼 전체 · users 권한)
```

| 구분 | 저장 위치 | 화면 배지 | 사용자 영향 |
|---|---|---|---|
| 신고 접수/검토/인정/기각 | `community_reports.status` (+CHECK) | 회색/파랑/초록/회색 | 없음 |
| 콘텐츠 숨김(관리자) | `status=hidden` + `moderated_by` | 주황 「관리자 숨김」 | 작성자만 보임 + 안내 문구 |
| 콘텐츠 삭제 | `status=deleted` | 빨강 「삭제됨」 | 아무도 못 봄, 복구 가능 |
| 커뮤니티 활동 제한 | 제한 원장 (O-3) | 보라 「커뮤니티 제한 ~MM-DD」 | 커뮤니티 글·댓글·신고·모임만 차단, 거래·배달·메신저 정상 |
| 계정 정지/차단 | `profiles.status` | 빨강 「계정 정지」 | 플랫폼 전체 |

## E-1. 권한표와 전환 설계 (v2 — O-12 보완, 신규 `community` 키 철회)

> **Owner 최종 결정 (승인 ②, 2026-10-20):** 홍보 권한(`ads`)은 **모든 활성 관리 운영자**에게 부여한다. 운영자 기본 권한(`DEFAULT_PERMISSIONS_BY_ROLE.operator`)에 `ads` 포함 → 명시 권한 행이 없는 운영자·신규 운영자 자동 적용, 명시 행이 있는 활성 운영자는 데이터 마이그레이션(`20270520121300`)으로 `ads` 만 추가. 최고 관리자 불변. 해지 멤버십은 관리자 확인에서, 차단·탈퇴는 로그인에서, **정지 운영자는 홍보 게이트에서** 거부. 홍보 중지·종료·환급의 사유·귀책·환급 RPC·감사 규칙은 그대로. 아래 E-1-2·E-1-3 의 「Owner 지정 운영자」 절차는 이 결정으로 대체된다.

### E-1-2. 결정: 신규 키를 만들지 않고 기존 키로 대응

v1 의 `community` 신규 키는 **철회**한다. 이유: ① 신규 키는 operator 기본값에 없으므로 배포 즉시 운영자 2명의 커뮤니티 업무가 전부 차단된다 ② 일괄 부여(O-12 v1)는 Owner 가 거부 ③ 의미가 맞는 기존 키(`boards`·`reports`)가 이미 operator 기본값에 있다.

| 커뮤니티 업무 | 서버 권한 키 | 현재 가드 | 운영자 2명 영향 | 최고 관리자 |

| 작성자 조회·운영 기록·통계 조회 | `boards` 또는 `reports` | 관리자 여부만 | **변화 없음** | ● |

### E-1-3. 전환 절차 (기존 운영 기능이 막히지 않도록)

1. **배포 전 확인(읽기 전용)**: 활성 관리자·명시 권한 행을 다시 조회해 위 표와 같은지 확인 (승인 ② 보고에 첨부).
2. **Owner 지정**: 홍보 업무(`ads`)를 맡을 운영자를 Owner 가 지정 (O-12). 지정 없으면 홍보 조치는 최고 관리자만.
3. **권한 부여 방식**: 기존 관리자 권한 관리 경로로 명시 행을 쓴다. **명시 행은 기본값을 대체하므로** 「operator 기본 15키 + ads」 전체 목록을 저장한다 (ads 만 저장하면 boards·reports·users 등이 사라져 기존 업무가 막힘). 구현에 「기본값 + 추가 키」로 저장하는 보호 로직과 테스트를 포함.
4. **배포 순서**: 권한 부여(지정 운영자) → 서버 가드 적용 배포. 403 화면은 「권한 필요: 홍보(ads)」로 표시.
5. **되돌리기**: 가드 상수 1곳(`lib/admin/community-admin-guards.ts` 신설 예정)에서 키를 바꾸면 즉시 원복, 권한 행은 이전 값으로 복원.

## E-3. 관리자 수정과 원본 보존

- 신설 `community_post_revisions` (post_id, revision_no, editor_id, editor_role `author|admin|import`, title, content, content_blocks, topic_id, reason, created_at). **DB 트리거**가 제목·본문·블록·카테고리 변경 시 변경 **전** 값을 기록 → 작성자 원본이 언제나 남는다.
- 관리자 수정 시 게시글에 `last_admin_edit_at/by` 표시 → 사용자 화면에 「운영 정책에 따라 일부 수정됨」 안내 (Owner 결정 O-8 에 포함).
- 수정은 CAS(`expected_updated_at`), 트리거가 `updated_at` 갱신(C-39).

## E-4. 작성자 추적 (누가·언제·무엇)

모든 목록·시트에 고정 표시: 작성 구분(회원/외부 수집 — 수집 글은 「출처: 사이트명」 + 원문 링크) · 닉네임·DIBAY ID·회원 링크 · 작성/게시/수정 PHT · 카테고리 · 현재 상태 · 받은 신고 수 · 마지막 조치(누가·언제). 작성자 → 글 → 신고 → 조치 기록이 서로 링크.

## E-5. 신고 처리 흐름 (한 화면에서 끝)

1. 처리함 → 대상별 묶음 행 → 상세 시트 (대상 요약 + 신고 n건 사유 + 기존 조치)
2. 「검토 시작」(L0, 담당자 표시)
3. 「신고 기각」(L2) 또는 「신고 인정」(L2) → 조치 선택(복수): 콘텐츠 숨김 / 삭제 / 경고 / 커뮤니티 활동 제한(범위·기간) / 계정 정지로 이동(users 권한)
4. 서버 1요청 `POST /api/admin/community/reports/{id}/decision` : 신고 CAS → 조치 실행 → 같은 대상의 다른 열린 신고 일괄 종결(선택) → `report_actions` 연결 기록 → 감사 → 알림
5. 결과 배너 + 행 갱신, 처리함 복귀 시 필터 유지

중복 처리 차단: 신고 status CAS + 전이표(resolved/dismissed → 재오픈은 최고 관리자, 포인트 회수는 신고 ID 기준 1회 unique). 삭제된 글 신고: 리비전·스냅샷으로 본문 표시, 처리 가능.

## E-6. 제재·해제

- 저장(O-3 권장안): **기존 `sanctions` 재사용** + `scope('community'|'platform')`, `restriction('post'|'comment'|'all')`, `revoked_at/by/reason`, `source_report_id` 컬럼 추가 → 세 번째 원장을 만들지 않음. 계정 정지는 기존 `profiles.status` + `user_moderation_events` 그대로.
- 강제: 커뮤니티 쓰기 API(글·댓글·신고·모임 개설/참여) 공통 가드 `assertCommunityWriteAllowed(userId, kind)` — 만료는 조회 시 `end_at` 비교(크론 불필요).
- 기간: 1·3·7·30일·영구. 해제 L2, 만료·해제 시 회원 알림.
- 이의신청: 제한·숨김 알림에 「이의신청」 링크 → 고객지원 케이스(`reference_type = COMMUNITY_SANCTION|COMMUNITY_POST|COMMUNITY_REPORT`) → 커뮤니티 문의 화면 → 결과 버튼(제한 해제·다시 공개).

## E-7. 감사 기록

모든 커뮤니티 변경 = `appendAuditLog` (await, 실패 시 경고 배너), `after_json.reason` 에 사유, 전후 스냅샷(본문 포함). 영구 삭제는 전체 행 + 댓글 수·연결 정보 스냅샷.

# F. 홍보·포인트·충전·문의 설계

## F-1. 홍보 — 상태 흐름과 환급 기준 (v2 — O-5 보완)

### F-1-1. 실제 결제·노출 구조 (확인 결과)

- 결제: 회원 구매 시 **포인트 즉시 차감**(원장 `spend`, 원자 RPC `purchase_member_community_promotion`), 주문 `active` 로 노출 시작. 현금 결제 없음 → 환급도 **포인트 원장 `refund` 로만** (현금 환불 경로 없음·만들지 않음).
- 노출 기간: `start_at` ~ `end_at` (= `duration_days` × 24h). 현재 「노출 중지」 시간을 기록하는 컬럼이 없어 실제 노출 시간을 계산할 수 없다 → **M9** 에서 `paused_at`, `paused_seconds_total` 추가.
- 종료 주체·귀책을 기록하는 컬럼 없음 → **M9** 에서 `ended_by`, `end_reason_code`, `fault('operator'|'member'|'none')`, `refund_points`, `refund_ledger_id` 추가.
- 회원 취소: 현재 **심사 대기(pending_review) 주문만** 취소 가능(보류 해제), 노출 중 취소 경로 없음.
- 운영 데이터: 커뮤니티 홍보 7건 모두 QA 성격, 기준 검증에 쓸 실제 주문 없음 (C-48).

### F-1-2. 환급 기준표

환급액 = `floor(결제 포인트 × 남은 노출 시간 ÷ 구매 노출 시간)` (1P 미만 버림). 남은 노출 시간 = `end_at − 종료 시각 + 미반영 중지 시간` (중지 중 종료 시 중지 시간 포함). 계산·원장 기록·주문 갱신은 **DB RPC 1회**(주문 행 `FOR UPDATE`), 원장 `(related_type='promotion_order', related_id=주문 ID, entry_type='refund')` **unique** 로 1회만.

| # | 종료 상황 | 종료 주체 | 귀책 | 환급 | 노출 |
|---|---|---|---|---|---|
| 1 | 기간 만료 | 시스템(cron) | 없음 | 없음 | 종료 |
| 2 | 관리자 「노출 중지」 → 「노출 재개」 | 관리자 | 없음 | 없음 — **종료일을 중지 시간만큼 연장** | 재개 |
| 3 | 관리자 귀책 중단 (시스템 오류·정책 변경·잘못된 숨김 등 운영 판단) | 관리자 | **운영** | **남은 노출 비례 100%** | 종료 |
| 4 | 회원 위반 사유로 관리자 종료 (홍보 정책 위반 등, 신고 없이) | 관리자 | 회원 | 없음 (사유 필수·회원 알림) | 종료 |
| 5 | **신고 인정** → 게시글 숨김·삭제 | 관리자 | 회원 | **없음** | 자동 종료 |
| 6 | 신고 없이 관리자 숨김·삭제 (카테고리 정리 등 운영 판단) | 관리자 | 운영 | 남은 노출 비례 100% | 자동 종료 |
| 7 | 관리자 숨김 후 「다시 공개」 (오판 정정) | 관리자 | 운영 | 숨김 시 종료됐다면 #3 으로 환급 확정 (재노출 없음) | — |
| 8 | **회원 취소 — 노출 시작 전**(심사 대기) | 회원 | 회원 | 전액 (기존 보류 해제 유지) | — |
| 9 | **회원 취소 — 노출 중** | 회원 | 회원 | 현행대로 **취소 불가** (O-5 에서 허용 여부 결정, 허용 시 남은 노출 비례 50% 권장) | — |
| 10 | **회원 본인 게시글 삭제** | 회원 | 회원 | 없음 (삭제 전 앱에서 「홍보 중 — 삭제 시 환급되지 않음」 확인) | 자동 종료 |
| 11 | 작성자 커뮤니티 활동 제한·계정 정지 | 관리자 | 회원 | 없음 | 자동 종료 |
| 12 | 심사 반려 (레거시 경로) | 관리자 | 없음 | 전액 (기존 보류 해제) | — |

- 관리자가 홍보 중인 글을 숨기거나 삭제하거나 홍보를 종료할 때 시트에 **귀책 선택(운영/회원)이 필수**이고, 선택에 따라 환급액 미리보기가 표시된다 (`ads` 권한, L3).
- 회원에게 종료·환급 알림 (사유·환급 포인트 포함).
- SSOT 유지: 잔액 = 원장 합계 그대로, 홍보 주문 상태·원장 기록·환급은 같은 RPC 트랜잭션. 거래 홍보(domain=trade)는 같은 RPC 를 쓰되 **이번에는 커뮤니티 경로에만 연결** (거래 적용은 거래 Admin 작업에서 결정).
- 레거시 「신청→승인」 보류 경로(C-47)는 API 비활성 (데이터 보존).

## F-2. 포인트

- 원장 단일 통화 유지(K-1). `point_ledger.actor_id` 추가(관리자 지급·회수·충전 승인 자동 기록).
- 관리자 지급·회수: 시트를 열 때 멱등 키 1회 생성 → `(related_type, idempotency_key)` unique, 차감은 `FOR UPDATE` 잠금 RPC 로 이동(C-06). 경로는 하나로 통일 (`/api/admin/points/adjust` 유지, 회원 상세 경로는 같은 함수 호출 — C-45).

## F-3. 충전 (v2 — O-7 보완)

### F-3-1. 커뮤니티 관련 충전을 구분할 수 있는가 — **불가 (확인)**

| 확인 대상 | 결과 |
|---|---|
| `point_charge_requests` 컬럼 | id, user_id, plan_id, plan_name, payment_method, payment_amount, point_amount, request_status, depositor_name, receipt_image_url, admin_memo, user_memo, 시각·처리자·요율 — **도메인·출처 컬럼 없음** |
| `point_plans` | 도메인 구분 없음 (공통 요금제) |
| 포인트 통화 | 단일 플랫폼 포인트 (커뮤니티 전용 잔액 금지 — `docs/dibay-community-dpoint-financial-hard-lock.md`) |
| 운영 10건 신청자 | 커뮤니티 글 작성·커뮤니티 홍보 구매·커뮤니티 보상 원장 **모두 0명** |

→ 「커뮤니티 충전」 필터는 만들지 않는다 (추측 금지). 회원 활동으로 추정하는 표시도 하지 않는다.

### F-3-2. 커뮤니티 워크스페이스의 충전 화면 = 전체 회원 충전 조회 (범위 명시)

| 항목 | 기준 |
|---|---|
| 데이터 | **전체 회원 충전 신청** — 공통 `/api/admin/point-charges` 를 그대로 호출 (처리 API·RPC 중복 구현 없음, 같은 행을 공통 화면과 동시에 보므로 CAS·`already_processed` 로 이중 처리 차단) |
| 화면 표시 | 상단 고정 문구 「포인트는 전체 서비스 공통입니다. 이 목록은 모든 회원의 충전 신청입니다.」 |
| 권한 | 메뉴·화면·API 모두 `point` 키 필요 (현재 운영자 2명은 미보유 → 메뉴 비노출). `boards` 만 있는 커뮤니티 운영자는 볼 수 없다 |
| 개인정보 | 목록: 닉네임·DIBAY ID·금액·상태·신청 시각. **입금자명·증빙 이미지·회원 메모는 상세 시트에서만**, 조회 시 감사 기록(열람 로그). 전화·이메일·계좌 정보 표시 안 함 |
| 운영 범위 | 승인·반려·보류·정정은 공통 처리 API 결과와 동일. 커뮤니티 화면은 **진입 위치만 다르고 업무 규칙은 공통 SSOT** |

### F-3-3. 흐름 (P0-5)

```
회원 신청(요금제 스냅샷, 입금자명, [증빙 이미지 — O-4]) → 승인 대기 ─┬ 「입금 확인 후 승인」: 입금 확인 체크 + 확인 근거(은행 거래 시각·참조번호) 필수 → 기존 RPC(원자) + verified_* 기록 → 원장 charge → 알림
                                                              ├ 「반려」: 사유 필수 → 알림(사유 포함)
                                                              └ 「보류」 → 대기 유지
승인 후 정정: 「충전 정정」 = 관리자 회수(원장 reverse, related_id=충전 ID) + 사유 — 충전 건 상세에 연결 표시
```
- `point_charge_requests` 에 `verified_by, verified_at, verification_note, reject_reason` 추가, 원장 `(related_type='point_charge', related_id)` unique.
- (선택 O-7b) 앞으로의 구분이 필요하면 신청 시 **진입 화면(`source_surface`)을 사실 그대로 기록**하는 컬럼을 추가할 수 있다. 과거 10건은 「기록 없음」. 권장: **이번엔 추가하지 않음** (단일 통화라 운영상 의미 낮음).

## F-4. 문의 (공통 고객지원 SSOT 재사용)

- 테이블·API 는 `support_cases` 그대로. 추가: 참조 유형 `COMMUNITY_POST · COMMUNITY_COMMENT · COMMUNITY_REPORT · COMMUNITY_SANCTION`, 카테고리 그룹 `COMMUNITY`(포인트 적립·차감, 충전, 홍보, 게시물, 신고, 제재 이의).
- 커뮤니티 문의 화면 = 같은 API 의 필터 화면 → 공통 고객지원과 **같은 케이스**를 보므로 중복 처리 없음 (담당자 배정이 양쪽에 동일 표시).

## F-5. 공지·상단 고정 (v2 — O-6 범위 포함)

### F-5-1. 기존 기능 확인 (중복 방지)

| 기존 | 위치 | 용도 | 커뮤니티 피드 공지로 쓸 수 있나 |
|---|---|---|---|
| `app_notices` | `/admin/app/notices`, 앱 「설정 › 공지사항」(댓글·조회수) | **앱 전체 공지** | 아니오 — 피드에 노출되지 않음, 용도 다름. **재구현·이동하지 않는다** |
| `platform_events` (`is_pinned`) | `/admin/platform-events` | 이벤트 게시판 | 아니오 |
| `meeting_notices` | 모임 안 (모임장 작성) | 모임 내부 공지 | 아니오 (모임 범위) |
| `community_topics` / 카테고리 버킷 `notice` | 코드 상수만 존재, 운영 토픽 9개 중 공지 토픽 **없음** | — | 토픽으로 공지 게시판을 만들 수는 있으나 고정·기간 종료가 없음 |
| `community_posts` 고정 필드 | **없음** (`is_pinned`/`is_notice` 0건) | — | — |

→ **커뮤니티 피드 공지·고정은 없는 기능**이다. 새 테이블을 만들지 않고 **기존 게시글 엔진에 필드를 추가**해 댓글·신고·숨김·수정 이력·감사를 그대로 재사용한다. 앱 전체 공지(`app_notices`)는 「커뮤니티 공지」 화면에서 링크로만 안내한다.

### F-5-2. 설계

| 항목 | 설계 |
|---|---|
| 공지 작성 | 관리자가 Admin 「공지 작성」에서 작성 → `community_posts` 행, `origin_kind='operator'`(신규 값), `user_id`=**작성한 관리자 본인**(누가 썼는지 추적), 화면 작성자명 `display_author_name='DIBAY 운영팀'`(기존 컬럼). 카테고리 선택 또는 「전체 피드」 |
| 노출 기간 | `notice_starts_at`, `notice_ends_at` (PHT 입력 → UTC 저장). 예약 게시 가능. 종료 시각이 지나면 **조회 조건으로 자동 해제** (크론 불필요) |
| 공지 수정 | 같은 게시글 PATCH (리비전 기록, CAS) |
| 공지 종료 | 「공지 종료」 = 고정 해제 + `notice_ends_at=now` (글은 일반 글로 남거나 숨김 선택) |
| 회원 글 상단 고정 | `pinned_at, pinned_until, pinned_by, pin_scope('feed'|'topic'), pin_rank` (M10). 사유 선택, 작성자 알림(O-8) |
| 고정 한도 | 피드 전체 3개, 카테고리별 2개 (O-6 확정). 한도 검사는 DB 함수에서 잠금 후 수행 (동시 고정 경합 방지) |

## H-4. 승인 방식

- 「설계 승인」(또는 「O-n 수정 후 설계 승인」) → 승인 ① 범위만 진행하고 검증 보고에서 멈춤.
- 검증 보고 확인 후 「운영 반영 승인」 → 승인 ② 진행, 완료 보고(원인·수정·검증·배포 SHA·남은 위험).
- 승인 ① 때 함께 받을 결정: O-6 고정 한도, O-12 홍보 담당 운영자 지정 (지정은 승인 ② 전까지 가능).
