## 4. 사용자가 늘면 (계산식 · 한도는 NOT_PROVEN)

- 활발히 쓰는 사용자 1명 ≈ 분당 동작 4~6회 × 동작당 50~150건 ≈ **분당 200~900 Supabase 요청** (Owner iPhone 실측 분당 633~1,015와 같은 범위).
- 화면을 켜 두기만 해도(메신저): 수신 확인 약 5.7회/분 × 약 5건 + 접속 상태 5회/분 × 약 2건 ≈ **분당 약 40건**.
- 동시 활성 100명 ≈ 분당 2만~9만 건, 1,000명 ≈ 분당 20만~90만 건. 지금 Supabase 요금제의 요청·연결 한도는 확인하지 않았다(**NOT_PROVEN**) — 한도와 비교한 판정은 다음 단계.

## 5. 대책 (우선순위 · 각각 설계·승인 후 구현)

1. **F1 거래 상세 → 채팅방 생성 중단**: 메시지를 처음 보낼 때만 방 생성(조회는 기존 방 id 조회만). 이미 생긴 빈 방 정리는 별도 데이터 승인.
2. **F2 목록 사전조회 축소**: 화면에 보이는 몇 개만·한 번만, 돌아올 때 다시 받지 않음(메신저 28개·배달 카드·거래 상품·홈 탭).
3. **F3 조회 중 쓰기 제거**: 바뀐 것이 있을 때만 쓰기(주문 채팅 S1 과 같은 원칙) — 알림 지우기는 대상이 있을 때만, 조회수는 사용자·기간당 1회, `updated_at` 은 내용이 바뀔 때만.
4. **F4 반복 계산 제거**: 자기 반향 무시, 같은 행 1회 조회, 배지 계산 1회 공유(S2 계속).
5. **F5 상시 요청**: 수신 통화 확인은 통화 규정(분리 반영·실기 검증) 대상 — 별도 설계·승인.
6. **재발 방지 장치**:
   - 동작별 요청 예산을 계약 문서로 고정(이 표가 기준선).
   - 서버에서 API 요청 1건당 Supabase 호출 수를 세어 기존 모니터링 집계(`cm_monitoring_rollup_hourly`)에 기록 → 예산 초과 시 경보.
   - 핵심 API 마다 「DB 호출 수·쓰기 0건」 단위 테스트(주문 채팅 S1 테스트 방식) → 늘어나면 CI 실패.
   - 공통 인증 RPC·프로필 조회 비용은 Owner 결정대로 별도 감사.
