## 5. 화면 이동·팝업 종료 동작표 (확정)

| 상황 | 정확한 동작 |
|---|---|
| 요청 전송 | DB **pending** 저장 · 상대에게 실시간 알림 |
| 상대가 앱 사용 중 | 현재 화면 위 **정중앙** 수락·거절 팝업 |
| 다른 화면으로 이동 | 팝업은 닫힐 수 있음 · **요청은 유지** |
| 팝업 X·뒤로·바깥 터치 | **거절 아님** · 나중에 확인 · 받은 요청에 보관 |
| 앱 재시작·재로그인 | 미처리 요청 **재조회 가능** |
| 친구 요청 목록 | 받은 요청에서 수락·거절 |
| 수락 | DB **한 트랜잭션**으로 요청 상태 변경 + **양쪽** friend 행 |
| 거절 | 요청 → rejected · **friend 행 생성 안 함** |
| 여러 기기에서 수락 | **1회만** 처리 · 다른 기기 팝업·목록 동기화 |
| Realtime 누락 | **DB 재조회로 복구** 가능해야 함 |

## 6. DB 요청 상태 · 수락 트랜잭션 (설계)

### 6.1 요청 상태

| status | 의미 |
|---|---|
| `pending` | 미처리 · 목록·팝업 대상 |
| `accepted` | 수락 완료 · 양쪽 friend 존재 |
| `rejected` | 거절 · friend 없음 |
| `cancelled` | 요청자 취소(정책 유지 시) |

저장소: 레거시 `community_friend_requests` **재계약** 또는 동등 pending 테이블 — **마이그레이션은 Owner DB 승인 후**.  
현재 LOCK 하에서는 pending INSERT **금지 유지**.

### 6.2 수락 (원자)

단일 DB 트랜잭션(또는 동등 RPC):

1. pending 행을 `accepted`로 갱신 (이미 처리됨 → no-op / idempotent)  
2. `owner=A→target=B` friend 행 upsert  
3. `owner=B→target=A` friend 행 upsert  
4. 실패 시 전체 롤백 · 부분 friend만 남지 않음

### 6.3 거절

- pending → `rejected`  
- friend INSERT **없음**  
- (정책) 재요청 쿨다운은 기존 문구/헬퍼가 있으면 구현 승인 시 재연결

### 6.4 동시성·가드

| 케이스 | 처리 |
|---|---|
| 중복 요청 (A→B pending 존재) | 새 pending 거부 또는 기존 유지(idempotent) |
| 이미 양쪽/한쪽 friend | 정책: 요청 불필요 · 즉시 안내 |
| 차단 관계 | 요청 거부(기존 차단 게이트) |
| 다중 기기 동시 수락 | 첫 성공만 · 이후 idempotent |
| 거래·주문·배달 peer | **friend INSERT 경로에 연결 금지** |

### 6.5 동기화

- Realtime/푸시: 수신 팝업·목록 무효화  
- 폴백: 홈/친구 탭 포커스·앱 기동 시 pending **GET 재조회**
