# 문서 H — 2단계 금전 정책안 (D-2 · D-3 최종안 · 승인 대기)

- 작성 2026-10-21 PHT · 기준 `35a12fb8` + 운영 DB 읽기 전용 확인(함수 원문 `store_commission_charge_order_internal`·`store_commission_resolve_policy`, 정책·상품권 집계).
- Owner 원칙(2026-10-21 지시, 고정): 상품권·쿠폰·Coin·Cash 를 **하나의 자산으로 통합하지 않는다** · 상품권 사용·환불·잔액 별도 추적 · 쿠폰 할인 부담 주체 구분 · Coin 적립·사용 원장 유지 · Cash 충전·차감·환급 원장 유지 · 동일 주문 중복 지급·중복 차감 차단 · 수수료는 기존 승인 계약·실제 계산 근거 유지 · **입금 확인 없는 Cash 충전 금지** · 환불 시 금전 역거래 원자성 보장 · 기존 계약 임의 변경 금지 · 과거 데이터 정정·소급 금지.
- 이 문서는 **정책안**이다. 2단계 구현은 Owner 승인 후.

## 1. 현행 계약 — 코드·DB 로 확인한 실제 계산

| 항목 | 현행 (근거) |
|---|---|
| 결제 | 고객 → 매장 직접 결제 (`payment_amount`, 배달비 포함). 플랫폼은 이 돈을 받지 않는다. |
| 매장 부담 쿠폰 | `store_funded_amount` — 주문 금액에서 빠지고 매장이 부담. 플랫폼 지급 없음. |
| 플랫폼 부담 쿠폰 | `platform_funded_amount` — 고객 할인분을 플랫폼이 매장에 보전해야 함(플랫폼 지급 의무). |
| 상품권 | 고객이 회원 POINT 로 플랫폼에서 구매 → 매장에서 사용(`gift_redemption_amount`). 사용 시 상품권 수수료 `platform_fee_rate`(운영 상품 10%, 일부 0%)를 뗀 **매장 순액 `merchant_net_amount`** 가 `gift_certificate_revenue_ledger` 에 기록(REVENUE_CREATE→REVENUE_AVAILABLE). 플랫폼이 매장에 지급할 의무. 현재 현금화·전환 API 는 410(지급 경로 없음). |
| 판매 수수료 기준액 | `store_commission_charge_order_internal`: **기준액 = payment_amount + gift_redemption_amount + platform_funded_amount** (SSOT 문서 108행 "고객 결제 + 상품권 + 플랫폼 쿠폰"과 일치). |
| 판매 수수료 | 정책(매장→업종2→업종1→기본) `fee_percent`(현재 카테고리 7%) × 기준액, **원 단위 절사(floor)** + `fixed_fee`(현재 0). 조리 이후 상태 첫 진입 시 1회, 캐시 차감·부족분 미납(`store_sale_fee_obligations`, 주문당 1행 UNIQUE). |
| 배달비 수수료 | 별도 `delivery_fee_mode`(현재 전 정책 `none`). `percent` 로 바꾸면 배달비 × %가 **추가** 부과. |
| Coin | 매장 지갑. 현재 코드: 완료 시 `gift_redemption_amount + platform_funded_amount`(총액) 만큼 적립(env `DIBAY_CURRENCY_SALE_RECOGNITION_LIVE` 일 때). 출금 가능, 충전 불가. |
| Cash | 매장 선불 지갑. 충전(관리자 승인) → 수수료·광고비 차감. 출금 불가. |

## 2. 계산 사례 (같은 주문으로 비교)

주문: 상품 ₱1,000 · 배달비 ₱50 · 매장 부담 쿠폰 ₱100 · 플랫폼 부담 쿠폰 ₱40 · 상품권 ₱300(상품권 수수료 10%) · 수수료 정책 7%.

| 단계 | 금액 |
|---|---|
| 주문 총액 | 1,000 + 50 = **1,050** |
| 할인 | 매장 부담 100 + 플랫폼 부담 40 = 140 |
| 상품권 차감 전 | 1,050 − 140 = 910 |
| 상품권 사용 | 300 |
| **고객 → 매장 직접 결제** | 910 − 300 = **610** |
| 상품권 수수료(플랫폼 수익) | 300 × 10% = **30** → 매장 순액 270 |
| **플랫폼 → 매장 지급 의무** | 상품권 순액 270 + 플랫폼 쿠폰 40 = **310** |
| 판매 수수료 기준액(현행) | 610 + 300 + 40 = **950** (배달비 50 포함) |
| 판매 수수료(현행) | floor(950 × 7%) = **66** (캐시 차감) |
| 매장 최종 | 610 + 310 − 66 = **854** |
| 플랫폼 최종 | 상품권 수수료 30 + 판매 수수료 66 − 쿠폰 보전 40 (+상품권 판매대금 300 은 이미 POINT 로 수령) |

검산:
- 주문 총액 1,050 의 출처 = 고객 직접 결제 610 + 상품권 300(고객이 미리 POINT 로 플랫폼에 지불) + 플랫폼 부담 쿠폰 40 + 매장 부담 쿠폰 100 = **1,050** ✓
- 매장 최종 854 = 1,050 − 매장 부담 쿠폰 100 − 판매 수수료 66 − 상품권 수수료 30 ✓
- 각 금액은 원장 한 곳에만 기록된다: 610 = `store_orders.payment_amount` · 300/30/270 = `gift_certificate_redemptions` + `gift_certificate_revenue_ledger` · 40 = `platform_funded_amount`(→ Coin) · 100 = `store_funded_amount` · 66 = `store_sale_fee_obligations` + `business_cash_ledger` SALE_FEE.

### 현행 코드의 결함 (FIN-03, 금액으로)

| 경로 | 이 주문에서 매장에 주는 금액 | 문제 |
|---|---|---|
| Coin 적립(플래그 ON) | 300 + 40 = **340** | 상품권 수수료 30 을 빼지 않음 → 30 과다 |
| 상품권 매출 원장 | **270** 「지급 가능」 기록 | 지급 경로 410 → 미지급. 플래그 ON 이면 Coin 340 과 **이중 지급 위험** |
| 지급 의무 분류 | 상품권 300 을 "상품권 레일에서 지급"으로 제외, 쿠폰 40 만 의무 | 실제 레일 지급 없음 |

## 3. D-2 — 플랫폼 보유분(상품권·플랫폼 쿠폰) 지급 정책

Owner 원칙상 상품권과 쿠폰을 한 자산으로 합치지 않는다 → 아래 두 안 모두 **자산을 분리**한다.

| 안 | 상품권(사용분 순액) | 플랫폼 부담 쿠폰 | 위 사례 매장 지급 | 장점 | 단점 |
|---|---|---|---|---|---|
| **A (권장)** — 레일 분리 | **상품권 정산 레일**: `gift_certificate_revenue_ledger` REVENUE_AVAILABLE(270) → 관리자 정기 지급(참조번호 필수) → PAID_OUT 원장. Coin 에는 넣지 않음 | **Coin**: 완료 시 40 적립(`sale_coin:{order}` 멱등) → 기존 Coin 출금 | 상품권 270(레일) + Coin 40 = **310** | 상품권 사용·환불·잔액·부채를 상품권 원장에서 끝까지 추적, 쿠폰 부담 주체 분리, Coin 은 기존 원장 유지 | 상품권 지급용 관리자 화면·RPC 신설 필요 |
| B — Coin 통일 지급(자산은 분리 기록) | 레일에 순액 270 기록 후 같은 트랜잭션에서 `CONVERTED_TO_COIN` 소진 행 + Coin 270 적립 | Coin 40 | Coin **310** | 지급 수단 1개(출금 흐름 재사용) | Coin 잔액에 상품권 몫이 섞여 회계상 성격 구분이 원장 연결로만 남음 — 원칙("임의 통합 금지")과 충돌 소지 |

공통 수정(어느 안이든): Coin 적립액에서 상품권 총액(300) 제거 또는 순액화 → **현행 30 과다 지급 차단**, 지급 의무 분류 함수 항등식 정정, 환불 시 역거래(상품권 레일 REVERSED · Coin 역분개)를 환불 트랜잭션 안에서 함께 처리, 주문당 지급 멱등키(중복 지급 차단). 과거 행은 정정하지 않음(D-5).

## 4. D-3 — 판매 수수료 기준액

Owner 지시: 기존 승인 계약·계산 근거 유지, 임의 변경 금지 → **권장 = 현행 유지 + 계약 명문화 + 이중 부과 잠재 결함 차단**.

| 안 | 기준액 | 위 사례 수수료 | 변화 |
|---|---|---|---|
| **현행 유지 (권장)** | 고객 결제(배달비 포함) + 상품권 + 플랫폼 쿠폰 = 950 | **66** | 계약 그대로. 문서에 "배달비 포함, 상품권 사용분은 상품권 수수료와 별개로 판매 수수료 대상"을 명시 |
| 대안 1 — 배달비 제외 | 950 − 50 = 900 | 63 | 매장 −3, 계약 변경(승인 필요) |
| 대안 2 — 상품권분 제외 | 950 − 300 = 650 | 45 | 상품권 이중 수수료(10%+7%) 해소, 계약 변경 |
| 대안 3 — 둘 다 제외 | 600 | 42 | 계약 변경 |

**계약 변경 없이 고칠 잠재 결함**: 정책의 `delivery_fee_mode='percent'` 를 켜면 배달비가 기준액(결제액 안)과 배달비 수수료 양쪽에 들어가 **이중 부과**된다(현재 해당 정책 0건). → 관리자 정책 저장 API·SQL 에서 `percent` 모드 설정 시 기준액에서 배달비를 빼도록 하거나(계약 해석 필요), 정책 결정 전까지 `percent` 저장을 거부한다. **권장: 저장 거부**(현행 계약 보존).

## 6. Owner 승인 요청 (2단계)

1. **D-2: 안 A(레일 분리) 승인** — 상품권은 상품권 정산 레일로, 플랫폼 부담 쿠폰만 Coin 으로.
2. **D-3: 현행 계약 유지 + 명문화 + `delivery_fee_mode=percent` 저장 거부** 승인 (대안 1~3 은 계약 변경이라 별도 결정).
3. **D-4 세부**: Cash 충전 수취 방법(플랫폼 계좌/GCash 번호), 1회·월 상한, 승인 권한(business vs super_admin).
4. 위 승인 시 2단계 구현 착수 범위: G-1 §5 전 블록(FIN-10 선행 → 2-A 캐시·미납 → 2-B 지급 레일 → 2-C 환불 원자화 → 2-D 상품권 → 2-E 쿠폰 분할 → 2-F 레거시 정산).
