## 1. 현재 구조의 중복 (사실)

### 1.1 같은 일을 하는 진입점 4곳
| # | 위치 | 하는 일 |
|---|---|---|
| E1 | 알림 › 푸시·알림 발송 `/admin/notifications/create` | 캠페인 작성·발송 |
| E2 | 광고·배너 › 푸시 캠페인 (`admin-menu.ts` `ads-push-campaigns`) | **E1 과 같은 URL** 을 다른 메뉴에 한 번 더 |
| E3 | 고객지원 › 공지 상세 `/admin/app/notices/[id]` 「알림 보내기」 | E1 을 원본 연결 상태로 열기 |
| E4 | 플랫폼 운영 › 이벤트 배포 › Push (`platform-events/[eventId]/distribution/push/send`) | 별도 화면에서 캠페인 참조 후 같은 send 엔드포인트 호출 |

### 1.2 같은 내용을 두 번 쓰는 구조
- 공지·시스템은 **고객센터 글(app_notices) + 알림 캠페인** 두 객체가 필수 (`campaign-source-authority.ts` RULE 1·2·5). 운영자는 글 작성 → 알림 작성 2단계, 제목·내용을 두 번 쓴다.
- 오늘 배포한 `53a17eec8` 은 이를 「자동 게시」로 숨겼지만, **알림 1건 = 고객센터 글 1건이 계속 생긴다** → 게시판에 알림 사본이 쌓이는 새 중복. (→ 본 설계안 채택 시 되돌림 대상)

### 1.3 쓰이지 않고 쌓이는 상태
운영 DB `admin_notification_campaigns` 134건:
- 실제 회원 발송(QA 아님) **16건** (공지 10 · 마케팅 4 · 시스템 2)
- 발송 안 된 초안(QA 아님) **30건**, QA·테스트 캠페인 **85건**
- 반복 발송 활성 1건, 예약 3건
- 고객센터 글 32건 전부 QA·테스트 글(회원에게 게시 상태)

→ 「임시 저장」과 「테스트 = QA 캠페인 생성」이 목록을 채우고, 실발송은 전체의 12%.

### 1.4 화면에서 운영자가 고르는 축이 겹친다
유형(공지/시스템/마케팅) · 대상(마케팅 동의 포함) · 채널 · 원본 · 딥링크/웹 URL 이 서로 얽힘.
예) 「마케팅 유형」과 「마케팅 동의 대상」을 따로 고름, 원본을 고르면 딥링크가 정해지는데 딥링크 입력란도 있음.

## 2. 설계 원칙
1. **알림 1건 = 객체 1개** — 알림은 알림이고, 글은 필요할 때만 「목적지」로 고른다. 내용을 두 번 쓰지 않는다.
2. **진입점은 여러 곳, 화면·엔진은 하나** — 공지·이벤트 화면의 버튼은 같은 발송 화면을 목적지가 채워진 상태로 연다.
3. **운영자가 고르는 축은 4개**: 내용 · 눌렀을 때 열 화면 · 받는 사람 · 시점.
4. **흔적은 실발송만** — 테스트·미발송 작성은 캠페인 목록을 채우지 않는다.

## 3. 프로세스 (권장안)

```
[알림 보내기] 한 화면
 ① 내용      제목 · 메시지 · (이미지)
 ② 누르면    ◉ 알림 내용 보기 (기본)  ○ 고객센터 글  ○ 이벤트  ○ 앱 화면
 ③ 받는 사람  ◉ 전체 회원  ○ 광고 수신 동의 회원  ○ 회원 지정
 ④ 시점      ◉ 지금  ○ 예약
 ─────────────────────────────
 [내 폰으로 테스트]   [발송 ▶] → 확인창 1회 (인원·사유) → 상세 화면
```

| 축 | 결정 규칙 | 없애는 것 |
|---|---|---|
| ① 내용 | 제목·메시지만 필수 | 별도 「게시글 본문」, 이미지 2벌 |
| ② 목적지 | 기본 = **알림 상세** `/notifications/{id}` (이미 존재, 구 캠페인이 이 경로로 열림) · 글/이벤트는 게시 중인 것만 선택 · 앱 화면은 허용 경로 목록에서 선택 | 원본 필수 규칙, 딥링크·웹 URL 직접 입력 |
| ③ 받는 사람 | 「광고 수신 동의 회원」= 마케팅(광고성) 발송, 나머지 = 공지. **유형 선택 삭제** | 유형 칩, 대상 중 마케팅 중복 |
| ④ 시점 | 지금 / 예약 | 반복 발송은 캠페인 상세 「반복으로 전환」으로 이동 (활성 1건) |
| 채널 | 기본 푸시+알림함, 고급 설정에서만 변경 | — |
| 시스템 유형 | 수동 발송 제외 — 서버 자동 알림(거래·계정) 전용 (수동 실발송 2건, 8/3 이후 없음) | — |

### 테스트·초안
- 「내 폰으로 테스트」 = **캠페인을 만들지 않는 테스트 발송** (입력 내용 그대로 내 계정에만, 감사 로그만 기록). QA 캠페인 85건 같은 누적 중단.
- 「임시 저장」 삭제 — 미발송 초안 30건은 한 번도 발송되지 않음. 나중에 보낼 것은 「예약」으로.

## 5. 위험·확인
- **Owner 결정 필요 1건**: RULE 5 「제목·본문만으로 공지 발송 금지」는 Owner 하드락 규칙이다. 본 설계는 이 규칙을 「목적지 필수(알림 상세 포함)」로 바꾼다. 승인 없이는 구현하지 않는다.
- 광고성 판정이 「대상」으로 옮겨가므로, 광고 수신 동의 회원 외 대상에게 광고 문구를 보내지 않도록 확인창에 「광고성 알림은 동의 회원에게만」 안내 1줄.
- `53a17eec8` 자동 게시로 생긴 글은 현재 0건 (최근 1일 생성 글 = 08:19 PHT 마케팅 「test」 1건, 고객센터에서 직접 작성 · 연결 캠페인 0건). 설계 채택 전 실발송이 생기면 그 글은 정리 대상.
- 실기기 검증(Android·iPhone 수신, 알림 탭 → 목적지 열림)은 구현 후 별도 실행 — 현재 NOT_PROVEN.
