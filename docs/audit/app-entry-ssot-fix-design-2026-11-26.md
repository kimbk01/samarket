## 1. 감사 정정 (앞선 보고의 틀린 숫자 — 작업자 잘못)
- 앞선 보고의 「네이티브 시작 1.24초」는 틀렸다. 진입 계측의 `nativeStart`·`webviewReady`·`firstHtml` 은 **웹 문서 시작(performance.now 0) 기준**으로 네이티브가 주입한 값이다 [코드 `MainActivity.java:2168-2186, 2202-2226`]. 탭~문서 시작 구간은 계측에 없다.
- 실기 logcat 으로 다시 잰 탭(ActivityTaskManager START) 기준 구간(Samsung 8회 · Xiaomi 1회) [실기]:

| 구간 | Samsung | Xiaomi(배포 직후) |
|---|---|---|
| 탭 → 앱 프로세스 onCreate(OS 화면 계획) | 0.64~0.67초 | 1.40초 |
| 탭 → 초록 OS 화면 표시 | 1.10~1.19초 | 2.59초 |
| 탭 → 웹 문서 시작 | 1.07~1.15초 | 2.54초 |
| 탭 → 웹 「준비」 신호 | 5.19~6.64초 | 13.08초 |
| 탭 → OS 화면 걷힘 | **5.38~6.83초** | **13.22초** |

- 결론: OS 화면 시간의 대부분(Samsung 약 4.1~5.5초)은 **웹 문서 시작 → 웹 「준비」** 구간이다. 네이티브 구간은 약 1.1초다.

## 2. 근본 원인 (한 문장)
**콜드 진입의 OS 화면 해제 조건이 「목적지 화면 완성」(문서 → JS → React → 로그인 → 앱 안 이동 → 서버 데이터 → 목적지 그림)에 묶여 있다.** 그래서 OS 화면이 로딩 전체를 가린다.
- 원격 실행이다: `server.url` = 운영 사이트 [코드 `capacitor.config.ts:53`]. 로컬 실행은 `localRuntime:false` [코드 `capacitor-www/dibay-runtime-mode.json`].
- 해제 신호는 웹 하나다(H1-1) [코드 `startup-metrics.ts:502-540`]. 신호 앞에 유지 조건이 4겹 있다:
  1. 알림 목적지 일치
  2. 23-9 목적지 그림
  3. D3 복원 목적지 그림
  4. 생명주기 이동 예정
- 그 결과:
  - 같은 「알림 → 채팅방」이 앱 꺼짐(OS 화면으로 가림)과 앱 켜짐(「입장 중」 0.9초 보임 · D-13)에서 다르게 보인다.
  - Android·iOS 도 다르다(D-3·D-4).
- 11-08 이후 9회 수정이 모두 「유지 조건」만 바꿨다 → 흰 화면 ↔ 긴 OS 화면 맞바꿈 반복.
- 레거시 앱(카카오톡·배민) 구조: OS 화면은 프로세스 시작~앱 첫 화면까지이고, 내용은 앱 안에서 저장본·뼈대 → 채움으로 그린다. 카카오톡은 「이전 화면 복원·스플래시 0」 관찰 기록만 있다 (`DIBAY_APP_LIFECYCLE_SSOT.md:24`). 레거시의 잠금·알림 진입 실측은 없다(NOT_PROVEN).

## 3. SSOT 계약 (단일 규칙 — 모든 진입 경로 공통)
**E-1 (OS 화면).** OS 화면은 「앱 첫 화면이 아직 없을 때」만 존재한다.
- 콜드 진입(①아이콘 ⑤알림·딥링크(잠금 포함) ⑥시스템 종료 후 재실행)에서 OS 화면은 **앱 셸의 첫 실제 화면(머리글·하단 탭·본문 틀)이 그려지는 즉시** 걷힌다.
- 목적지 완성·데이터·로그인 결과를 기다리지 않는다.
- 웜 진입(②아이콘 복귀 ③잠금 해제 ④켜진 앱 알림)에는 OS 화면이 없다(현행 유지 · [실기] Samsung 3/3).

**E-2 (목적지).** 목적지(직전 화면 복원·알림 대상·첫 화면 설정)는 OS 화면이 걷힌 **뒤 앱 안에서** 그 화면 자체로 그린다.
- 순서: ① 기기 저장본(채팅방 IndexedDB 등) ② 없으면 그 화면의 뼈대. 「불러오는 중…」·「채팅방 입장 중…」 같은 문구·스피너 대기 화면은 진입 경로에서 쓰지 않는다.
- 콜드·웜, Android·iOS, 알림·복원 모두 **같은 함수·같은 화면**이다.

**E-3 (화면 전환).** 진입 목적지에는 들어오는 움직임이 없다(현행 #607 규칙 유지). 웜 복귀에 빈 화면 프레임이 없어야 한다.

**E-4 (인트로).** 인트로는 콜드 아이콘 실행에서 OS 화면 다음에 나온다.
- **어드민이 정한 시간(1~5초)이 보이는 시간 기준으로 정확히 끝난다.** 웹 목적지 준비를 기다리지 않는다.
- 인트로 뒤에는 E-1 의 앱 첫 화면이 있다. 인트로가 끝났는데 앱 첫 화면이 아직 없으면 OS 화면 그림으로 이어 가린다. 이 경우만 정한 시간보다 길어진다(아래 §6 경계).
- 알림·딥링크·웜 진입에는 인트로가 없다(현행 유지).

**E-5 (해제 단일 주체).** 콜드 진입의 OS 화면 해제 조건은 「앱 셸 첫 화면 그림」 **하나**다. 유지 조건(알림 목적지·23-9·D3·생명주기 이동)은 해제에서 제거한다. 네이티브 고장 판정(T_doc 10초·T_js 8초·T_release 15초 · H1)은 그대로 둔다.

## 6. 남는 경계 (숨기지 않음)
- **셸 첫 화면 자체가 늦다.** 원격 실행이라 탭 → 셸 첫 화면은 Samsung 기준 문서 시작 1.1초 + 웹 셸 그림이다.
  - 운영 중앙값 shellReady(문서 기준)는 아이콘 3.70초, 복원 2.41초 → 탭 기준 약 3.5~4.8초 [운영+실기 합산 추정 → 구현 후 실측으로 확정].
  - E-1 로 줄어드는 것은 「셸 이후 → 목적지 완성」 구간이다(복원 약 2.1초 [운영]).
  - 셸 이전 구간(문서·JS·React)은 이 설계로 줄지 않는다.
- 셸 이전 구간을 레거시 앱 수준(프로세스 시작~첫 화면 약 1초)으로 줄이는 방법은 **앱 전체를 앱 안에 넣는 로컬 실행(Option A)** 뿐이다.
  - 07-27 껍데기 화면으로 전환했다가 제품 화면 회귀로 같은 날 되돌렸다 (`docs/dibay-local-runtime-cutover-p0-recovery.md`).
  - 「앱 전체가 로컬 번들이 되기 전 재전환 금지」로 잠겨 있다.
  - 이 설계에 넣지 않는다. 따로 타당성 감사가 필요하다(Next 서버 컴포넌트·인증 쿠키·배포 구조).
- 인트로: 셸 첫 화면이 정한 인트로 시간보다 늦으면(예: Xiaomi 배포 직후 13초) 그 차이만큼 OS 화면 그림이 이어진다. 그 외에는 정한 시간 정확히다.
- Xiaomi 백그라운드 즉시 종료(D-6 · 시스템 정리 기능, DIBAY 약 280MB)는 이 설계 범위 밖이다. 메모리 감사는 별도로 한다. 종료돼도 E-1·E-2 로 같은 화면이 빨리 나오게 하는 것이 이 설계다.

## 8. 위험·롤백
- 위험:
  - 셸에서 걷은 뒤 목적지 뼈대 → 저장본/실데이터로 바뀌는 순간 화면이 한 번 바뀐다. 레거시 앱과 같은 방식이고, 「입장 중」 문구 화면은 없다.
  - 저장본이 오래되면 잠깐 옛 내용이 보인다. 메신저 저장본은 이미 쓰는 구조다(`isAuthoritativeMessengerRoomEntrySnapshot`).
  - 네이티브 C3·C5·C6 는 구 바이너리에 적용되지 않는다. 구 바이너리는 웹 C1·C2 만 적용된다 → 구 바이너리 동작을 시험 행렬에 포함한다.
