### 3-3. 원장별 수정 설계 (원장·API 재사용)

**마이페이지 배너**
- **삭제 (AD-01, J-4):** `DELETE /api/admin/banners/[id]` 를 추가한다. 다른 배너와 정책을 맞춘다.
  - 노출된 적이 없는 초안(`status=draft`, `impression_count=0`): 실제 삭제.
  - 그 외: `status='archived'`, `is_active=false` 로 보관. 이력은 보존.
  - `status` 컬럼에 CHECK 제약이 없어 **DB 변경 없이** 가능하다 (운영 DB 제약 조회로 확인).
  - `admin_banner_change_logs` + 감사 기록을 남긴다.
- **기간 적용 (AD-05):** 고객 리더 2곳(`load-mypage-cms-pack.ts`, `mypage-summary.server.ts`)에 `status`·`start_at`·`end_at` 조건을 추가한다. 고객에게 보이는 변화가 생기는 유일한 변경이다. 운영 행이 0건이라 지금 보이는 차이는 없다.
- **경로 정리 (AD-03):**
  - `/admin/banners` → `/admin/my/banners` 로 redirect.
  - `/admin/banners/[id]` → `/admin/my/banners/[id]/edit` 로 redirect. 상세 화면의 미리보기와 노출 토글은 편집 화면으로 옮긴다.
- **기타:** PHT 표시(AD-07). 이미지 업로드(AD-08)는 기존 배너 업로드 API 를 재사용하는데, 어느 것을 쓸지는 구현 전에 확인한다(NOT_PROVEN).

**프로모션 배너**
- **목록 (AD-04):** 「노출 설정」 버튼 라벨을 「수정」으로 바꾼다. 이동 경로(이벤트 `#distribution`)는 그대로다. 수정 위치를 하나로 유지하기 위해 목록에서 직접 편집하는 기능은 만들지 않는다.
- **중지 (AD-09):** 배너 채널만 `enabled=false` 로 저장한다. 팝업·푸시·알림 설정은 다시 쓰지 않는다. 기존 `distribution` PUT 에 채널 단위 갱신을 추가한다.
- 운영 목록의 QA 데이터 7건은 정리하지 않는다 (운영 데이터 변경은 별도 승인 사항).

**피드 배너 (AD-10)**
- `PATCH /api/admin/feed-ads/[id]` 를 신설한다. 기존 `feed-ad-campaigns-db` 모듈에 update 함수를 추가하고, 감사 기록을 남긴다.
- 출처별로 수정 범위를 다르게 둔다:
  - `ADMIN_DIRECT`: 이름 · 우선순위 · 기간 · 목적지 · 소재(이미지 · 제목 · 설명 · CTA · 목적지).
  - `MEMBER_REQUESTED` (유료): **소재만 수정 가능**. 기간 변경은 기존 보상 연장 경로(`adminCompensateExtendFeedAdCampaign`)로만 한다. 금전 계약을 지키기 위해서다 (J-8).
- `ended` 상태는 수정할 수 없다. 게시 이력은 보존한다.
- **N-01:** `status=active` 인데 종료 시각이 지난 캠페인은 관리자 화면에 「종료」로 표시한다. 표시 규칙만 바꾸고 DB 는 고치지 않는다.

**배달 홈 배너**
- 기능 변경은 없다.
- `business` 키가 없으면 CTA 를 비활성으로 두고 사유를 표시한다 (AD-06, §4 공통 규칙).

## 4. 권한 변경에 따른 기존 운영자 영향 (운영 DB 실측)

**현재 활성 관리자는 4명이다.**

| 관리자 | 등급 | 저장된 권한 행 | 실효 권한 | 감사 기록 (전체 기간) |
|---|---|---|---|---|
| A (`11111111…`) | super_admin | 있음 (19키) | master 전체 | 4,043건, 마지막 10-30 02:19 PHT |
| B (`e6e35c51…`) | super_admin | 없음 | master 전체 | 281건, 마지막 10-29 19:08 PHT |
| C (`34f0542e…`) | operator | 없음 → 운영자 기본값 | users · reports · business · ads · products 등 16키. **point · settings · manage 없음** | 2건 (비밀번호 재설정, 내 정보) |
| D (`a5bfcb70…`) | operator | 없음 → 기본값 | C 와 같음 | 0건 |

**세 업무의 실제 수행 이력**
- 포인트 충전 처리 13건, 계정 제재 11건, 실제 푸시 발송 16건(QA 19건 제외)을 운영 DB 에서 확인했다.
- 세 업무 모두 **수행자 100%가 super_admin** 이다. 운영자 C·D 의 수행은 0건이다.

| 변경 | 서버 정책 (중앙·도메인 동일) | 변경 후 차단되는 운영자 | 실제로 막히는 과거 업무 |
|---|---|---|---|
| 계정 정지 · 차단 (MB-01) | `users` 키 | **없음** (C·D 기본값에 `users` 있음) | 0건 |
| 포인트 승인 · 반려 · 조정 (FN-01) | `point` 키 | C·D (기본값에 `point` 없음) | 0건. 다만 O-2 에 따라 **지금은 가능한 업무** |
| 전체 푸시 발송 (IA-01) | J-2 에서 정하는 키 | 키에 따라 다름 (아래 J-2) | 0건 |
| 고객문의 (RS-04) | `support` 키를 신설하고 운영자 기본값에 포함 | 없음 | 0건 |
| master 메뉴 URL 조회 (IA-06) | 접근표를 super 로 | C·D (URL 직접 입력 시) | 기록 없음 |

**메뉴 · CTA · 403 일치 규칙** (구현은 기존 모듈 재사용)
1. 권한 원천은 `lib/admin/access/admin-route-access.ts` 접근표 하나다. 각 화면(route)에 조회 키와 동작별 키(action)를 적는다.
2. **메뉴:** 조회 키가 없으면 숨긴다. 기존 `filterAdminMenuByAccess` 를 그대로 쓴다.
3. **CTA:** 동작 키가 없으면 보이되 비활성으로 두고 「권한 없음: ○○ 권한 필요」를 표시한다. `canAccessAdminRoute(path, actor, action)` 을 쓴다.
4. **API:** 같은 키를 `requireAdminPermission` 으로 검사하고 403 + `admin_permission_required` 를 응답한다. 화면은 기존 오류 i18n 으로 같은 문구를 띄운다.
5. **테스트:** (route, action, 권한 조합) 표 하나로 「메뉴 노출 · CTA 활성 · API 응답」 세 값이 일치하는지 vitest 로 고정한다.

### 5-0. 판정 방법과 한계

## 8. 통합 검증 및 최소 배포 계획

**원칙**
- 단계(기준 보고서 §I 1~7)마다 Production 에 배포하지 않는다.
- 작업 브랜치에서 단계별로 커밋하고 로컬 검증한다. 서로 의존하는 변경은 묶어서 통합 검증한다.
- **main 반영 = Production 배포는 2회로 끝낸다.** 각 반영은 Owner 의 별도 승인 후에만 한다.
- 모두 웹 변경이다. 네이티브 재빌드 · 버전 증가 없음, 앱 재시작으로 반영. DB 변경은 J-10(배달 광고 대기 큐 RPC) 하나뿐이다. 승인되면 R2 에 넣고, 운영 DB 적용은 별도 승인 후 적용 결과를 확인한다. N-03 인덱스는 이번 범위에 넣지 않는다.

| 반영 | 묶음 (기준 §I 단계) | 묶는 이유 | 통합 검증 (최종 트리 1회) | 회귀 범위 | 롤백 |
|---|---|---|---|---|---|
| **R1 화면 · 메뉴** | 1 셸 + 4 메뉴 재구성 + 6 UI 표준 (§5 핵심 이탈 80개 + 공통 부품 2개, 래칫 기준선 확장) + 3 의 화면 부분 (배너 현황 · 경로 redirect · 라벨 · PHT · 미리보기 이동 · N-01 · N-02 표시) | 모두 표시 · 라우팅이고 데이터 의미는 바꾸지 않음. 메뉴 · 셸 · 화면이 서로 맞물림 | `typecheck:build` · 관련 vitest · 변경 파일 eslint · `verify:routes` · `npm run build` 1회 (라우트 변경) · CUT G 탐침(로컬, 1024/1280/1440/1600/1920) · 메뉴 key · matchPaths 계약 테스트 · 모든 leaf 렌더 스모크 | 관리자 전 화면 (고객 앱 영향 없음) | revert 1커밋 (병합 커밋) |
| **R2 권한 · 데이터 경로** | 2 권한 정합 + 3 의 쓰기 부분 (배너 DELETE · AD-05 고객 리더 · AD-09 · AD-10 PATCH) + 5 신고 통합 (RS-01 · RS-02 TS 조회 · RS-03 · RS-05) | 접근표 · CTA 비활성 · API 403 이 한 규칙이라 같이 바뀌어야 함. 신고 · 포인트 · 배너 쓰기가 모두 새 권한표를 씀 | 위 공통 검사 + 권한 조합 × (메뉴 · CTA · API) 일치 테스트 · 같은 신고를 3개 화면에서 처리 → 재조회 일치 · 통합 조회 5개 기준(§2) · 배너 등록 → 수정 → 보관 → 삭제 → 재조회 · 고객 마이페이지 기간 반영 | 관리자 쓰기 전체 + 고객 마이페이지 배너 · 피드 배너 노출 | revert 1커밋. 권한 회귀 시 접근표만 되돌려도 됨 |

- R1 을 먼저 반영하고, R2 는 R1 이 운영에서 확인된 뒤 반영한다.
- R2 반영 직전에 운영 관리자 권한 현황(§4)을 한 번 더 읽기 전용으로 확인한다. 바뀐 게 있으면 영향 표를 갱신해 보고한다.
- 반영 후 확인: 배포 SHA 확인 → 운영 화면을 읽기 전용으로 확인. 데이터를 바꾸는 확인은 QA 표식 데이터로만 하고, 실행 전에 Owner 승인을 받는다.
- CI 결과는 기다리지 않는다 (절대 금지 2번).
