## 0. 작업자 잘못 먼저
1. 11-26 D3(복원 실행도 목적지가 그려질 때까지 OS 화면 유지)는 Owner 요구 「OS 화면 최소」와 반대다. 운영 24시간(Android 복원 22회) 중앙값을 보면 첫 화면 준비 2.41초인데 OS 화면은 4.49초에 걷혔다. **약 2.1초를 OS 화면으로 더 가렸다. [운영]**
2. 실기 측정마다 `am kill`(앱 강제 종료)을 했다. 그래서 「켜진 앱인데 OS 화면이 매번 나온다」처럼 보이는 상황을 측정이 만들었다. 켜진 앱 복귀는 한 번도 측정하지 않았다.
3. 11-17~11-26 동안 「언제 OS 화면을 걷느냐」만 바꿨다(§3). 그 결과 흰 화면과 OS 화면 시간을 서로 맞바꾸는 수정이 되풀이됐다.

## 1. 정확한 원인 — 구조
**DIBAY 의 OS 화면은 「앱 시작 화면」이 아니라 「원격 웹 앱 전체 로딩을 가리는 덮개」로 쓰이고 있다.**
- 앱은 화면을 자기 안에 갖고 있지 않다. 콜드 실행마다 WebView 가 운영 사이트(`server.url` = `https://samarket.vercel.app`)를 네트워크로 연다. [코드] `capacitor.config.ts:9,53` · Android `Bridge.java:324` · iOS `capacitor.config.json` server.url.
- `capacitor-www/`(로컬 파일)는 실행 모드 파일과 빈 `index.html` 뿐이다. 첫 화면을 로컬에서 그리는 구조가 없다. [코드]
- OS 화면을 걷는 것은 웹 신호(`dismissSplash`) 하나뿐이다(H1-1). 웹 신호는 아래가 **모두 끝나야** 나간다. [코드] `lib/startup/startup-metrics.ts:502-540`
  1. 네이티브 프로세스·WebView 생성
  2. 네트워크 HTML
  3. JS(WebView 캐시 · 배포 직후는 네트워크)
  4. React 시작
  5. 로그인 확인
  6. (복원·알림) 앱 안 이동 → 서버 데이터 → 목적지 그림
- 운영 중앙값(24시간 · Android) [운영]:

| 실행 | 네이티브 시작 | 첫 HTML | React 시작 | 첫 화면(shellReady) | OS 화면 걷힘 |
|---|---|---|---|---|---|
| 아이콘 새로 실행(11회) | 1.34초 | 3.63초 | 3.47초 | 3.70초 | **3.98초** |
| 직전 화면 복원(22회) | 1.24초 | 2.39초 | 2.31초 | 2.41초 | **4.49초** |

  iOS 아이콘 실행(19회)은 걷힘 1.46초다. 네이티브 쪽 기록 칸이 없어 Android 와 같은 기준인지는 **NOT_PROVEN**.
- 레거시 앱(카카오톡·배민·당근)은 화면 틀이 앱 안에 있다. 그래서 OS 화면은 프로세스 시작~첫 네이티브 그림까지만이고, 내용은 앱 안에서 뼈대 → 채움으로 그린다.
  - 프로젝트 실측은 배민 1회뿐이다: Xiaomi 아이콘 → 민트 OS 화면 ~4.4초 → 광고 인트로 ~3초 → 홈 8.0초 (`intro-popup-entry-audit-2026-11-17.md:37`).
  - 카카오톡은 「OS 프로세스 종료 후 이전 화면 복원·스플래시 0」 관찰만 있고 숫자는 없다 (`DIBAY_APP_LIFECYCLE_SSOT.md:24`).
  - 켜진 앱 복귀·잠금 화면 알림 진입의 레거시 실측은 **없다**(NOT_PROVEN).
- 그래서 「걷는 시점」을 앞당기면 그 뒤 로딩(흰 화면·「불러오는 중」·「입장 중」)이 보이고, 늦추면 OS 화면이 길어진다. 11-08 이후 9회 감사·수정이 이 둘 사이를 오갔다(§3). **걷는 시점 조정으로는 끝나지 않는 구조 결함이다.**

## 4. 인트로 — 「정해진 시간만큼 진행되는가」 → **아니다** [코드]
- 지금 운영 상태 [운영 DB 읽기 전용 조회 17:1x PHT]:
  - 네이티브 인트로 정책 `admin_settings.launch_intro_pool_policy_v1` 은 **행이 없다**. 코드 기본값은 `enabled: true`(`lib/launch-intro/pool.ts:54`).
  - 인트로 소재 `launch_intro_creatives` 는 **0개**다.
  - 웹 인트로 `launch_intro_live.state` 는 `unpublished`(10-12 이후)다.
  - 따라서 지금 인트로가 안 나오는 이유는 「꺼짐」이 아니라 「소재 0개」다.
- 네이티브 인트로(Android·iOS 같은 계약) — 정한 시간 1~5초(기본 2초):
  - 끝나는 시점은 **max(정한 시간, 웹 준비)** 이다. 웹이 늦으면 정한 시간보다 길어지고, 상한은 붙은 뒤 10초다. [코드 NI(Android):423-435,466-472 · NI(iOS):445-449,240-243]
  - 정한 시간을 넘으면 Android 는 10초 상한에서 인트로를 걷는다. 이때 OS 화면이 이미 없어서(인트로가 있으면 덮개를 계획하지 않음 SC:61) **준비 안 된 WebView 가 보일 수 있다**(Android 결함 1).
  - 인트로 시간 타이머는 화면이 꺼진·잠긴 동안에도 흐른다. 고장 판정은 보이는 시간만 센다 (NI:336,342 vs MA:2279-2285).
  - Android·iOS 모두 「아이콘 실행」에서만 고른다. 알림 실행은 인트로 없음.
  - 복원 실행은 Android 는 `showOnOsRestore` 설정을 따르고, iOS 는 restore 를 못 만들어 아이콘 실행처럼 나온다(**다름**).
- 웹 인트로(지금 unpublished):
  - 장면 1~10초, 합계 5초 제한이고, 타이머는 OS 화면이 걷힌 뒤 시작한다.
  - 끝난 뒤 목적지가 그려질 때까지 퇴장 화면이 남는데, **상한이 없다** [코드 LaunchIntroRoot.tsx:241-249].
  - 그래서 정한 시간 + 목적지 준비 시간이 된다.
- 결론: 두 인트로 모두 「정한 시간」은 최소 시간일 뿐이다. 실제 끝은 웹 준비에 묶여 있다. Owner 요구 「로딩 시간을 채우는 것이지 더하는 것이 아니다」와 맞추려면, 인트로가 OS 화면을 대신해 로딩을 덮어야 한다(OS 화면 → 인트로 순서 · 인트로 동안 웹 준비). 지금 네이티브 인트로가 그 구조이긴 하나, 웹이 늦으면 늘어나는 문제는 같다.

## 7. 해결 방향 (설계 전 · Owner 결정 필요 — 임의 선택 안 함)
- 원인 A1 은 「걷는 시점」이 아니라 「첫 화면이 원격」이라는 구조다. 레거시 앱과 같은 구조는 **첫 화면 틀(하단 탭·머리글·뼈대)을 앱 안(로컬)에 두고**, 그것이 그려지는 즉시 OS 화면을 걷는 것이다. 내용·목적지는 앱 안에서 뼈대 → 채움으로 그린다.
