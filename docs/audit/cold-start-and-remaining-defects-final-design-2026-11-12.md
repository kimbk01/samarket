# 첫 진입 시작 화면 지연 + 남은 결함 — 최종 설계안 (2026-11-12 · 설계만, 구현 없음)

측정: 운영 `c47a218`(S2 되돌림 반영) · 09:10~09:20 PHT · 샤오미 태블릿(Android, 앱 1.2.6/40) · 삼성 M15(1.2.6/40) · 로그인 회원 · `am force-stop` → `am start -W` · 기기 로그(logcat) + WebView 계측(Navigation/Resource Timing). 기존 분석 `docs/audit/android-cold-start-deploy-cache-root-cause-2026-11-09.md`(배포마다 캐시 무효화 → Skew Protection 끔, 해결됨)를 이어서 쓴다.

**판정**: 지연은 사용자 수·서버 부하와 무관(문서 응답 0.04초, 파일 캐시 적중). 원인은 전부 **기기 안 시작 비용 + 매번 새 보안 연결**이다.
- 샤오미가 긴 이유: ①②(1.28초)가 삼성(0.26초)의 5배 — 저사양 CPU에서 **미컴파일 앱 코드**와 **메인 스레드 WebView 적재**.
- 두 기기 공통: ④ 연결 약 1초, ⑤⑥ 웹 실행 0.5~0.85초.
- 참고(배제): 「로컬 시작 화면(Local Runtime)」 방식은 2026-07 시도 후 실패·복구됨(`docs/dibay-local-runtime-cutover-p0-recovery.md` — 실루엣 화면 회귀). 이 설계는 **원격 문서 부팅 구조를 유지**한다.

## 5. 진행 원칙 (반복 실패 방지 — 이번 작업의 잘못을 고정)
1. **운영에 올려 보고 재지 않는다.** 웹 수정은 로컬 운영 빌드를 기기에 USB 역방향 연결로 띄워 **수정 전·후 숫자**를 먼저 확인하고, 효과가 확인된 것만 PR.
2. 네이티브(C1~C3)는 빌드가 필요 — Owner 일괄 빌드 규칙(빌드 제안 안 함)에 따라 Owner 가 빌드할 때 함께 반영. 그 전에는 코드·계획만.
3. 한 항목 = 한 PR. 범위 밖 발견은 목록에만.
4. 보고는 측정한 것만. 나머지 NOT_PROVEN.

## 7. 남은 위험
- C2 의 WebView 미리 적재 API 는 현재 `androidx.webkit` 버전 지원 여부 미확인 — 지원 안 하면 의존성 갱신 필요(네이티브 변경 범위 증가).
- C4 지연 적재는 첫 사용 시 그 기능이 늦게 열릴 수 있음(통화 수신 경로는 통화 규정상 지연 금지 대상 — 분석 단계에서 제외 목록화).
