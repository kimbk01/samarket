## 3. 왜 배포마다 캐시가 비는가 (코드·운영으로 확인)
1. Next.js 16.1.7 `node_modules/next/dist/shared/lib/deployment-id.js`: 환경 변수 `NEXT_DEPLOYMENT_ID` 가 있으면 모든 정적 파일 주소에 `?dpl=<배포ID>` 를 붙인다. `server/config.js:678` 이 그 값을 `deploymentId` 로 쓴다.

4. 파일 이름은 내용 해시라 내용이 같으면 이름이 같다. 연속 배포 비교:
   | 비교 | 이름 같은 파일(내용 같음) | 바뀐 파일 |

   | `bf6eee6` → `70e0d6e` | 48 / 60 (**1,657,799 B, 89%**) | 12 (211,972 B) |

   → 내용이 같은 89% 도 `?dpl` 값이 바뀌어 **주소가 달라지므로** 기기 HTTP 캐시·JS 코드 캐시(주소 기준)에서 못 찾고 전부 다시 받고 다시 해석한다. 파일은 `cache-control: public,max-age=31536000,immutable` 이라 주소만 같으면 1년 재사용된다.

**원인 확정**: Skew Protection 의 `?dpl` 이 배포마다 첫 화면 파일 주소 100% 를 바꿔(실제 내용 변경은 10~20%), 새 배포 뒤 첫 실행마다 약 2MB 를 다시 받고 해석한다. 저사양 Android 에서 그 비용이 4~6초다. 하루 수십 회 배포라 거의 모든 실행이 이 경로를 탄다.

확인 못 한 것(NOT_PROVEN): `?dpl` 을 없앴을 때의 실제 시각 — 구조상 바뀐 10~20% 만 새로 받지만 실측은 변경 후에만 가능. iOS 같은 경로 영향 크기(빌드 28·29 새 배포 첫 실행 3.7~3.8초 관측 2건뿐).
