## 3. SSOT 가 안 된 원인 (정확히)
1. **OS 화면을 걷는 결정이 한 곳이 아니라 7곳에 나뉘어 있다** [코드]:
   - 네이티브: ① Android 덮개 계획(onCreate) · iOS 연속 화면 · 네이티브 인트로 ② 고장 판정(8·15초)
   - 웹 해제: ③ `releaseForInitialDestination` 경로 판정(알림 목적지·생명주기 이동)
   - 화면: ④ 경로 로딩 `loading.tsx` ⑤ 로그인 확인 `AuthSessionBoundary` ⑥ 방 게이트 `EntryEmpty` ⑦ 방 셸 진입 움직임 + 메인 화면 이동 `AppRouteTransition`
   - 이들이 서로의 **시점**에 숨은 의존을 가진다. 예: #607 움직임 조건은 「해제 시점」에 의존했다 → #610 이 해제 시점을 바꾸자 깨졌다(E12).
   - 한 곳을 고치면 다른 곳이 깨지는 구조가 반복 수정의 원인이다.
2. **「목적지 첫 화면」의 정의가 없다.**
   - 방을 기다리는 화면이 3단계(④⑤⑥)이고 각자 다른 층에 그려진다. ④⑤ 는 일반 흐름, ⑥ 은 화면 전체 고정 층이다.
   - 그래서 같은 「기다림」이 단계마다 다르게 보이고, 흐름 안 단계는 주변 변화로 밀리거나 가려진다(흰 화면 회귀 — 정확한 경로는 NOT_PROVEN).
3. **플랫폼별 입력이 다르다** [코드]:
   - 알림 목적지를 미리 아는 경로가 Android 만 있다(동기 브리지). iOS 는 홈에서 걷고 이동한다.
   - 복원 판단도 iOS 는 만들지 못한다(`AppDelegate.swift:17-26`).
   - 같은 상황이 플랫폼마다 다른 구조다.
4. **구조적 한계**: 앱이 화면을 원격(운영 사이트)으로 연다.
   - OS 화면 시간의 대부분(Samsung 탭 기준 약 4~5초)이 웹 문서·JS·로그인·이동 구간이다.
   - 레거시 앱처럼 「프로세스 시작 → 앱 첫 화면」 약 1초가 되려면 화면 틀이 앱 안에 있어야 한다(07-27 껍데기 전환 실패·잠금).
5. **검증 방식의 한계**:
   - 실기는 운영에서만 가능하다(테스트 DB 금지 · Preview 를 앱에서 열 방법 없음). 그래서 「병합 = 운영 반영 = 첫 실기」가 된다.
   - 진입처럼 기기에서만 보이는 결함은 병합 뒤에야 드러난다(E11).

## 4. 설계 대책 (원하는 것 구현 — 승인 전 구현 안 함)
### 4-1. 단일 계약 (U3·U4·U7)
**「진입 표면」 하나**를 둔다(신규 모듈 1개 = 단일 소유자):
- 입력(목적지): 알림 · 직전 화면 복원 · 첫 화면 설정 · 아이콘(지금 주소). 결정 함수 1개이고 Android·iOS 같다.
  - iOS 는 실행 때 알림 응답(`connectionOptions.notificationResponse`)으로 목적지를 미리 안다 — PR-2 네이티브.
- 그리기:
  - 목적지가 결정되면 **진입 대기 층 1개**(화면 전체 고정 · 불투명 · 목적지 모양의 뼈대)를 문서 첫 프레임부터 그린다.
  - 경로 로딩·로그인 확인·데이터 대기 단계는 모두 이 층 안에서만 바뀐다(④⑤⑥ 통합).
  - 목적지 실제 화면이 그려지면 이 층을 걷는다.
- 해제(OS 화면): 조건은 「진입 대기 층(또는 실제 목적지)의 첫 프레임」 **1개**다. 다른 조건(알림 목적지 일치·생명주기 이동 대기)은 이 층이 대신한다. 홈이 먼저 보일 일이 없으므로 OS-4 도 이 층이 막는다.
- 움직임: 진입 표면에서 붙은 화면은 움직이지 않는다. 앱 안 목록 탭만 움직인다(#611 규칙 유지).
- 켜진 앱(②③④): OS 화면은 없다(현행). 같은 진입 표면 함수로 목적지를 그린다 → 알림 「입장 중」 0.9초(D-13)도 같은 층.
- 결과: 같은 상황은 같은 화면이 된다. 해제 시점이 바뀌어도 화면이 바뀌지 않는다 — 시점 의존을 없앤다(원인 3-1·3-2 제거).

### 4-2. 인트로 (U5)
- 네이티브 인트로 시간은 보이는 시간만 센다. 정한 시간에 끝나고, 웹 준비를 기다리지 않는다.
- 뒤에는 진입 대기 층이 있다. 층의 첫 프레임이 아직 없으면 OS 화면 그림으로 잇는다 — 이때만 길어진다.
- 시험 소재 1개로 실기한다(운영 시험 저장 규칙: 알림 → 시작 revision → 백업·대조 보고).

### 4-3. 회귀를 막는 반영 방식 (E11·E12 재발 방지)
- **기능 스위치로 반영**:
  - 새 진입 표면을 운영 설정(어드민 시작 설정 `/api/admin/startup-config` 계열 — 필드 설계 시 확인)의 스위치 뒤에 둔다.
  - 기본은 끔이다. 병합해도 사용자 화면은 그대로다.
  - 시험 계정·시험 기기만 켜서 실기 행렬을 통과한 뒤 전체로 켠다.
  - 문제가 나면 롤백·재빌드 없이 스위치만 끈다.
- 한 작업 = PR 1개(코드 + 시험 + 문서). 실기 FAIL 수정도 같은 PR 이다. 병합 전 스위치 끈 상태로 운영 영향 0 을 확인한다.

### 4-4. 지금 상태 정리 (먼저 할 것)
- main 에 남은 #610·#611(회귀 코드)을 **되돌리는 PR 1개** → 병합 → Promote(Owner 지시) → main = 운영(`fca61b5` 동작).
- 작업 폴더의 흰 화면 수정(`fix/entry-ssot-pr1-wait-layer`)은 병합하지 않는다. 내용(같은 층 대기)은 4-1 진입 대기 층에 흡수한다.

### 4-5. 구조 한계 (별도 결정)
- OS 화면을 레거시 수준(약 1초)으로 하려면 앱 첫 화면을 로컬로 두어야 한다(Option A).
