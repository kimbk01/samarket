   - 반영 후: 데이터가 이미 와 있다. 그래서 게이트가 셸과 무거운 채팅방 본문(목록 그림 약 160ms + 본문 약 260ms)을 **한 번에** 붙인다. 셸의 움직임은 「두 프레임 뒤」에 시작하는데, 무거운 첫 그림이 끝난 뒤로 밀린다. 그 결과 OS 화면이 걷히는 시점(본문 그림 + 약 0.38초)에 아직 움직이는 중이다.
   - 영상 근거: 흰 띠는 움직임 360ms 중 마지막 100~150ms만 보인다. 즉 걷힘 0.2초 남짓 전에 시작했다. 본문 그림 로그 시각(x_icon2 4,041ms → 걷힘 4,417ms)과 맞는다.
   - 셸이 붙은 시각과 움직임 시작 시각을 직접 찍은 기록은 없다 → 3번의 「프레임 밀림」은 **NOT_PROVEN**(정황 근거만). 1·2번은 코드로 확인했다.
- 결론: 미리 받기가 결함을 만든 것이 아니다. 「시작 목적지에도 진입 움직임을 하고, OS 화면은 움직임을 기다리지 않는다」는 원래 결함이 미리 받기로 시점이 바뀌면서 드러났다. 시점만 맞추는 수정(늦추기·지연)은 다시 터진다.

### 10-4. 수정안 (한 규칙으로 묶음)
규칙: **OS 화면이 떠 있는 동안 붙은 시작 목적지는 진입 움직임 없이 제자리에 그린다.** 움직임은 사용자가 본 「이전 화면」이 있을 때만 의미가 있기 때문이다.
1. 채팅방 셸: 첫 마운트 때 `isInitialDestinationVisualReady()` 가 false(OS 화면 유지 중)면 분할 화면·축소 모션과 같은 분기로 처리한다. 움직임 없음, 목록 복사본 정리, 진입 완료 표시는 즉시.
2. 메인 화면 이동(`useRouteTransitionKindRef`): OS 화면 유지 중에 일어난 경로 변경(복원 `router.replace`)은 `none`.
3. 계약 보강(재발 방지): 움직임을 가진 셸은 움직이는 동안 `data-entry-motion="running"` 을 단다. `isLaunchDestinationPaintPending` 은 이것이 보이면 걷지 않는다. 1·2로 시작 때 움직임이 없으니 평소 지연은 0이다. 나중에 누가 새 움직임을 넣어도 OS 화면이 움직임 중간에 걷히지 않는다. 기존 8초 상한은 그대로 둔다.
4. 시험: 셸(OS 화면 유지 중 마운트 → 움직임 없음 · 유지 아님 → 움직임 있음) · 경로 종류(시작 복원 → none) · 해제 조건(`running` 이 있으면 pending).
5. 실기(승인 필요): Samsung 알림 2 + 복원 2 + 메인 탭 복원 1, Xiaomi 알림 1 = 6회(약 1,170건). 판정은 녹화 20fps 왼쪽 띠 흰 프레임 0 · 탭→걷힘 시간 유지.
- 바뀌는 파일: `components/community-messenger/room/MessengerRoomSwipeBackShell.tsx` · `components/route-transition/useRouteTransitionDirection.ts` · `lib/startup/launch-destination-paint.ts`(+ 시험). 웹만. 통화 코드 무관.
- 영향: 목록 탭 진입·뒤로 스와이프·분할 화면은 OS 화면이 이미 걷힌 뒤라 그대로다. iOS·웹은 같은 코드라 같이 적용된다(실기 NOT_PROVEN).
