## 3. 결함 (확정 · 심각도 순)

판정 표기: **FAIL** = 코드로 재현 경로 확정 · **잠재** = 코드 결함이나 운영 데이터상 아직 발생 0건 · 화면 문구는 `lib/i18n/catalog/*` 원문.

### L1 · FAIL · 활동 제한·정지 회원에게 엉뚱한 오류 문구
- 서버: 제한 회원은 `assertCommunityWriteAllowed` → 403 `{ error: "community_restricted", end_at, messageKo }` (`lib/community/community-write-restriction.ts:83-93`). 정지 계정은 `validateActiveSession` 403.
- 화면: 댓글·답글 작성은 `res.status === 403` 이면 무조건 「차단 관계에서는 댓글을 작성할 수 없습니다.」 (`hooks/use-philife-post-comments.ts:106-107`).
- 수정: `community_restricted` 가 `COMMUNITY_COMMENT_ERROR_KEYS`(`lib/community/community-api-error-text.ts:74-88`)에 없어 「처리하지 못했습니다. 잠시 후 다시 시도해 주세요.」.
- 저장소 전체에서 `community_restricted` 를 읽는 화면 코드 0곳. 서버 응답의 `messageKo`(한국어 문장)는 i18n 규정 위반이고 영어 사용자에게 쓸 수 없다.
- 영향: 제재받은 회원이 원인(제한·해제일)을 알 수 없고, 상대를 차단한 적 없는데 차단 문구를 본다.

### L2 · FAIL · 사용자가 쓴 글자가 「삭제된 댓글」로 판정됨
- `CommunityCommentItem.tsx:94-101` 는 `is_removed` 외에 **댓글 내용이 화면 문구 「댓글이 삭제 되었습니다.」 또는 하드코딩 4문장과 같으면** 삭제로 본다.
- 재현: 「댓글이 삭제 되었습니다」라고 댓글을 쓰면 회색 삭제 표시가 되고 수정·삭제·신고·차단·좋아요·답글이 모두 사라진다. 본인도 지울 수 없다(⋮ 에 「링크 복사」만).
- 코드 안 한국어 문자열 4개(`"댓글이 삭제 되엇습니다"` 오타 포함)는 i18n SSOT 신규 금지 항목과 같은 모양이다.

### L3 · FAIL · 삭제 직후 화면 ≠ 새로고침 화면
- 삭제 성공 시 화면은 `content` 를 삭제 문구로 바꾸기만 한다(`use-philife-post-comments.ts:355-363`). `is_removed` 를 세우지 않는다.
- 결과: ① 답글 없는 댓글도 「삭제되었습니다」 줄로 남는다(새로고침하면 사라짐, 서버는 답글 없는 삭제 댓글을 내리지 않음 `comment-tombstones.ts:1-3`) ② 작성자 이름이 그대로 보인다(새로고침 후 빈 이름) ③ 관리자가 지운 경우 ⋮ 에 「차단」이 남는다(`canBlockAuthor` 가 `is_removed` 만 봄, `:109-110`).

### L4 · FAIL · 「댓글 N」 숫자에 삭제 자리 포함
- 제목 숫자 = 트리 노드 전체 수(`CommunityCommentSection.tsx:20-30,96`). 삭제·숨김 자리(tombstone)도 센다.
- 피드 카드·목록 숫자 = DB `comment_count`(보이는 댓글만, 트리거). 같은 글에서 목록 「댓글 3」, 상세 「댓글 4」가 된다(답글이 달린 댓글을 지운 경우).

### L5 · FAIL(잠재) · 관리자 처리만 해도 「· 수정」 표시
- 「수정됨」 판정 = `updated_at - created_at > 2초` (`queries.ts:613-647`).
- 관리자 콘솔 PATCH 는 `updated_at` 을 바꾼다(`app/api/admin/community/engine/comments/[commentId]/route.ts:72-78`). 신고 결정 RPC 도 `updated_at = now()` (운영 정의 확인).
- 재현: 관리자가 숨김 → 복구하면 작성자가 한 글자도 안 고쳤는데 「· 수정」. 운영 해당 0건(관리자 처리 이력 0).
- 원인 구조: 「본문 수정 시각」을 담는 칸이 없고 범용 `updated_at` 을 빌려 씀.

### L6 · 잠재 · 댓글 좋아요 수 동시성 (CM-P3-04 미반영)
- `toggleCommentLikeServer` 는 `like_count` 를 읽고 +1/-1 해서 쓴다(`comment-mutations.server.ts:66-103`). 운영 `community_comment_likes` 에 트리거 없음(확인).
- 두 사람이 동시에 누르면 한 건이 수에서 사라진다. 요청은 「토글」이라 재시도하면 반대로 바뀐다(멱등 아님).
- 운영: 좋아요 3건, 수 불일치 0건.

### L7 · FAIL · 좋아요 실패 안내
- 차단 외 실패(삭제된 댓글 `comment_not_likeable`, 저장 실패)는 숫자만 되돌리고 아무 말 없음(`use-philife-post-comments.ts:240-252`).
- 차단 실패 문구는 **글 공감 버튼 아래**에 뜬다(`CommunityDetail.tsx:549-552`). 댓글이 화면 아래쪽이면 보이지 않는다.

### L8 · FAIL · 댓글 링크·알림이 댓글로 가지 않음
- 「링크 복사」는 `현재주소#comment-<id>` 를 복사한다(`CommunityCommentItem.tsx:156-166`). 저장소 어디에도 이 해시를 읽어 스크롤하는 코드가 없다(`location.hash` 검색 0건). 답글은 기본 접힘이라 대상이 화면에 없다(`:87`).
- 복사 성공·실패 안내가 없다(실패는 무시 `:162-164`). `window.location.origin` 기준이라 공유 주소 단일 정의(`buildCommunityPostSharePath`)와 다르다.
- 댓글·답글 알림 `link_url` = 글 주소뿐(`community-social-inapp-notify.ts:65,98`). `comment_id` 는 `meta` 에만 있어 탭하면 글 맨 위.

### L9 · 부분 · 신고 사유 선택 없음
- 신고 창 = 빈 입력칸 하나(설명·예시 없음, `CommunityDetail.tsx:615-657`). 서버가 입력 글자에서 사유 코드를 추정한다(`inferReportReasonCode`, `app/api/community/reports/route.ts:191-192`) → 관리자 분류가 추정값.
- 신고 뒤에도 신고자 화면에 그 댓글이 그대로 보인다(레거시 6개 앱도 숨김 근거 없음 → 결함 아님, 참고).
- 제목이 글은 「게시글 신고」, 댓글은 「신고」로 짝이 맞지 않는다.

### L10 · 부분 · 차단 시 다른 사람 답글까지 사라짐
- `filterCommentRowsExcludingBlockedRelations`(`lib/social/user-block-ssot.ts:132-167`)는 조상 중 차단 회원이 있으면 그 아래 **모든** 답글을 뺀다. 제3자가 단 답글도 안 보인다.
- 차단한 사람 댓글이 있던 자리 표시도 없어 대화 흐름이 끊긴다. 레거시 비교는 §5.

### L11 · 없음 · 댓글 고정(찝)·글 작성자 관리 권한
- `community_comments` 운영 칸에 고정 관련 칸 없음(15칸 확인). 계약(CM·CM-R)에도 없음.
- 글 작성자가 자기 글의 댓글을 숨기거나 고정할 수 없다. 「작성자」 배지 없음. 글 단위 「댓글 막기」 없음(`CommunityCommentSection` 의 `locked` 는 호출처가 넘기지 않아 항상 열림, `CommunityDetail.tsx:579-607`).
- 계약에 없으므로 **Owner 결정 필요**(§6 권장안).

### L12 · FAIL · 목록 조회 실패가 「첫 댓글을 남겨 보세요」로 보임
- `listCommunityPostComments` 는 DB 오류·예외를 모두 `[]` 로 바꾼다(`queries.ts:568-575,650-652`). GET 은 200 빈 목록 → 화면은 빈 상태 문구. 재시도 버튼도 안 나온다.
- 같은 함수는 칸 조합 12개를 차례로 시도한다(`:536-566`). 운영 칸은 모두 있어 첫 시도로 끝나지만, 오류가 나면 최대 12회 조회 후 빈 목록이다.

### L13 · FAIL · 글자 수 상한을 화면이 모름
- 상한은 운영 설정 `max_comment_length`(서버 `comments/route.ts:169-172`). 입력칸·답글·수정칸에 `maxLength`·남은 글자 표시 없음 → 다 쓰고 「게시」해야 실패를 안다.

## 6. 설계안 — 라운지 댓글 SSOT

### 6.1 원칙
1. **상태 하나, 표시 하나.** 댓글 상태는 서버가 판정해 `display_state` 하나로 내린다. 화면은 글자를 비교해 상태를 추측하지 않는다(L2 근본).
2. **화면 = 새로고침 결과.** 작성·수정·삭제·좋아요 뒤 화면은 서버가 돌려준 행으로만 바꾼다(L3·L4).
3. **오류는 코드 → 문구.** 403 을 한 문구로 뭉치지 않는다. 모든 오류 코드는 `COMMUNITY_COMMENT_ERROR_KEYS` 한 곳(L1·L7).
4. **메뉴·버튼은 앱 공용 부품.** 행 메뉴 = `DibayActionSheet`(모임과 같음), 확인 = `dibayConfirm`, 안내 = `DibayToast`(L18).

### 6.2 표시 상태 (서버 단일 판정)

| `display_state` | 조건(DB) | 내용 | 이름·사진 | 행 버튼 | 답글 |
|---|---|---|---|---|---|
| `visible` | status=active, 숨김·삭제 아님 | 본문 | 표시 | 좋아요·답글·⋮ | 가능(깊이 3까지) |
| `deleted_by_author` | status=deleted, `moderated_by` 없음 | 「작성자가 삭제한 댓글입니다」 | 숨김 | 없음(⋮ 도 없음) | 불가 |
| `removed_by_admin` | status=hidden 또는 (deleted, `moderated_by` 있음) | 「운영정책에 따라 숨겨진 댓글입니다」 | 숨김 | 없음 | 불가 |
| `blocked_author` | 보는 사람과 작성자 차단 관계 | 「차단한 사용자의 댓글입니다」(§6.6 결정에 따름) | 숨김 | 없음 | 불가 |

- 자리 표시는 **살아 있는 답글이 있을 때만** 남긴다(지금 규칙 유지). 답글 없는 삭제 댓글은 목록에서 빠진다 — 삭제 직후 화면도 같은 규칙으로 바로 뺀다.
- 「댓글 N」 = `visible` 수만. DB `comment_count` 와 같은 정의(L4).

### 6.3 데이터 변경 (운영 DB 적용 — Owner 승인 필요)
