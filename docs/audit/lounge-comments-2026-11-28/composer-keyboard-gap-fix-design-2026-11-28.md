## 2. 원인 (16:41 PHT, 앱 WebView 원격 검사로 직접 측정)

| 측정값 | 값 |
|---|---|
| 키보드 열림 표시 `html[data-kb-open]` | `true` |
| 하단 탭 | 아래로 100px 이동해 숨겨짐 (자리는 남음) |
| 본문 스크롤 영역 `main.main-hub-scroll-body` 하단 여백 | **92px** = 하단 탭 여백 76 + 16 (`MAIN_SCROLL_PADDING_WITH_BOTTOM_NAV_CLASS`) |
| 상세 화면 하단 여백 | 바깥 틀 `pb-[max(1rem,safe-bottom)]` 16 + 글 영역 `pb-6` 24 = **40px** |
| 스크롤 위치 | 1752 = 최대값(2357 − 605) — 더 내려갈 수 없음 |
| 카드 끝 ~ 화면(키보드) 위 끝 | 554 → 686 = **132px** = 92 + 40 |

- 하단 탭 숨김은 「보이기만 숨기고 여백은 그대로」가 공용 계약입니다(`lib/layout/bottom-nav-keyboard-hide.ts`). 스크롤할 때 화면이 들썩이지 않게 하려는 목적입니다.
- 입력칸이 내용의 맨 끝에 있어서, 스크롤을 끝까지 내려도 이 여백(132px)이 키보드 위에 남습니다.
- 모임 화면에서도 같은 원인의 결함이 있었습니다(2026-11-12 Samsung). 그때는 공용 계약을 그대로 두고 **그 화면에서만** 같은 크기만큼 보정했습니다(`MoimStickyFooter`의 `MOIM_STICKY_FOOTER_KB_OFFSET_CLASS`). 이번 수정도 같은 방식을 따릅니다.

### iPhone (확인 안 함 — 코드로 아는 것만)
- iPhone 앱은 키보드가 화면을 줄이지 않고 **위에 덮습니다**. 공용 측정값 `keyboardOcclusionInset`이 iPhone에서는 키보드가 가리는 높이, Android에서는 0입니다(`form-keyboard-platform-adapter`).
- 지금 코드에는 키보드가 가리는 만큼 아래 공간을 더해 주는 장치가 입력칸에 없습니다. 그래서 iPhone 앱에서는 입력칸이 키보드 밑에 가려질 **수 있습니다**. 실제로 그런지는 확인하지 못했습니다(시뮬레이터 앱 로그인 필요).
- 시뮬레이터 Safari에서 본 빈 공간은 앱 껍데기가 아니어서 이 원인과 같은지 모릅니다. 이 수정의 대상이 아닙니다.

## 4. 영향 범위

| 화면·경로 | 영향 |
|---|---|
| 라운지 글 상세 (`/philife/[id]`, `/community/posts/[id]` — 둘 다 `CommunityDetail`) | 키보드가 열린 동안에만 하단 여백이 접힙니다. 댓글 입력칸·답글·댓글 수정 칸 모두 해당합니다. 수정 칸은 목록 중간에 있어서 여백이 접혀도 가려지지 않습니다. |
| 다른 모든 화면 | 바꾸지 않습니다 (상세 틀에만 붙는 규칙). |
| 키보드를 닫을 때 | 여백이 원래대로 돌아오며 내용 길이만 늘어납니다. 스크롤 위치는 그대로라 화면이 튀지 않습니다. |
| 공감·메뉴 시트·신고 시트 | 시트 안 입력은 상세 틀 밖(겹친 층)입니다. F3의 가림 높이 여백은 상세 뒤쪽에만 생기고 시트 배치에는 영향이 없습니다 — 실기에서 신고 시트 입력으로 확인합니다. |

### 깨질 수 있는 것과 확인 방법
- 셸 여백 식이 바뀌면 F1 값이 어긋납니다 → F4 시험이 잡습니다.
- iPhone에서 F3 값이 과하면 입력칸 아래에 빈 공간이 생길 수 있습니다. 또 키보드를 닫을 때 맨 아래에 있었다면 내용이 줄어 화면이 한 번 위로 튈 수 있습니다(독립 재감사 지적, 코드로는 가능성만) → iPhone 앱 실기로 확인합니다(로그인 필요).
- 시트(신고 등) 입력 중에도 뒤 상세 화면 여백이 접힙니다. 시트 뒤라 보이지 않지만 맨 아래에 있었다면 닫은 뒤 스크롤 위치가 조금 올라가 있을 수 있습니다(재감사 지적).
