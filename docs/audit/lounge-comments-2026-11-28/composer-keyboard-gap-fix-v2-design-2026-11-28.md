# 라운지 댓글 입력칸 — 키보드 위 빈 띠 재수정안 (2026-11-28 · Owner 「승인」 후 구현: `components/community/post-detail/community-detail-keyboard-gap.tsx`)

## 1. 어떤 결함인가

라운지 글 상세에서 댓글 입력칸을 누르면 입력칸과 키보드 사이에 **빈 띠가 생긴다**.
- 크기: 화면 단위 132px(Xiaomi 기기 약 176px).
- 증거: Xiaomi 16:35·18:04 PHT 캡처, 운영 eac581f·2758a95.
- 입력칸은 「게시물 끝 칸, 글을 쓸 때 키보드 바로 위」라는 Owner 지시와 다르다.

## 2. 왜 생기는가 (18:04 PHT 실측 · Xiaomi 앱 WebView 원격 측정)

| 단계 | 실측 |
|---|---|
| 키보드 열림 전 | 화면 높이 1006. 본문 스크롤 위치 958 = 끝. 입력칸 아래쪽 854, 하단 탭 시작 931. |
| 키보드 열림 | 화면이 686으로 줄어든다. 하단 탭은 아래로 숨는다(931 → 화면 밖). |
| 남는 것 | 본문 스크롤 영역(`main-hub-scroll-body`)의 아래 여백 **92px**(하단 탭 76 + 16)과 상세 화면 아래 여백 **40px**(바깥 16 + 글 영역 24). |
| 결과 | 스크롤을 끝까지 내려도(1279 중 1278) 이 132px이 입력칸 아래에 남아 키보드 위 빈 띠가 된다. |

- 하단 탭은 키보드가 열리면 **보이기만 숨기고 여백은 둔다**. 앱 공용 규칙이다(`lib/layout/bottom-nav-keyboard-hide.ts`).
- 입력칸이 내용의 맨 끝이라, 남은 여백이 그대로 키보드 위에 보인다.
- 글 중간의 입력칸(로그인·글쓰기 등 다른 화면)은 아래에 내용이 더 있어서 이 빈 띠가 드러나지 않는다.

## 3. 지난 수정(#701)이 실패한 이유 (18:09 PHT 같은 동작을 기기에 넣어 시간 순서로 측정)

#701은 「키보드 열림 표시(`html[data-kb-open]`)」가 켜져 있는 동안 CSS로 여백 132px을 접었다.

| 시각(ms) | 화면 높이 | 스크롤 위치 / 끝 | 입력칸 아래쪽 | 일 |
|---|---|---|---|---|
| 2975 | 1006 | 826 / 826 | 986 | 키보드가 닫혀 화면이 커짐. 표시가 아직 켜져 있어 여백이 접힌 채 → 스크롤 끝이 826으로 줄어 위치가 826으로 잘림 |
| 3055 | 1006 | 826 / 958 | 986 | 0.08초 뒤 표시가 꺼지며 여백이 돌아옴. 스크롤 위치는 826 그대로 → 입력칸이 하단 탭(931~) 뒤에 숨음 |

- 키보드 열림 표시는 화면 크기가 바뀐 뒤 두 프레임 늦게 바뀐다. 그 사이에 브라우저가 스크롤 위치를 접힌 내용 기준으로 잘라 버린다.
- #701은 이 순서를 확인하지 않았다. 열림 상태만 기기에서 확인하고 배포했다.

## 4. 재수정안 (라운지 글 상세만 · 공용 규칙은 그대로)

여백을 접는 것은 같다. 다른 점은 **되돌리는 시점과 방법**이다.

| # | 내용 |
|---|---|
| A | 여백 접기·되돌리기를 CSS 표시가 아니라 상세 화면 부품이 직접 한다. 바깥 틀에 −(하단 탭 여백 + 16px), 바깥·글 영역 아래 여백 0. 대상은 `CommunityDetail.tsx` + 새 부품 1개. |
| B | **접기**: 키보드가 열리면(공용 측정값 `keyboardOpen`) 접는다. 열릴 때는 시점이 늦어도 공용 포커스 보정이 입력칸을 키보드 위로 올리므로 문제가 없다. |
| C | **되돌리기 ①**: 화면이 100px 넘게 커지는 크기 변경 이벤트 안에서 **그 자리에서** 바로 되돌린다(Android: 키보드가 닫힘). 크기 변경 이벤트는 화면을 그리기 전에 실행되므로, 잘린 화면이 한 번도 그려지지 않는다. |
| D | **되돌리기 ②**: 공용 측정값이 「닫힘」이 되면 되돌린다. 화면 크기가 변하지 않는 iPhone, 또는 ①이 없었을 때를 위한 것이다. |
| E | **끝 유지 규칙**: 되돌리기 직전에 스크롤이 끝(1px 안)에 있었으면, 되돌린 뒤에도 끝에 둔다. 끝이 아니었으면 위치를 건드리지 않는다. 결과는 키보드를 열기 전과 같은 자리다. |
| F | iPhone(키보드가 화면을 덮음): 열린 동안 키보드가 가리는 높이만큼 아래 칸을 둔다(공용 측정값 `keyboardOcclusionInset`, Android는 0). 되돌릴 때 함께 없앤다. |
| G | 시험 두 가지. ① 접는 값이 셸 여백 상수와 같은지 대조한다(구조 확인). ② 동작 시험: 「끝에 있을 때 화면이 커지면 → 되돌린 뒤 끝 유지」 「끝이 아니면 위치 그대로」 「100px 이하 변화는 무시」. |

### 기기에서 미리 확인한 결과 (18:10 PHT · Xiaomi · 운영 2758a95 화면에 같은 동작을 임시로 넣어 측정 · 배포 없음)

| 상태 | 화면 높이 | 스크롤 위치 / 끝 | 입력칸 아래쪽 | 하단 탭 시작 | 판정 |
|---|---|---|---|---|---|
| 키보드 열림 | 686 | 1134 / 1147 | 678 (화면 끝 686, 간격 8 = 공용 포커스 간격) | 숨김 | 빈 띠 없음 — 정상 |
| 키보드 닫힘 | 1006 | 958 / 958 | 854 | 931 | 입력칸이 탭 위 원래 자리 — 정상 |
| 되돌리는 시점 | 크기 변경 이벤트 후 2ms, 같은 작업 안 | 826 → 958 | 986 → 854 | — | 잘린 화면이 그려지기 전에 바로잡음 |

캡처: 같은 시각 q6(열림)·q7(닫힘). 임시로 넣은 동작은 앱을 종료해 지웠다.

## 5. 영향과 남는 위험

| 항목 | 내용 |
|---|---|
| 바뀌는 화면 | 라운지 글 상세(`/philife/[id]`, `/community/posts/[id]` — 둘 다 `CommunityDetail`)만. |
| 다른 화면 | 바뀌지 않는다. 공용 하단 탭 규칙·셸 여백·공용 키보드 보정은 그대로. |
| 회전·화면 분할 | 키보드가 열린 채 화면이 커지면 ①이 먼저 되돌린다. 그동안 빈 띠가 다시 보이고, 다음에 키보드를 열 때 다시 접는다. 결함이 아니라 원래 상태로 돌아가는 것이다. |
| 시트 입력(신고 등) | 시트에 입력해도 뒤 상세 화면이 접혔다가 끝 유지 규칙으로 되돌아온다. 시트 뒤라 보이지 않는다. |
| iPhone | **확인 못 함.** 화면 크기가 변하지 않아 ②와 F로만 동작한다. 시뮬레이터 앱 로그인이 필요하다. |
| Samsung | **확인 못 함.** 기기에 DIBAY가 지워져 있다. |

## 6. 진행 순서 (승인 시)

1. 코드 → 검사(타입 2종·관련 시험·전체 시험) → 독립 재감사 → PR(병합 지시 대기).
2. 병합 후 Xiaomi에서 확인한다.
   - 끝에서 열기·닫기
   - 끝이 아닌 곳에서 열기·닫기
   - 답글 입력칸, 댓글 수정 칸
   - 신고 시트 입력
   - 「게시」 첫 탭
3. 앱 실행 2회가 필요하다(Owner 허용).

## 8. 구현 후 독립 재감사 반영 (같은 PR)

- 막는 결함 없음(코드 판단 — 기기 확인 아님).
- 보완 2건:
  - 닫힘 판정을 「직전 크기 변경 대비」가 아니라 「접을 때 화면 높이 대비」로 바꿨다. 크기 변경이 여러 번에 나뉘어 와도 놓치지 않는다.
  - 스크롤 영역을 되돌릴 때 찾는다. 열 때 짧던 글이 열린 동안 길어져도 끝 유지가 동작한다.
  - 두 경우 모두 동작 시험을 추가했다.
- 남는 위험(원래 동작으로 돌아가는 것, 새 결함 아님):
  - 키보드가 열린 채 화면이 100px 넘게 커지면 빈 띠가 다시 보이고, 다음에 키보드를 열 때 다시 접는다. 예: 회전, 화면 분할 확대, 이모지 판에서 글자 판으로 전환.
  - 끝에서 132px 안쪽에 있을 때 다른 입력(신고 시트 등)으로 키보드를 열었다 닫으면, 끝으로 최대 132px 이동할 수 있다.
- iPhone 시험은 구조 확인 수준이다. 흉내 낸 스크롤이 자동으로 끝을 자른다.
