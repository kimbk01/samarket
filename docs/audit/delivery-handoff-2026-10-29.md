4. **배너·광고·상위 노출**: 어드민 등록(지면·업종·순서·개수·기간) ↔ 앱. 업종 상단 배너 업종 대상 지정 부재(모든 업종에 같은 배너), CATEGORY_TOP 한도 초과 8건, 3장 우→좌 슬라이드.
5. **노출 기준**: 비로그인(로그인 유도) · 주소 없는 회원(배너) · 주소 있는 회원(배달 가능 실매장 + 샘플 전부) — 홈·업종·검색·배너·상세.
6. **샘플**: 2차 업종마다 3곳 · 실제 운영 형태(메뉴·옵션·이미지·영업시간·선반 데이터 소스에 해당하는 운영 데이터: 주문 실적·평점/리뷰·배달비 할인·추천·기획 프로모션) · 반경 10,000km(반경 방식 vs LGU 선택 방식 확인) · 「샘플 매장」 배지 · 최종 주문 차단 · 샘플 광고.
7. **부록 A 전체 범위**: 고객(15개 프로세스)·오너(10개)·관리자(12개) 재감사, 기존 테스트 매장 전수 조사·숨김, 이미지 정확성·권한, 광고 샘플·통계 분리, 기존 기능 보호.
8. **UI·UX·성능**: 빈 화면·CTA SSOT, 슬라이드·애니메이션, 배달 누수·누락·병목, 이미지 저장·API 누수·저장 공간.

## DIBAY 배달 서비스 전체 재감사 및 정식 샘플 운영 체계 구축 지시

### 0. 작업 목적 및 절대 원칙

DIBAY 배달 서비스는 이전 작업에서 고객 웹, 매장 오너, 통합 관리자 기능을 구현하고 완료 보고한 상태다.

이번 작업은 기존 기능을 처음부터 재개발하는 것이 아니다.

**현재 구현 상태를 코드·운영 DB·실제 화면·관리자 기능과 대조하여 재감사하고, 서비스 정식 오픈 전 샘플 매장 운영 체계를 안정적으로 구축하기 위한 작업이다.**

작업 순서는 반드시 다음과 같다.

**① 전체 감사 → ② 원인 및 구조 분석 → ③ 설계안 제출 → ④ Owner 승인 → ⑤ 구현 → ⑥ 검증 → ⑦ 실기기 시나리오 승인 → ⑧ 실기기 검증 → ⑨ 최종 보고**

Owner 승인 이전에는 코드 수정, DB 변경, 데이터 숨김, 샘플 생성, 배포, 실기기 테스트를 진행하지 않는다.

추측이나 임시 처리, 기존 기능에 조건문을 덧붙이는 땜빵 방식은 금지한다.

기존 SSOT와 정상 작동 기능을 최대한 보존하고, 구조적 문제가 확인되면 최초 원인을 기준으로 설계한다.

### 2. 기존 테스트 매장 및 메뉴 전수 조사

현재 운영 DB에 존재하는 매장과 매장별 메뉴는 정식 오픈 전 테스트용으로 사용된 데이터다.

다만 실제 DB를 확인하기 전까지 특정 행을 임의로 테스트 데이터라고 단정하지 않는다.

다음 항목을 조사한다.

- 전체 매장 수 및 업종별 수
- 매장 ID·이름·오너·상태
- 매장별 메뉴 및 옵션 수
- 테스트 데이터 식별 근거
- 실제 주문·결제·정산·상품권·광고 등과의 연결
- 현재 고객 노출 여부
- 관리자 숨김 기능과 상태 SSOT
- 숨김 처리 시 다른 기능에 미치는 영향

설계 목표는 **기존 테스트 매장과 메뉴를 관리자 목록에는 유지하면서 고객에게는 노출되지 않도록 하는 것**이다.

단, 숨김은 승인 이후 실행한다.

삭제하거나 운영 데이터를 임의 초기화하지 않는다.

관리자에서 숨김 대상과 사유, 처리 결과를 확인할 수 있어야 한다.

### 3. 정식 샘플 매장 체계 설계

#### 핵심 요구

DIBAY 서비스 오픈 초기에는 실제 입점 매장이 없을 수 있다.

따라서 고객이 앱을 실행하면 주소와 관계없이 업종별 샘플 매장과 메뉴를 확인할 수 있어야 한다.

샘플은 단순한 임시 카드나 하드코딩 목록이 아니다.

**실제 매장·메뉴 데이터 모델을 기반으로 하되, 샘플이라는 별도 운영 성격이 명확한 관리형 콘텐츠여야 한다.**

#### 샘플 매장 구성

현재 운영 DB 및 관리자에 등록된 업종 분류를 먼저 확인한다.

확인된 각 업종마다 다음을 구성한다.

- 업종당 샘플 매장 2개
- 매장마다 업종에 적합한 대표 이미지
- 매장별 실제 메뉴 구성에 준하는 샘플 메뉴
- 메뉴별 이름·설명·가격·이미지
- 필요한 옵션 및 옵션 가격
- 메뉴 카테고리
- 품절·숨김 등 기존 메뉴 상태 지원

메뉴 수는 일괄적으로 임의 지정하지 말고 업종별 실제 매장 화면을 충분히 체험할 수 있는 수준으로 설계한다.

업종별 샘플 매장명, 메뉴명, 가격, 옵션, 이미지 구성표를 승인 전에 제출한다.

기존 업종 체계를 임의 변경하거나 새로운 업종을 만들어서는 안 된다.

#### 고객 화면 표시

샘플 매장은 일반 매장 목록에서 확인할 수 있어야 한다.

단, 실제 매장과 명확히 구분한다.

표시 예시:

- `샘플 매장`
- `서비스 체험용`
- `실제 주문 불가`

샘플 매장 카드를 선택하면 해당 샘플 매장의 상세 화면으로 이동한다.

상세 화면에서는 실제 매장과 같은 수준으로 메뉴, 옵션, 이미지, 가격, 화면 구성을 확인할 수 있어야 한다.

샘플이라는 이유로 빈 메뉴나 단순 안내 페이지만 보여주는 방식은 허용하지 않는다.

실제 주문·결제·정산이 발생하지 않도록 해야 한다.

장바구니·주문서 체험 범위는 기존 구조와 안전성을 검토한 후 설계안에서 별도로 명시하고 Owner 승인을 받는다.

### 4. 회원 주소와 무관한 샘플 노출

기존 실제 매장 노출에는 회원 주소, 배달 가능 지역, 거리 등의 정책이 적용되어 있다.

이 정책은 유지한다.

단, 샘플 매장은 회원 주소와 관계없이 모든 회원이 확인할 수 있어야 한다.

검토 대상:

1. 배달 홈 기본 목록
2. 업종별 목록
3. 검색 결과
4. 매장 상세 직접 접근
5. 로그인·비로그인 상태
6. 주소 미등록 회원
7. 주소 변경 이후
8. 페이지네이션·정렬·캐시
9. 샘플과 실제 매장이 함께 존재하는 경우

**실제 매장에 적용되는 배달 가능 지역 정책을 깨뜨리지 않고 샘플만 전국·전 지역 체험 노출이 가능하도록 설계한다.**

샘플 매장에 가짜 좌표를 넣거나 배달 반경을 무한대로 조작하는 방식은 금지한다.

기존 매장 목록 SSOT를 확인하여 샘플 노출 정책을 어디에서 처리해야 하는지 근거를 제시한다.

### 5. 관리자에서 샘플 매장·메뉴 완전 제어

관리자 매장 목록에서 다음 유형을 구분할 수 있어야 한다.

| 유형 | 의미 |
|---|---|
| 실제 매장 | 정식 운영 매장 |
| 샘플 매장 | 고객 체험용 매장 |
| 기존 테스트 매장 | 과거 개발·검증 데이터 |

유형과 별개로 노출 상태도 확인되어야 한다.

관리자에서 필요한 제어 기능:

- 샘플 매장 검색 및 필터
- 업종별 샘플 조회
- 샘플 매장 추가·수정
- 매장 이미지 수정
- 메뉴·옵션 수정
- 메뉴 가격 변경
- 매장 및 메뉴 노출·숨김
- 샘플 전체 노출 제어
- 상태 변경 이력 확인

유형과 노출 상태는 서로 다른 개념이다.

기존 DB에 관련 필드나 정책이 존재하는지 먼저 확인하고 재사용 가능성을 분석한다.

새 컬럼이나 테이블이 필요하면 그 이유와 기존 구조에 미치는 영향을 승인안에 명시한다.

관리자 변경이 고객 화면에 반영되는 경로와 캐시 무효화 정책도 함께 검증한다.

### 6. 업종별 이미지 정확성

샘플 이미지는 클라우드 작업 환경에서 실제 업종과 메뉴를 확인하면서 구성한다.

필수 기준:

1. 업종에 맞는 매장 대표 이미지
2. 메뉴 이름과 일치하는 메뉴 이미지
3. 이미지 없는 카드 방지
4. 모바일·태블릿 비율과 크롭 확인
5. 실제 서비스와 일치하는 이미지 표시 방식

## DIBAY 배달 — 임시·땜빵·중복 구조 검증 및 설계안 재판정

현재 제출한 2026-10-28 배달 전체 재감사 및 샘플 운영 설계안에 대한 추가 지시다.

**현재 설계안은 승인하지 않는다.**

기존 기능을 다시 개발하라는 지시가 아니다. 이번 감사에서 발견한 문제와 제안한 해결책이 실제로 근본적인 해결인지, 기존 구조에 조건을 덧붙이는 임시·땜빵 방식인지 정확히 판정하라.

### 1. 검증 대상

다음 항목을 우선 검증한다.

- 샘플 매장 구분 `store_kind`가 기존 매장 유형·노출 SSOT와 충돌하는지
- `owner_user_id` NULL 허용이 기존 매장·오너·권한·알림·캐시에 영향을 주는지
- Discovery RPC 2개와 검색·홈 피드의 샘플 분기가 중복 정책을 만드는지
- UI·API·DB 주문 차단의 책임이 명확한지, 서로 다른 판정이 발생할 수 있는지
- 관리자 샘플 메뉴 편집이 기존 오너 메뉴 저장 로직을 복제하는지
- 샘플 광고 구분과 성과 집계가 기존 광고 SSOT를 훼손하는지
- 샘플 전체 노출 스위치와 매장별 숨김 상태의 우선순위가 일관적인지
- H-02~H-12 수정안이 증상만 가리는지, 실제 최초 원인을 제거하는지
- 관리자 HOME 저장의 CAS·트랜잭션·권한이 단일 구조인지
- 기존 고객·오너·관리자에서 완료 판정한 기능이 현재도 정상인지

### 2. 판정 기준

각 항목을 다음 중 하나로 분류한다.

- **정상:** 기존 SSOT를 준수하고 구조적으로 문제가 없음
- **근본 수정 필요:** 원인이 확인됐으며 현재 구조의 수정이 필요함
- **땜빵:** 기존 원인을 남긴 채 조건문·재시도·별도 조회·화면 강제 갱신 등으로 증상만 우회함
- **중복 구조:** 동일 업무 규칙이나 저장 책임이 여러 경로에 분산됨
- **NOT_PROVEN:** 실제 근거가 부족해 판정할 수 없음

조건문이 추가된다는 이유만으로 땜빵이라고 단정하지 말고, 실제 책임과 SSOT를 분석해 판정하라.

### 3. 검증 방법

각 문제는 다음 순서로 확인한다.

1. 현재 실제 코드 및 DB 구조
2. 기존 레거시와 완료된 HARD LOCK 계약
3. 최초 오류 발생 지점
4. 현재 수정안이 그 원인을 제거하는지
5. 다른 화면·API·RPC에 같은 책임이 중복되는지
6. 기존 정상 기능에 미치는 영향
7. 최소한의 안정적인 근본 해결 방법

기존 감사 결과를 그대로 PASS로 재사용하지 않는다. 이번에 직접 확인하지 못한 화면과 프로세스는 NOT_PROVEN으로 유지한다.

특히 고객·오너·관리자 3개 영역의 전체 프로세스 감사가 실제로 완료됐는지도 다시 판정한다.
