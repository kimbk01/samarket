## R4. 부동산 임대 글의 가격 조건

### 지금 동작 (사실)

| 항목 | 내용 | 근거 |

| 조건 적용 | 운영 `trade_list_page` 가 `posts.price` 만 본다. 조건 밖이거나 **price 가 비어 있으면** 글을 숨기지 않고 「조건과 다른 글」 줄 뒤로 민다 | `20271103160000_trade_sold_visible_window.sql:153-159`, 운영 함수 정의에 `WHEN b.price IS NULL THEN 1` 이 있음을 확인 [DB] |

### Owner 결정 R4-1 — 부동산에서 가격 조건이 무엇을 뜻하나

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A (권장)** | 부동산에서는 거래 유형을 먼저 고르게 한다. 「판매」면 가격 칸 = 매매가. 「임대」면 가격 칸 = **월세**(최소·최대). 유형을 안 골랐으면 가격 칸을 숨긴다 | 고객이 보는 숫자와 조건이 같다. 칸 하나로 끝난다 | 보증금으로는 찾을 수 없다 |
| B | 임대일 때 월세 칸 + 보증금 칸 두 줄 | 조건이 정확하다 | 필터 시트가 길어진다. 다른 주제와 모양이 다르다 |
| C | 지금처럼 두되, 부동산에서는 가격 칸을 숨긴다 | 작업이 가장 작다 | 부동산은 가격으로 찾을 수 없다 |

### 안 A 구현 범위 (승인 시)

1. **SQL (운영 DB 적용 = 별도 승인)**
   - `trade_list_page` 에 새 인자 `price_field` 를 받는다(`price` 기본값 | `meta_monthly`).
   - `meta_monthly` 이면 `(b.meta->>'monthly')::numeric` 으로 같은 규칙(밖이면 「조건과 다른 글」)을 적용한다.
   - 숫자가 아닌 값은 비어 있는 값과 같게 처리한다(`monthly` 는 지금 글자로 저장된다).
   - 인덱스는 만들지 않는다. 판정은 이미 가져온 후보 행 안에서만 한다.
2. **서버**: `home-posts-route-core.ts`·카테고리 목록 경로가 부동산 + `deal_type=임대` 조건일 때만 `price_field=meta_monthly` 를 보낸다. 판단은 서버가 하고, 화면 값은 쓰지 않는다.
3. **화면**: `MarketFilterSheet`
   - 부동산 주제이고 거래 유형을 안 골랐으면 가격 칸을 숨기고, 「거래 유형을 먼저 고르세요」를 보여 준다(i18n 키 신규, ko·en).
   - 임대를 골랐으면 칸 이름을 「월세」로 바꾼다.
4. **영향받는 곳**
   - 홈·카테고리·찾기 목록의 같은 함수 호출
   - 조건 칩 문구(`priceChipLabel`)
   - 주소창 `priceMin/priceMax` 이어받기
   - 다른 주제는 인자가 기본값이라 동작이 같다.
5. **검증**
   - SQL 계약 테스트(임대·판매·빈값·글자값)
   - 화면 테스트
   - 운영 적용 뒤 부동산 실기 확인. 단, 운영에 보이는 부동산 글이 0건이라 **시험 글이 필요하다(R4-2)**.

### Owner 결정 R4-2 — 실기 확인용 부동산 글

운영에 보이는 부동산 글이 없어 화면 확인을 할 수 없다. 둘 중 하나를 정해 주셔야 한다.
- (권장) Owner 계정으로 임대 1건·판매 1건을 직접 올리고, 확인 뒤 삭제한다.
- 작업자가 시험 계정으로 올린다. 이 경우 운영 데이터를 쓰는 일이라 따로 승인이 필요하다.

## P3. 판매완료·거래 평가 알림

### 지금 동작 (사실)

| 사건 | 지금 받는 사람에게 가는 것 | 근거 |
|---|---|---|
| 판매자가 판매완료를 누름 | 그 글의 **모든 거래 채팅방에 시스템 메시지**(DB 직접 삽입)가 들어가고, 채팅방 안 읽음 수만 오른다. **푸시·벨 알림은 없다** | `owner-status/route.ts:237` → `insert-seller-listing-change-system-messages.ts:96-200` (푸시 발송 호출 없음) |
| 한쪽이 거래 평가를 남김 | 상대에게 아무것도 가지 않는다. 양쪽이 다 남기거나 7일이 지나면 공개된다 | `trade-rating.ts:323` |
| 평가가 공개됨 | 알림 없음 | 같은 파일 |
| 관심(찜)한 사람 | 판매완료를 알 방법이 목록·상세를 다시 보는 것뿐 | — |

운영 사실 [DB, 최근 60일]:
- `notification_events` 의 `trade_status` 41건(마지막 11-09), `trade_message` 52건 → **거래 알림 종류와 발송 경로는 이미 운영 중이다**(가격 제안 등).
- 판매완료 2건, 공개된 거래 평가 1건 → 새 알림을 켜도 양은 매우 적다.

### 재사용할 기존 장치 (새 장치를 만들지 않음)

- 알림 종류 `trade_status`(`notification-event-registry.ts:199`)
  - 설정 키 `trade`, 거래 채널 `dibay_trade_v1`, 벨 포함, 앱 아이콘 숫자 제외
  - 중복 방지 `domain_entity_recipient`, 7일 보관
- 발송 함수 `appendUserNotification`(가격 제안이 쓰는 경로, `lib/offers/price-offers.server.ts:526`).
  - 알림 설정 fail-closed 잠금(`dibay-notification-preference-fail-closed-hard-lock.md`)과 전역 알림 SSOT 잠금을 그대로 따른다. **잠금 문서는 바꾸지 않는다.**

### 구현 범위 (승인 시 · 웹만 · DB 변경 없음)

1. **판매완료 (①)**
   - `applySellerMarkSold` 의 판매완료 성공 뒤, 이미 읽은 채팅방 목록의 상대 user_id 마다 `appendUserNotification` 을 부른다.
   - 중복 키: `trade_sold:{postId}:{userId}`.
   - 판매자 본인·차단 관계는 제외한다.
   - 응답을 늦추지 않도록 응답 뒤(`after`)에 보낸다.
2. **평가 도착 (③)**: `trade-rating.ts` 평가 저장 성공 직후, 상대가 아직 평가하지 않았을 때만 보낸다. 중복 키는 `trade_rating:{roomId}:{revieweeId}`.
3. **i18n**: 서버 문구는 받는 사람 언어로 만든다(`docs/i18n-ssot.md` — 서버 문구는 요청 언어). 키를 신규 등록하고, 한국어 문자열을 코드에 쓰지 않는다.
4. **영향받는 곳**
   - 벨 목록·안 읽음 수(`trade_status` 는 벨 포함)
   - 앱 아이콘 숫자는 제외 규칙이라 그대로
   - 알림 설정 「거래」를 끈 회원에게는 푸시가 나가지 않는다(벨에는 남는다 — 잠금 계약 6번)
   - 알림 누름 → 채팅방 이동(`display_route`)
5. **요청 예산**
   - 판매완료 1건당 쓰기는 상대 수만큼 늘어난다. 운영 기준 60일에 판매완료 2건이라 무시할 수준이다.
   - `owner-status` 경로 예산(`lib/perf/request-budget.ts`)에 증가분을 반영한다.
6. **검증**
   - 단위 테스트(받는 사람 선정·중복 키·차단 제외·설정 끔)
   - 운영 반영 뒤 실기: Android·iPhone 각 1회 — 판매완료 → 상대 기기 푸시·벨 → 누르면 채팅방, 평가 → 상대 기기 알림
   - 시험 거래 1건이 필요하다(P3-3).

### Owner 결정 P3-3 — 실기 시험 거래

판매완료와 평가는 되돌릴 수 없다(계약: 판매완료 되돌리기 없음). 그래서 실기 시험에는 **실제로 판매완료 처리할 시험 글 1건**과 대화 상대 계정 1개가 필요하다. 사용할 계정 2개를 정해 주셔야 한다.
