## 0. 결론 (먼저)

1. **선행 계획 C4(「API·RSC 는 검증만, 만료면 401 → 클라 재시도」)는 그대로 구현하면 안 된다.** `/api` 를 직접 부르는 클라이언트 파일이 **578개**인데 401 후 갱신·재시도하는 곳은 **2곳**(프로필·앱 부팅, `lib/auth/api-auth-recovery.ts` 사용처)뿐이다 (C). 서버가 만료 토큰에 401 을 주면 복귀 직후 수백 곳이 실패한다 → 계획 수정.
2. **운영에서 증명된 인증 Code First Break 는 없다.** 최근 3일 auth 로그(24h 창 3개): 갱신 충돌 `refresh_token_already_used` **0건**, `refresh_token_not_found` 11·1·0건(최초 원인 NP) (O).
3. **증명된 구조 사실 2개가 사용자 증가 시 위험이다.**
   - 세션 갱신의 **64~84% 가 서버(Vercel)에서** 일어난다 — 11-05 483/577, 11-06 208/277, 최근 24h 287/459 (O, `referer` 끝 `/` 유무로 브라우저/서버 구분).
   - Supabase 갱신 제한은 **IP 단위 1,800회/시간·순간 30회** (D, `guides/auth/rate-limits`). 서버 갱신은 공유 Vercel IP 로 나가므로 사용자 수에 비례해 IP 한도에 먼저 닿는다. 한 사용자 복귀에 서버 갱신 시도 9~10건이 1초 안에 나간 기록 있음 (O, 11-07 16:29:55 UTC).
4. 따라서 Phase 3 는 「401 전환」이 아니라 **① 서버의 낭비 갱신 제거(동작 불변) → ② 복귀 시 클라이언트가 먼저 갱신(서버 갱신 비중 축소) → ③ 필요 시 IP 전달** 순서로 바꾼다. C6 는 이득이 작아 **보류** 권장.

### 3-2. 복귀 시 클라이언트 먼저 갱신 + 복귀 조정자 (C5 수정판)

- **제외(통화 규정):** 수신 통화 확인(`GlobalCommunityMessengerIncomingCall` 복귀 GET)·통화 청크 경계 — 통화 단독 계획·실기 행렬 필요.
