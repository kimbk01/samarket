## 3. 재설계안

### 원칙
- **하나의 알림 = 하나의 판정 입력 = 하나의 결과.**
- 표면마다 따로 판정하던 것을 공통 판정 1개로 모은다.
- 덧대기·클라이언트 우회는 하지 않는다.

### D-1 공통 판정 함수 (P-2 · P-3 · P-4 · P-8 · P-13)
`resolveNotificationClassification(event)` 1개를 둔다.
- **입력:** 원본 이벤트(type · category · room_id · kind = legacyMeta.kind → 최상위 kind)
- **출력:**
  - 소속: A 회원 / 메신저(B 또는 메신저 전용) / 오너 C / 관리자 / 숨김
  - 알림센터 분류
  - 푸시 설정 키
  - 소리 키
- **사용처** (전부 같은 결과를 쓴다):
  - 숫자(A)·모두 읽음·앱 아이콘
  - 목록 변환
  - 탭 숫자·탭 목록·행 라벨
  - 오너 판정
  - 푸시 설정 게이트·소리
- **메신저 소속 종류:** 친구 요청·수락·거절, 그룹 초대, 선물 4종(이동 경로가 모두 메신저 → 증거).
- **방 있는 부재중:** B 만, 알림센터 제외(최신 계약).
- **데이터:** 최상위 kind 888행을 `legacyMeta` 로 옮기는 백필 마이그레이션(운영 데이터 변경 → Owner 별도 승인). 이후 SQL 140000 의 fallback 을 제거하는 정방향 마이그레이션으로 판정 위치를 1곳으로 만든다.
- **교체:** `3e597af8f` 의 오너 특례 코드를 이 함수로 바꾼다.

### D-2 푸시 안전 게이트를 종류 기준으로 (P-1)
- `notification-delivery-safety-gate.ts`: `order_status` 라도 주문 종류일 때만 주문 존재를 검사한다.
- 포인트 충전·매장 포인트·배달 광고는 각자의 대상(충전 요청·광고 요청) 존재 여부로 판정한다.
- 필수 알림이 「목적지 삭제」로 막히지 않게 한다.

### D-3 메신저 처리 시 알림 정리 (P-2)
친구 요청 수락·거절·취소, 선물 수락·거절 시 같은 대상의 알림 이벤트를 읽음 처리한다. 메신저 쪽 처리 API 에 연결한다.

### D-4 상태 알림 읽음 범위 (P-5)
- `offer_accepted` 등 상태 알림 탭은 상태 이벤트만 읽음 처리한다.
- 채팅 메시지 이벤트·거래 타깃은 방 읽음(`mark_read`) 경로에서만 읽음 처리한다.

### D-5 다른 기기 동기화 근본 수정 (P-6, N-05 제거)
- Realtime 구독을 `notification_events` 의 UPDATE 까지 넓힌다(본인 행, 읽음·삭제 필드). 받으면 배지 권위를 다시 받는다.
- N-05 의 화면 복귀 재조회·숫자 비교 재조회·`224fefdd0` 가드를 제거한다.
- **사전 확인:** replica identity·RLS 가 필요한지 확인한다. 운영 DB 설정 변경이 필요하면 별도 승인.

### D-6 오너 알림음 (P-7)
- 푸시 소리 키를 D-1 결과(kind 기준)로 쓴다.
- 인앱 소리 게이트는 수신 역할이 오너면 오너 설정만 본다.

### D-7 오늘 잘못·미완 교체 (P-9 · P-10)
- 모임 알림 키 = 요청·멤버십 행 id + 상태 시각(결정적 키).
- 전체 삭제 = SQL 한 번으로 일괄 소프트 삭제(RPC, 운영 DB 함수 추가 → 승인).
