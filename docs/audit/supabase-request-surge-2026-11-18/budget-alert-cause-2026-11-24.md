## 2. 실제 초과 3건 — 원인

### 2-1. 접속 상태 — 구조 변경 뒤 예산을 갱신하지 않음 (총 호출은 크게 줄었음)

| 사실 | 근거 |
|---|---|
| 11-19 「D1 2단계」(`ec17686e5`)에서 12초 하트비트를 없앴다. 이후 상태가 바뀔 때만 POST 하고, 바뀔 때마다 받는 쪽에 1건 발행(`realtime/v1/api/broadcast`)한다 | `app/api/community-messenger/presence/route.ts` (`isTransition` → `after()` 발행) |
| 요청 수가 크게 줄었다. 11-15~22 7일 54,086건(하루 약 7.7천) → 이번 창 186~307건/일 | 11-22 문서 §2 · Vercel |
| 1회당 구성(11-23~24): 상태 저장 1.00 + 발행 0.53 + 인증 키 0.04 + 계수기 0.02 | Vercel 대상 경로별 |
| 예산 1.1 은 하트비트 시절 측정값이다(11-17~18). 당시 요청 대부분은 발행 없는 하트비트였다 | `lib/perf/request-budget.ts` 머리말 |

- 판정: **호출 증가 결함이 아니다.** 하트비트가 빠져 남은 요청의 다수가 발행을 동반하게 됐고, 그래서 1회당 평균만 올랐다. 하루 총 호출은 약 8천 → 약 300 이다.
- 할 일: 예산 값 갱신(1.1 → 실측 기준). **예산 올리기 = Owner 승인 필요**(SSOT §4-1).

### 2-2. 동네 피드 — 2026-11-20 대책이 다른 `locations` 조회를 캐시했음

| 사실 | 근거 |
|---|---|
| 11-20 설계는 `locations` 0.98/요청을 「동네 키 → 동네 id 변환」으로 보고, 그 조회(전체 26행)를 공유 캐시로 옮겼다 | `neighborhood-feed-budget-design-2026-11-20.md` §1·§4, `lib/neighborhood/philife-feed-shared-config-cache.server.ts` |
| 그런데 반영 뒤에도 `locations` 는 **1.00/요청**이다 | Vercel 대상 경로별(11-23~24: `locations` 208 / 요청 208) |
| 실제로 요청마다 도는 것은 **글 목록의 지역 이름 조회**다: `loadLocationCitiesByIds` → `from("locations").select(…).in("id", ids)` (페이지마다 1번, 캐시 없음) | `lib/neighborhood/queries.ts:600` · `lib/addresses/community-public-region-label.ts:88` |
| 로그인 사용자 비율도 올랐다. 숨김·좋아요 상태 0.64 → 0.89, 관계 0.55 → 0.77 (11-19 대비) | Vercel 대상 경로별 |

- 판정:
  - **대책이 대상을 잘못 잡았다(작업자 측 11-20 설계 오류).** 지역 이름 조회 1.0 이 그대로 남았다.
  - 예산 5.0 은 「예상 4.2」를 근거로 내린 값이다. 실제로는 그 근거가 성립하지 않았다.
- 할 일(코드만): 지역 이름 조회가 이미 공유 캐시된 `locations` 전체 행(26행)을 쓰게 한다 → 약 −1.0/요청(6.45 → 약 5.45, 경보선 6.0 아래). 예산 5.0 아래로 내려가려면 로그인 사용자 본문 조회(숨김·상태·관계)를 합쳐야 하고, 이는 별도 단계다.
