## 3. 지금 읽음 1번 = Supabase 20 (운영 34건 내역)

| 묶음 | 1번당 | 무엇 |

## 4. 목표 구조 (레거시 메신저와 같은 형태)

**쓰기 시점에 사용자별 「안 읽은 방 상태」를 유지**하고, 배지·허브·목록은 이것만 읽는다.

| 단계 | 내용 | 효과(산술) |
|---|---|---|
| 2-a DB | `member_unread_rooms(user_id, room_id, bucket, unread_count, domain_identity_key, order_id, store_id, role)` — 지금 로더가 계산하는 **방별 행 그대로**. 트리거: 참가자 `unread_count`·`left_at`, 방 `deleted_at`·`last_message` 변경 시 그 행만 갱신(같은 트랜잭션, HTTP 추가 0). 메시지 1건 = 받는 사람마다 행 1개 갱신(전송 RPC 가 이미 하는 안 읽음 증가와 같은 트랜잭션) | DB 쓰기 소폭 증가, 요청 수 증가 0 |
| 2-b 그림자 | 배지 계산 시 표본 10%: 로더 결과(방 ID·개수·식별 키) ↔ 표 1번 읽기 비교 | — |
| 2-c 전환 | 배지 계산(badge-count·읽음 ACK·푸시 배지)이 참가자·방·주문·매장 4~5회 대신 **표 1회** — 응답 모양·ID 목록·A 계산 **그대로** | badge-count 7~9 → ~4 · 읽음 20 → ~16 · 푸시 1건 ~8 → ~4 |
| 2-d 사본 정리 | 허브 배지·홈 동기 사본이 같은 표를 읽게 → 읽음·보내기 뒤 **즉시 재생성 불필요**(항상 최신) | 읽음 ~16 → ~6 · 보내기 1건 −8~10 |

2-d 는 보내기 2단계·통화 규정과 겹치는 부분(푸시 배지)이 있어 그 부분만 통화 영향 분석 후 별도 PR.
