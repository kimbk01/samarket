## 0. 내 잘못 먼저 (이전 보고 정정)
1. 이전 보고에 「Realtime 은 25초 심장박동으로 끊김을 잡으므로 10초 폴링의 이득이 작다」고 썼다. **과장이었다.** `realtime-js` 는 응답 없는 심장박동을 **다음 박동(25초 뒤)** 에 끊김으로 본다 → 조용한 끊김 감지는 최대 약 50초. 25초 폴링이 안전한 근거는 심장박동이 아니라 「25초 + 요청 왕복 ≈ 26초 < 울림 30초」(아래 §3)다.
2. 이전 보고의 「숨김 창 = 정기 HTTP 0」은 Realtime 이 끊긴 숨김 창까지 0 으로 만든다 → 그 상태에서 걸려 온 통화를 다시 볼 때까지 못 받는다. **이 계획에서는 바꿨다**: 숨김 + Realtime 정상만 0, 숨김 + 끊김은 10초.
3. 이전 보고의 F7-3(정리→목록 순서, 유령 벨)은 **실기 증거가 없다** → 규정 2(증거 없이 통화 경로 변경 금지)·4(한 번에 한 원인)에 따라 이번 변경에서 **뺀다**. 별도 항목으로 기록만.

## 2. 바꾸는 것 (파일·함수)

**파일 1개**: `lib/community-messenger/call-v4/call-v4-incoming-discovery.ts`
- `resolveCallV4IncomingDiscoveryPollDelayMs` 에 탭 상태 인자 추가:

| 상태 | 지금 | 변경 |
|---|---|---|
| 울리는 중 | 2초 | **불변** |
| 실패 백오프·429 | 4→30초·Retry-After | **불변** |
| 채팅 화면 밖 | 60초(HTTP 없음) | **불변** |
| 보임 + Realtime 정상(SUBSCRIBED 5초↑) | 10초 | **25초** |
| 보임 + 끊김·연결 중 | 2초 | **불변** |
| 숨김 + Realtime 정상 | 10초 | **정기 조회 없음** (울림 신호 → 즉시 1회 조회 · 다시 보이면 즉시 재조회 — 둘 다 기존 코드) |
| 숨김 + 끊김·연결 중 | 2초 | **10초** |

- 서버·DB·네이티브·푸시 변경 없음. `service.ts`·`/incoming` route·VoIP/FCM 발송 **무변경**.

## 3. 안전 근거 (30초 울림 안에 반드시 찾는가)
- 보임 + 정상: Realtime 0.5초. 조용히 끊겨도 25초 폴링 + 왕복 ≈ 26초 < 30초. (지금 10초 → 11초. **최악의 경우 수신 표시가 최대 15초 늦어질 수 있다** — 조용한 끊김 0건/14일인 드문 경우.)
- 숨김 + 정상: Realtime 신호 → 즉시 조회(기존, 숨김에서도 동작 — 웹 숨김 신호 4건 실측). 조용히 끊긴 숨김 창은 **다시 볼 때까지 못 받는다** — V3 와 같은 수준. 맥은 PushKit 이 없어 대체 경로 없음. **Owner 수용 필요 위험.**
- 숨김 + 끊김: 10초 → 30초 안에 찾음(지금 2초 → 더 늦지만 상한 안).
