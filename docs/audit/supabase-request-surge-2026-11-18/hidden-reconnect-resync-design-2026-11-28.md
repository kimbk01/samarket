## 2. 원인 (코드로 확인)

1. 실시간 채널이 다시 붙으면 「재동기화 묶음」(`messenger-realtime-resync.ts`, 계약 R2)이 등록된 받는 쪽을 1번씩 부른다.
2. 받는 쪽은 5곳이다. 모두 서버에서 다시 받는다. 여기에 다시 열기 판정(R5)의 기다림이 이 묶음을 듣는다(받는 쪽은 아님).

   | 받는 쪽 | 다시 받는 것 |
   |---|---|
   | 열린 방 (`global-messenger-room-bundle-channel.ts`) | 새 메시지 `after=` |
   | 메신저 홈 (`community-messenger-home-realtime-channels.ts`) | 목록 확인 |
   | 알림 (`useSupabaseNotificationsRealtime.ts` → `NotificationsBadgeRealtimeBridge.tsx`) | 배지 수·고객센터 숫자 |
   | 친구 요청 (`use-global-friend-request-feed.ts`) | 요청 목록 |
   | 그룹방 읽은 수 (`use-group-message-read-counts.ts`) | 읽은 수 |

3. 이 묶음에는 **「화면이 보이는가」 조건이 없다.** 그래서 숨김 중 재연결이 반복되면, 보는 사람이 없어도 매번 5곳을 다시 받는다.
4. 「다시 열기 조회」(계약 R5)는 이미 보임으로 바뀔 때만 동작한다. 그러나 재연결 묶음은 그와 별개라 숨김 중에도 돈다.

- **구조 결함이다.** 「끊긴 동안 놓친 것을 따라잡는」 일은 **사람이 볼 때 한 번**이면 된다. 지금은 숨김 중 재연결 횟수만큼 반복된다.

## 3. 바꾸는 것

**재동기화 묶음이 실행될 때 앱이 숨겨져 있으면 실행하지 않고 「밀린 묶음」으로 남긴다. 보임이 되면 1번 실행하고, 그때 다시 열기 조회(R5)는 따로 나가지 않는다.**

> 독립 검토(2026-11-28)가 첫 안의 오류 4가지를 찾아 고쳤다.
> - 다시 열기 판정이 밀린 묶음을 보지 않아 2번 조회되던 문제
> - 보임 신호가 없던 문제
> - 숨김 판정이 흐리던 문제
> - 감독을 껐을 때 2번 조회되던 문제

| # | 파일 | 바꾸는 것 |
|---|---|---|
| 1 | 새 `lib/community-messenger/realtime/messenger-app-visibility.ts` | 지금 `resume-resync-gate.ts` 안에 있는 숨김·보임 시계를 이 모듈로 옮긴다(동작 같음). 여기에 **「보이게 됨」 알림**(`onAppBecameVisible`)과 지금 숨김 여부(`appHiddenNow`)를 더한다. 설치는 재동기화 묶음이 스스로 한다(누가 먼저 떠도 설치됨). `resume-resync-gate.ts` 는 이 모듈을 쓴다. 지금 두 파일이 서로를 import 하는 순환을 피하려고 따로 둔다 |
| 2 | `messenger-realtime-resync.ts` | 실행 순간 `appHiddenNow()` 이면 실행하지 않고 「밀림」으로 둔다. 묶음 대기 중(`isPending`)은 계속 참이다. 숨김 중 재연결이 여러 번 와도 하나로 합친다. **보이게 됨 알림을 받으면 다시 숨김 여부를 묻지 않고, 다음 차례(0ms 뒤)에 1번 실행한다.** 다음 차례로 미루는 이유: 같은 보임 순간의 다시 열기 판정(R5)이 먼저 「밀린 묶음이 있음」을 보고 기다리게 하기 위해서다. 밖에서 부르는 `flushDeferredMessengerResync()` 도 둔다(아래 4) |
| 3 | `resume-resync-gate.ts` `resumeRefetchPlan` | 입력에 「밀린 묶음 있음」을 더한다. 있으면 연결·감독 상태와 무관하게 **`wait_resync`**. 묶음이 실행되면 그 결과로 끝나고 조회는 0번이다. 감독을 껐을 때도 같은 규칙이 적용된다(첫 안은 감독을 끄면 매번 2번 조회였다). `shouldRefetchOnAppResume`(배지·친구 요청의 사전 판정)도 밀린 묶음이 있으면 「예약으로 넘김」이 되게 한다 |
| 4 | 다시 열기 예약 `scheduleResumeRefetch`(배지·친구 요청이 함께 씀) | 기다리기 시작한 뒤 `flushDeferredMessengerResync()` 를 부른다(구현: 받는 곳마다가 아니라 예약 한 곳에서). 보임 알림을 놓쳐도(네이티브 WebView 등) 다시 열기 신호(visibilitychange·focus·appStateChange) 어느 것이든 밀린 묶음을 실행시킨다. **안전망.** 9초 기다림이 끝났는데 아직 밀려 있으면 그때도 실행시킨다 |
| 5 | 숨김 판정 | 숨김 = `visibilityState === "hidden"` 또는 「네이티브 비활성 뒤 아직 활성 신호 없음」. 보임 = visibilitychange visible 또는 appStateChange active 중 **먼저 오는 것**. 이때 다시 판정하지 않는다(WebView 가 visibilitychange 를 늦게 보내도 막히지 않게) |
| 6 | 기록 | 밀린 횟수·보임 때 실행 횟수를 앱 기록(`realtime.connection`)에 `resync_deferred.hidden`·`resync_flushed.visible` 로 남긴다. 효과 측정용 |
| 7 | 계약 문서 `docs/messenger-realtime-policy.md` | R2 줄에 「숨김 중 묶음은 보일 때 1번」을, R5 줄에 「밀린 묶음이 있으면 기다림」을 같은 PR 에서 적는다(지금 R5 줄의 「감독 꺼짐·25초 이상 숨김이면 바로 조회」 문구와 충돌하므로 고친다) |

**보임 1번의 흐름 (목표)**
1. 숨김 중: 재연결 N번 → 밀린 묶음 1개, 조회 0번
2. 보임 순간:
   - 다시 열기 판정(R5)이 밀린 묶음을 보고 「기다림」
   - 다음 차례에 묶음 1번 실행 → 받는 쪽 5곳이 각 1번 다시 받는다
   - R5 기다림은 그 묶음으로 끝나 조회 0번
3. 합계: 받는 쪽마다 1번

### 바뀌지 않는 것

- **실시간 사건 자체는 숨김 중에도 그대로 받는다.** 다음은 지금과 같다.
  - 새 메시지 반영
  - 알림 소리
  - 앱 안 배너
  - 친구 요청 팝업 적재
- 처음 가입(첫 SUBSCRIBED) 조회는 그대로다.
- 다시 열기 조회(R5) 규칙도 그대로다.
- 실시간 소켓·채널 가입·재시도·감독 규칙은 바꾸지 않는다.

## 7. 검증

**코드**
- 숨김 중 재연결 3번 → 실행 0번, 보임 → 1번
- 보임 중 재연결 → 지금처럼 바로 1번
- 네이티브 활성 신호만 와도 실행(visibilitychange 없음)
- **밀린 묶음 + 모든 채널 연결 + 25초 이상 숨김 → 다시 열기 시 받는 쪽마다 정확히 1번**(첫 안의 2번 조회 재현 시험)
- 감독 꺼짐 + 밀린 묶음 → 받는 쪽마다 1번
- 보임 알림을 놓치고 focus 만 와도 실행
- 9초 기다림 끝에 아직 밀려 있으면 실행
- 전체 시험·타입검사

**운영 (반영 뒤)**
- 같은 기기 UA 로 「실시간 연결 새로 맺음」 대 「친구 요청·배지 조회」를 10분 단위로 대조한다. 숨김 중 연결은 늘어도 조회는 늘지 않아야 한다.
- 앱 기록 `resync_deferred.hidden`·`resync_flushed.visible` 수를 본다.

**실기 (Android 시험폰 1대, 앱 실행 3회 이내)**
- 앱을 백그라운드에 두고 1분 → 그동안 친구 요청·배지 조회 0번
- 다시 열기 → 각 1번
- 숨김 중 받은 메시지·통화 기록 줄이 보이는지

## 8. 이번에 고치지 않는 것 (따로 보고)

1. **iPhone 앱은 보이는 중에도 끊김이 많다**(2일 128번). 숨김과 무관한 별도 원인이다. 별도 조사가 필요하다.
2. **오늘 운영 배포가 28번**이었다(여러 작업 합계). 배포마다 설정 공유 캐시가 비워져 처음부터 다시 읽는다(설정 읽기 612번의 대부분). 「한 작업 = 배포 1번」 규칙을 지켜야 줄어든다.
3. **Mac 기기 1대(사무실 IP)**가 라운지 글 상세를 하루 1,170번 열었다. 친구 요청도 176번 조회했다. 사람 사용인지 다른 작업 세션의 시험인지 확인하지 못했다.
4. 숨김 중 소켓이 끊기는 것 자체(연결 확인 늦음)는 막지 않는다. 막으려면 소켓 설정을 바꿔야 하는데, 웹 통화 수신도 같은 소켓을 쓰므로 통화 변경 규정 대상이다. 이번 변경 뒤 남는 비용을 보고 판단한다.
