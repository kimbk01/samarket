## 1. 확인된 결함

### D1. 감시 계수기가 호출의 절반 안팎을 잃는다 — #553 뒤에도
같은 24시간(11-22 01:00 ~ 11-23 01:00 UTC · #553 병합 11-22 01:21 UTC 뒤)의 비교:

| 라우트 | 계수기 호출 / Vercel 호출 | 저장 비율 |
|---|---|---|
| 관리자 종 | 465 / 701 | 66% |
| 접속 상태 | 221 / 496 | 45% |
| 내 정보 | 206 / 451 | 46% |
| 알림음 | 101 / 285 | 35% |

- 판정: **FAIL.** 감시가 쓰는 숫자가 실제 호출의 34~88% 다. 라우트마다 비율이 달라 1회당 값이 치우친다.
- 원인: **NOT_PROVEN.** #553(전송을 요청 `after()` 에 묶음) 뒤에도 남는 유실의 경로는 아직 확인하지 못했다. 추측으로 적지 않는다.

### D2. 계수기의 「요청 수」 정의가 예산의 기준과 다르다
- 코드 `lib/perf/supabase-call-counter.ts` `record()`: 요청은 그 요청의 **첫 Supabase 호출 때만** 센다(`if (prev === 0) routeBucket.requests += 1`).
  - Supabase 를 부르지 않고 끝난 요청(서버 메모리 캐시 적중 등)은 분모에 들어가지 않는다.
- 예산 값은 Vercel 「모든 요청」을 분모로 정했다(`lib/perf/request-budget.ts` 머리말).
- 실측:
  - 캐시가 없는 관리자 종은 호출·요청 저장 비율이 같다(66% · 70%).
  - 캐시 경로가 있는 라우트는 요청 비율만 낮다.

| 라우트 | 호출 저장 | 요청 저장 | 계수기 1회당 | Vercel 1회당 | 캐시 경로 (코드) |
|---|---|---|---|---|---|
| 내 정보 | 46% | 24% | 3.75 | 1.95 | `me-profile-get-route-cache` 등 |
| 알림음 | 35% | 28% | 3.16 | 2.46 | `loadNotificationSoundSsotCached` |
| 동네 주제 | 34% | 26% | 2.23 | 1.75 | `Cache-Control s-maxage=20` |
| 사장님 허브 배지 | 88% | 32% | 2.44 | 0.88 | `owner-hub-badge-cache` |

- 판정: **FAIL.** 11-23 경보의 이 4건은 Vercel 기준으로 모두 경보선 아래다. 경보는 감시 정의 때문에 났다.
- NOT_PROVEN: 라우트별 캐시 적중 비율(측정 수단 없음 — 요청·호출 비율의 차이로만 드러남).

### D3. 「요청 1회당 평균」 하나로 판정 → 요청 구성이 바뀌면 개선도 초과로 판정
- **접속 상태**: D1 2단계(`ec17686e5`, 11-19)
  - 코드 `use-community-messenger-presence-runtime.ts` · `presence/route.ts`:
    - 전환 POST(앞화면·백그라운드·복귀·종료)는 상태 저장 1 + 발행 1.
    - 60초 keepalive POST 는 저장 1.
    - GET 은 조회 1.
  - 실측(11-22 09:00 ~ 11-24 08:00 UTC): 요청 498 · 상태 표 호출 1.00/요청 · 발행(`realtime/v1/api/broadcast`) 0.53/요청 → **1.58**.
  - 하트비트 제거 전 7일: 요청 54,086 · 1.04.
  - 하루 총 호출: 약 8,050 → 약 400.
- **관리자 종**: #562(11-22) 받은 알림 요약을 종 요청에 합침
  - 요약은 70초에 1번만 붙는다(`isAdminInboxSummaryDue`).
  - 요약이 붙는 요청은 받은 알림 1 + 발송 상태 1(최고관리자만) 이 더해진다.
  - 1회당: 11-23 4.64(요약 비율 0.46) · 11-24 12~16시 PHT 5.75(요약 비율 0.87).
  - 처리 대기 함수는 두 기간 모두 1.00 으로 같다.
- 판정: 라우트 동작은 설계대로다(결함 아님). **감시가 이를 초과로 판정하는 것이 결함**이다.

### D4. 관리자 API 는 요청마다 인증 확인으로 DB 를 3번 읽는다
- 코드 `requireAdminApiUser` → `validateActiveSession` → `requireAdmin`. 요청마다 다음 3번을 읽는다.
  1. `getCurrentProfile`(profiles 1)
  2. `validateUserSessionRegistryCached`(user_sessions 1 — 캐시 TTL **10초**, 종 폴링 75초라 거의 매번 적중 실패)
  3. `loadPrivilegedAdminMembership`(admin_memberships 1)
- 실측(관리자 종, 11-24 04~08 UTC, 요청 133): profiles 1.00 · user_sessions 0.96 · admin_memberships 0.92.
- 관리자 종 1회 = 인증 3 + 처리 대기 1 + (요약 때) 2. **인증이 절반이다.**
- 적용 범위: `requireAdminApiUser` 를 쓰는 관리자 API 전부.
- 판정: 실제 호출 낭비. 다만 같은 요청 안에서 중복은 없다(이미 1회씩) — 「요청마다 따로 3번」이 결함이다.
