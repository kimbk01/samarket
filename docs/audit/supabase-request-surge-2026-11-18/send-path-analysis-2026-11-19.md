# 메신저 메시지 보내기 1건 = Supabase 63~70건 · 구조 분석 (2026-11-19)

- 상태: **분석만 · 구현 없음.** 메신저·알림 hard-lock + 일부는 **통화 변경 규정**(푸시 발송을 통화 푸시와 공유) → 설계 승인 후 단계별 구현.
- 측정: Vercel `external_api_request` (origin_route = `rooms/[roomId]/messages`) ↔ 같은 시간 GET/POST 수.

## 1. 측정 (운영, 증거)

| 방법 | 값 |
|---|---|
| 보내기 0건인 시간 11곳 → 목록 GET 1회 단가 | **5.1** (4.9~6.3) |
| 보내기 있는 시간 7곳에서 GET 몫을 뺀 보내기 1건 단가 | **63~70** (11-17 00·04, 11-18 00·01·02·07·09 UTC) |
| 11-18 00~03 UTC: 텍스트 보내기 81건(`send_text_message` 81) | 표별 내역 §2 |

레거시 메신저: 보내기 1건 = 저장 1 + 받는 사람 알림 1(서버 큐) 수준. 회원·메시지가 늘면 이 단가가 그대로 곱해진다(메시지 1만 건/일 × 65 = 65만/일).

## 3. 목표 구조 (레거시와 같은 형태)

| # | 바꿀 것 | 1건당 | 규정 |
|---|---|---|---|
| ① | A → **즉시 재생성 대신 「낡음」 표시만**, 다음에 읽을 때 1회 만듦. 배지는 D2 카운터(트리거)가 이미 쓰기 시점에 유지 | ~10 → ~1 | 메신저·알림 hard-lock. 읽는 쪽이 「낡음」 이면 다시 만드는지 화면별 확인 필요(NOT_PROVEN) |

| ③ | C → 보내기 RPC 가 이미 돌려주는 방 종류·받는 사람을 끝까지 넘기고, 받는 사람별 알림 판단 재료(차단·음소거·언어·알림 설정·기기)를 **DB 함수 1번**으로 | ~15+4 → ~2 | 알림 파이프라인(통화 규정 밖) + 푸시 안전 검사·설정 읽기(**통화 규정 안**) |

## 4. 순서 제안

1. **① + ③ 앞쪽(파이프라인·배지 대상 연결)** — 통화 규정 밖. 메신저·알림 hard-lock 승인 후.
2. **② ④ ⑤ + ③ 뒤쪽(푸시 발송)** — 통화 변경 규정 절차: 영향 분석서(발신·수신·취소·부재중·통화 기록 푸시) → Owner 승인 → **통화 단독 PR** → 실기기 통화 행렬 PASS.
3. 각 단계 운영 전후 실측.

## 5. NOT_PROVEN
- 그룹방(받는 사람 여러 명)의 1건 단가 — 측정 표본이 1:1 위주.
- 이미지·스티커·음성 보내기 단가.
- ① 에서 「낡음」 표시 후 각 화면이 다시 만드는지.
