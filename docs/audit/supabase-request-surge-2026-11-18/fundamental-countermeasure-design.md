- Owner 지시: 「근본 대책을 만들어라, 매번 추측이나 대충 임시 땜빵으로 하니.. 매번 수정 하고, 또 터지고 하는 부분이다」

## 0. 작업자 잘못 (먼저 보고)

1. **S-1(PR #464)을 11-08 판정과 충돌하게 구현·병합했다.** 11-08 보완서 §6 은 수신 목록 조회에서 R3(`getUserLiveDirectCallSessionId`)·L1(재정리)을 빼면 상황 4(첫 정리 실패 후 재시도)·5(두 정리 사이 만료)가 달라진다고 판정했다 — 「동등하게 뺄 수 있는 쿼리는 현재 구조에 없다(BLOCKED)」. 나는 그 문서를 읽지 않고 「동작 변화 없음」이라 썼다. #464 는 11-18 12:10 PHT 병합(운영 반영 여부는 확인 안 함 — NOT_PROVEN). **되돌리기 PR #466 준비, 병합은 Owner 결정.**
2. 이 설계 중 작업 폴더에서 `git checkout origin/main -- .` 를 실행해 커밋 안 된 파일을 main 판으로 덮었다. 커밋된 상태로 즉시 복구했고 잃은 내용은 없다(브랜치 `docs/supabase-surge-root-cause-2026-11-18`, HEAD `d40d96d51` 그대로).

## 1. 왜 매번 다시 터지나 (증거)

| # | 원인 | 증거 |
|---|---|---|
| R1 | **요청량 예산이 없다.** 「API 1회당·앱 실행 1회당·켜 둔 기기 1시간당 Supabase 몇 건까지」를 정한 곳이 없다. 새 코드가 호출을 늘려도 막는 장치가 없다 | `package.json` 의 `verify:*`·`check:*` 205개 중 **CI(`ci:static`)에서 라우트의 Supabase 호출 수를 재는 검사 0개**. 비슷한 것은 수동 실행 e2e 2개(`verify:room-bootstrap-snapshot-e2e`·`verify:home-sync-snapshot-e2e` — 스냅샷 RPC 안의 DB 왕복 수만 확인)뿐이다. 홈 매장 피드 1회당 16.6건, 알림 읽음 1회당 19.0건이 아무 검사 없이 운영에 있다 |
| R2 | **감지 수단이 Owner 대시보드뿐이다.** | 11-08(34만 건/일)·11-18(27만 건/일) 모두 Owner 가 대시보드를 보고 지시. 자동 경보 없음 |
| R3 | **설계한 재발 방지 장치를 만들지 않았다.** | 11-08 원 설계 D1 「공용 반복 조회 도구」·D2 `verify:client-polling`·P1~P6 다른 반복 조회 6곳 → 11-08 구현 감사에서 **전부 「미구현」**. 11-18 의 맥 수신 조회는 11-08 원인 A 와 같은 장치(V4 수신 탐색)다 |
| R4 | **서버 쿼리를 줄이는 길은 통화 동등성 때문에 막혀 있다.** | 11-08 보완서 §6 BLOCKED. 대안(같은 사용자 정리를 「N초에 1회」로 묶기)은 「별도 설계」로 남은 채 미착수 |
| R5 | **시험 트래픽과 실사용 트래픽을 구분할 표지가 없다.** 시험이 운영 DB 를 쓰므로(테스트 DB 금지) 시험 반복이 그대로 운영 급증이 된다 | 11-18 증가분의 89% = 시험 기기 2대. 원인을 나누는 데 Vercel UA·IP 를 손으로 맞춰야 했다 |
| R6 | **반복 호출이 화면마다 제각각이다.** 숨김 탭 중지·오류 시 간격 늘리기·횟수 상한이 각 코드에 따로 있거나 없다 | 클라이언트 `setInterval` 73곳(네트워크·새로고침과 같은 파일 39곳) + `setTimeout` 재귀 반복(V4 수신 탐색 10초·presence 12초 등) — 공통 장치 없음 |

→ 건별로 고치면(S4 간격 조정, 모니터링 상한 U1, S-1) 그 건만 줄고, **다음 기능·다음 시험·다음 화면에서 같은 일이 다시 난다.** 근본 대책은 「요청량을 계약으로 정하고, 코드에서 강제하고, 운영에서 자동 감시」하는 것이다.

## 2. 대책 구조 — 요청 예산 계약

```
[K1 예산 SSOT] ──정의──▶ [K2·K3 CI 검사]  : 새 코드가 예산을 넘으면 병합 불가
       │                                    
       └──기준──▶ [K5 운영 자동 감시]       : 운영에서 넘으면 Owner 에게만 알림 (실패 때만)
[K4 공용 반복 스케줄러] [K6 요청 단위 읽기 재사용] : 예산을 지키기 쉽게 하는 구조 장치
[K7 시험 트래픽 표지]                         : 감시 결과에서 시험·실사용 분리
```

### K1. 예산 단일 정의 (SSOT)
- 파일: `docs/request-budget-ssot.md` (사람용) + `lib/perf/request-budget.ts` (검사·감시가 읽는 값).
- 예산 3종
  1. **라우트 예산** — API 1회당 Supabase 호출 상한. 초깃값 = 11-17~18 운영 측정값(`root-cause-design.md` §4-1). **내리기만 가능**(ratchet). 올리려면 Owner 승인.
  2. **표면 예산** — 화면을 켜 둔 기기 1대·1시간 주기 호출 상한(조회 간격 × Supabase 배수 합계). 예: 메신저 화면 = presence(12초) + V4 수신 탐색(10초, S4 승인값) …
  3. **총량 경보선** — 하루 Supabase 요청이 직전 7일 중앙값의 **1.5배**를 넘거나, 한 라우트의 1회당 호출 수가 예산의 **1.2배**를 넘으면 경보.
- 경보선 값은 이 문서 승인으로 정한다.

### K2. CI 검사 — `verify:supabase-call-budget`
- 공용 기록기 `lib/test/supabase-call-recorder.ts`: 가짜 Supabase 클라이언트가 `from(표)·rpc(이름)·auth.*` 호출을 순서대로 기록한다(S-1 테스트·D1 계약 테스트에 쓴 방식의 공용화).
- 라우트 계약 테스트: 호출 상위 12개 라우트(운영 Supabase 호출의 약 80%)에 대해 대표 시나리오 1회 = 호출 수 ≤ 예산.
- **새 라우트 등록 강제**: `app/api/**/route.ts` 목록과 예산 파일을 대조해 예산이 없는 새 라우트가 생기면 실패. 지금 있는 라우트는 기준 목록(baseline)으로 면제하고, 목록은 줄기만 한다 — `check:i18n-quality` 와 같은 방식.
- `ci:static` 에 추가 → `ci-ok` 필수 검사가 되어 예산을 넘는 PR 은 병합되지 않는다.

### K3. CI 검사 — `verify:client-polling` (11-08 D2 복원)
- 클라이언트 파일에서 `setInterval`·재귀 `setTimeout` 반복이 네트워크(`fetch`·`.rpc(`·`.from(`·`router.refresh`)를 부르면 **K4 스케줄러를 통해서만** 허용.
- 지금 있는 반복 39개 파일 이상은 기준 목록으로 면제, 목록은 줄기만 한다(새 반복 추가 = CI 실패).

### K4. 공용 반복 스케줄러 — `lib/runtime/periodic-task.ts` (11-08 D1 복원)
- 모든 주기 호출이 선언으로 등록한다: `id`, 간격, 숨김 탭 정책(`pause` 기본 / `continue` 는 사유 필수), 오류 시 간격 늘리기, 같은 `id` 타이머 1개, 담당 문서.
- 실행 1회마다 기존 U1 모니터링 집계(`cm_monitoring_rollup_hourly`, 5분 묶음 전송)에 `periodic:<id>` 를 센다 → 「기기 1시간당 주기 호출 수」를 운영에서 바로 본다. 새 DB 표 없음.
- **동작 변경 없이 장치만 먼저** 만든다. 기존 반복을 옮기는 일은 도메인별 PR(통화 반복은 통화 변경 규정, S4 승인 간격 그대로).

### K5. 운영 자동 감시 — 하루 1회, 실패 때만 알림
- GitHub Actions 예약 작업 1개(하루 1회, 09:00 PHT `CRON_TZ=Asia/Manila`). Vercel 관측 API 로 지난 24시간을 읽는다:
  - `vercel.external_api_request.count` × `origin_route`·`request_path` (라우트별 Supabase 호출 — 이번 분석에 쓴 지표)
  - `vercel.request.count` × `route`·`client_user_agent`·`client_ip` (보낸 기기)
- K1 경보선을 넘으면 GitHub 이슈 1건(라우트·기기·전일 대비 표)을 만들어 Owner 에게 알린다. 넘지 않으면 아무것도 보내지 않는다(「결과는 실패할 때만」 규정과 같음).
- CI·배포 결과를 기다리거나 반복 확인하는 작업이 아니다. 운영 사용량 감시 1회/일.
- **필요한 설정 변경(Owner 승인)**: GitHub 저장소 비밀값 `VERCEL_TOKEN`(읽기 전용 범위) 1개 추가.

### K6. 요청 단위 읽기 재사용 — `lib/server/request-scope-read-cache.ts`
- 같은 API 요청 안에서 같은 읽기를 여러 번 하는 곳(측정: 홈 매장 피드 `admin_settings` 1회당 2.68번, 메신저 첫 화면 `bootstrap_snapshots` 3.55번, 알림 읽음 `notification_events` 3.0번·`rooms` 2.71번)을 요청당 1번으로 줄이는 장치.
- 요청 범위(AsyncLocalStorage)에서만 기억하고 요청이 끝나면 버린다. 사용자 사이·요청 사이 공유 없음.
- **동등성 규칙**: 같은 요청 안에서 그 표에 쓰기가 있으면 그 표의 기억은 즉시 버린다. 통화 코드에는 적용하지 않는다(R4, 11-08 §6).
- 장치만 먼저 만든다. 라우트 적용은 도메인별 PR.

### K7. 시험 트래픽 표지
- 시험 계정 목록을 SSOT 로 둔다: `lib/perf/test-traffic-accounts.ts`(zxzx11·q테스트1 등 user id).
- K5 보고서가 시험 계정·사무실 시험 기기 UA 를 「시험」으로 따로 집계한다 → 다음 급증 때 원인 분리를 손으로 하지 않는다.
- AGENTS.md 「실기기 반복 실행 시험 상한」(PR #465)과 짝.

## 3. 단계 (승인 단위)

| 단계 | 내용 | 운영 동작 변화 | 승인 필요 |
|---|---|---|---|

| **3. 구조 장치** | K4 공용 반복 스케줄러 · K6 요청 단위 읽기 재사용 (장치만, 적용 0곳) | 없음 | 이 설계 승인 |

## 5. 완료 기준
- 1단계: 감시 작업이 이 문서 §1 표의 값(라우트별 1회당 호출·기기별 요청)을 같은 숫자로 재현한다 — 11-17~18 구간을 돌려 `root-cause-design.md` §4-1 과 대조.

- 3단계: 스케줄러 숨김 탭 정지·오류 간격·타이머 1개 보장, 읽기 재사용의 쓰기 후 무효화가 단위 테스트로 증명된다.
