## 2. 2-d 수정안 (승인 요청 범위)

### 2-d-1 — 종 알림 3번 → 1번 (결함 B)
- ③ 행을 먼저 읽는다. **행 수가 상한보다 적으면**(=전부 읽음) ①·②를 그 행에서 메모리로 계산한다.
  - ① = `aggregateOrphanMissedCallFacts`(기존 함수)에 `category = 'missed_call'` 행만 넣는다.
  - ② = 기존 폴백 계산(`isBadgeEligibleNotificationEvent` + 분류 합산)을 함수로 빼서 같이 쓴다.
- 행 수가 상한에 닿으면 지금처럼 ①·② 를 따로 읽는다(정확성 유지).
- **그림자 비교 10%**: 일부 요청에서는 예전 ①·② 도 읽어 결과를 비교하고 불일치를 기록한다(앞 단계와 같은 방식). RPC 와 JS 계산의 뜻이 다르면 여기서 드러난다.
- 절감: 배지 요청 1회당 −2 (그림자 10% 구간은 −1.8). 예산 badge-count 7.0 → 5.2 로 같은 PR 에서 낮춘다.

### 2-d-2 — 메신저 변경이 거래 채팅 목록 사본을 건드리지 않게 (결함 A)
- `invalidateOwnerHubBadgeCache` 에 「메신저 출처」 옵션을 둔다. 메신저 보내기·읽음·방 bump 호출처는 채팅 목록 사본 무효화와 재생성을 건너뛴다. 거래 읽음·거래 보내기·전체 읽음·주문 상태 호출처는 지금 그대로 둔다.
- 영향 화면: 거래 채팅 목록(`/api/chat/rooms`). 이 목록은 메신저 표를 읽지 않으므로 표시 내용은 바뀌지 않는다. 확인 방법: 단위 테스트(호출처별 옵션) + 운영에서 채팅 목록 RPC 하루 건수 전후 비교.
- 위험: 거래 쪽 변경이 메신저 출처로 잘못 표시되면 목록이 최대 8초(사본 TTL) 늦게 반영될 수 있다. 그래서 거래·주문 호출처에는 옵션을 넣지 않는다.

### 하지 않는 것 (이유)
- 허브 배지·홈 동기 사본 재생성을 없애거나 늦게 만드는 것: 읽는 쪽이 SWR(오래된 사본을 먼저 보여 줌)이라, 미리 만들지 않으면 읽음 직후 숫자·목록이 한 번 옛값으로 보인다. 기능 후퇴라서 하지 않는다.
- 결함 C(사장님 숫자): 쓰는 시점에 유지하는 표가 필요하다. 운영 DB 변경이 들어가므로 따로 설계한다. 절감이 작아(≈2/배지) 뒤로 미룬다.
