## 1. 원인 ① 친구 요청 전역 호스트가 화면 이동마다 내려갔다 다시 붙음 — 구조 결함

- 위치: `components/layout/providers/MessagingGlobalChrome.tsx`
  - 성능 라운드 BN12-B1(2026-06)이 `/mypage`·`/philife`에서 호스트를 idle 뒤에 붙이도록 바꿨다.
  - 그런데 그 effect 가 `pathname` 에 걸려, 화면이 바뀔 때마다 준비 상태를 **false 로 되돌렸다**.
- 결과: 마이페이지·필라이프 안에서 화면을 옮길 때마다 다음이 일어났다.
  1. 호스트가 내려간다. 실시간 채널이 떠나고 듣기를 해제한다.
  2. idle 뒤 다시 붙는다. 시작 조회 1번 → 채널 가입 → 구독 완료 조회 1번.
  3. 즉 친구 요청 전체 조회 **최대 2번 + 채널 떠남·가입 1번**이 화면 이동마다 일어났다.
- 실측 대조: 화면 이동 153번 → 조회 140번. 실제 변경 12건으로는 설명되지 않는다.
- BN12-B1 의 목적은 「첫 진입 때 붙이기를 미룬다」였다. 이동마다 내리는 것은 의도가 아니다(`docs/samarket-performance-track-state.md` BN12-B1 「idle defer」).
- **수정:** 처음 붙일 때만 미룬다. 한 번 붙은 뒤에는 화면을 옮겨도 내리지 않는다. 통화 화면에서 내리는 조건은 그대로 둔다.

## 2. 원인 ② 메신저 홈이 열릴 때마다 친구 요청 전체를 다시 조회 — 구조 결함

- 위치: `CommunityMessengerHome.tsx` 가 열릴 때마다 동기화 요청을 보낸다. 전역 피드(`use-global-friend-request-feed.ts`)는 이 요청을 받을 때마다 서버를 다시 묻는다.
- 그런데 피드는 실시간 채널로 요청 변경(`community_friend_requests` 받은·보낸)을 받는 즉시 다시 조회한다. 그래서 **채널이 연결돼 있는 동안 피드가 가진 목록은 이미 최신**이다.
- 홈이 열릴 때 친구 목록 보강(`hydrateMessengerFriends`)도 친구 요청 목록을 **따로 한 번 더** 받았다(`use-community-messenger-home-bootstrap.ts`). 같은 목록을 홈 열기 1번에 2번 받은 것이다.
- **수정 ①:** 채널이 연결된 상태에서 조회가 **성공한 뒤**면, 받은 목록을 다시 알리고 끝낸다. 서버는 묻지 않는다.
  - 다음 경우에는 받은 목록을 쓰지 않고 서버를 묻는다.
    - 연결 전
    - 끊김
    - 다시 연결됐는데 재연결 동기화 조회가 아직 안 끝남
    - 마지막 조회 실패
  - 조회 중이면 그 결과가 곧 알려지므로 아무것도 하지 않는다.
- **수정 ②:** 친구 목록 보강에서 친구 요청 조회를 뺀다. 요청 목록은 전역 피드 동기화가 홈에 넣는다(시작·실시간·복귀·재연결·홈 열기).

## 3. 원인 ③ 그룹방 「읽은 수」를 방 상태 객체가 바뀔 때마다 다시 조회 — 구조 결함

- 위치: `use-group-message-read-counts.ts` · `CommunityMessengerRoomPhase2MessageTimeline.tsx`
  - 다시 조회하는 신호가 `vm.snapshot`(방 상태 객체) 자체였다.
  - 방 상태 객체는 메시지 정합 조회·방 열기·실시간 반영마다 새로 바뀐다. 그래서 읽음과 무관한 일에도 「읽은 수」를 다시 물었다.
- 반대로, 다른 멤버가 읽었다는 사건(`cm-read-ack:<방>`)은 서버가 그룹방에도 보낸다(`rooms/[roomId]` PATCH mark_read). 그런데 받는 쪽이 **그룹방이면 무시했다**(`use-messenger-room-client-phase1.ts` `not_direct_room`).
  - 그래서 그룹 상태 아이콘은 방 상태 객체가 우연히 바뀔 때만 갱신됐다.
- **수정:** 다시 조회를 읽음에 관계된 때로만 바꾼다.
  1. 방·내 메시지 id 가 바뀔 때(입장·내가 보냄)
  2. 이 방 다른 멤버의 읽음 사건. 서버는 읽음 위치가 실제로 바뀐 때만 보낸다.
  3. 실시간 재연결 묶음. 끊긴 동안 놓친 읽음을 받는다.
  4. 다른 멤버의 새 메시지, 멤버 수 변경. 보내는 사람의 읽음 위치는 보낼 때 DB가 자기 메시지로 옮기는데, 이때 읽음 사건은 나가지 않는다(독립 재감사 확정 결함 — 답장만 한 멤버가 반영 안 됨). 이를 반영한다.
  - 2~4 의 사건은 0.4초 안이면 한 번으로 모은다.
  - 조회는 한 번에 하나만 하고, 조회 중 들어온 요청은 끝난 뒤 1번 더 한다.
- 효과: 읽음 반영이 **더 정확해진다**. 이전에는 읽어도 방 상태가 안 바뀌면 아이콘이 그대로였다.
