## 0. 작업자 잘못 (먼저)
1. **예산 값 미조정 — 규정 위반.** `docs/request-budget-ssot.md` §4-1 「호출을 줄인 PR 이 같은 PR 에서 값을 낮춘다」. #577·#592(동네 피드)에서 `/api/philife/neighborhood-feed` 5.0 을 낮추지 않았다.
2. **S4 를 설계보다 적게 구현.** 설계는 숨김·관계·상태 3조회 합치기, 구현은 숨김·관계 2조회. 상태(`community_post_viewer_states`)는 그대로. 완료 보고에서 이를 빼먹었다.
3. **S3 범위 보고 틀림.** 「관리자 API 전부」로 보고했지만 `isRouteAdmin` 을 쓰는 관리자 라우트 61개는 그대로 3조회다(§1-D4).
4. **S3 효과 계산 틀림.** 설계서는 「요약 없는 종 4 → 2」라 적었으나 종 요청의 95%(71/75)가 요약을 함께 받는다 — 요약 간격이 폴링 간격과 같은 75초라서다(§1-D3). 실제 1회당은 4.05 이다.
5. **알림음을 「가짜 경보(D2)」로만 분류한 것 틀림.** 11-24·11-25 Vercel 기준으로도 경보선 위다(§1-D6).
6. **11-26 작업 중 메인 체크아웃 브랜치를 바꿈.** `git checkout origin/main --` 로 다른 세션 브랜치(`perf/store-orders-minute-tick`)가 분리 HEAD 가 됐다. 즉시 되돌렸다(추적 파일 변경 없음 확인).

### D1 — 원인 (코드·운영으로 확인)
- 코드 `lib/perf/supabase-call-counter.ts` `installSupabaseCallCounter`: 셈은 인스턴스 메모리에 모으고, **다음 Supabase 호출 때 마지막 전송 뒤 5분이 지났을 때만** 전송한다. `lastFlushAt` 은 설치 시각에서 시작한다. 인스턴스가 멈출 때 전송하는 경로는 없다.
  → 5분 안에 멈춘 인스턴스는 전부, 오래 산 인스턴스도 마지막 묶음은 **반드시 잃는다**.
- 운영 11-25: 계수기 설치 로그 848회(= 인스턴스 시작) · 전송 RPC `cm_monitoring_rollup_add` 921회 → 인스턴스당 평균 1.1회 전송. 전송 실패 로그(`rollup_failed`)는 13건뿐(원인 아님).
- 저장 비율(계수기 ÷ Vercel 호출): 1분 cron(인스턴스가 계속 살아 있음) 82~85% · 관리자 종 66% · 메시지 54% · 동네 피드 45% · 접속 상태 42%.
- 영향: 요청 단위로 통째로 빠지므로 **1회당 값은 캐시 없는 라우트에서 거의 같다**(종 4.81/4.79 · 접속 상태 1.32/1.30). **절대값(`daily_total`)은 믿을 수 없다.**
