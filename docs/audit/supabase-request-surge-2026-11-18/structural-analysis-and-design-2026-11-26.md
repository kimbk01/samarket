## 1. 결론

1. 호출 상승의 원인은 **하나가 아니다.** 아래 다섯 구조가 겹친다.

   | 구조 | 성격 | 7일 몫 |
   |---|---|---|
   | S1 | 실시간 실패가 HTTP 폭주로 커짐 | 사건성 |
   | S2 | 화면이 켜져 있는 동안 도는 주기 조회 | 상시 |
   | S3 | 사용자 0명이어도 도는 고정 바닥 cron | 상시 |
   | S4 | 요청 1번당 비용이 큰 경로 | 상시 |
   | S5 | 이상을 늦게·못 잡는 감시 | 구조 |

   7일 합계는 Vercel 기준 **331,249**이다. 상위 35개 경로 기준 몫은 §2에 적는다.
2. **지난 조치는 경로 하나씩 고친 땜빵이었다.**
   - 11-18 이후 경로·숫자 단위 수정이 20건 넘게 들어갔다. 그중 4건은 되돌렸다(#474·#477·#478·F1).
   - 공통 장치는 설계만 하고 만들지 않았다(K4 공통 주기 작업 관리자·K6 요청 단위 읽기 캐시·F2·F4). 증거는 §4.
   - 그래서 같은 모양이 다른 경로에서 다시 나온다.
     - 실시간 실패 → HTTP 폴링: 11-09·11-18·11-19·11-23·11-26
     - 통화 조회 폴링: 11-08 → 11-18 → 11-25
3. **근본 원인 = 앱에 「요청을 내보내는 쪽」의 공통 규칙이 없다.**
   - 기능마다 자기 타이머·재시도·복귀 재조회를 따로 가진다.
     - 실시간 재시도 루프: 5종
     - 주기 조회: 20여 개
     - 복귀 재조회 리스너: 10여 개
   - 그중 어떤 것도 상한·공통 차단기·서버 거절 인식을 갖고 있지 않다.
   - 서버 감시는 하루 1번, 요청당 비용만 봐서 이런 반복을 잡지 못한다.
4. 설계는 경로별 수정이 아니라 **공통 장치 4개 + 기존 설계 2건 완료**다. 감시 개편이 첫 단계다. 순서는 §6.

## 3. 구조별 증거

### S1 실시간 실패 → HTTP 폭주 (사건성, 반복)

**운영 증거**

앱 감시 `realtime.subscription`, iOS 일별:

| 날짜 | 가입 시간초과 재시도 | 끊김 재시도 | 가입 성공 |
|---|---|---|---|
| 11-23 | 434 | 214 | 213 |
| 11-26 | **1,602** | **881** | 117 |
| 그 밖 날 | 0~39 | — | — |

- 11-26 서버 `realtime_logs` 의 `SocketJoinRateLimitReached`(한 연결에서 가입이 너무 많아 거절)는 282건이다. 대시보드 Realtime 오류 278건이 이것이다.
- 한 방 메시지 GET이 몰린 날이 반복된다. 일별 1위 방:

  | 날짜 | 방 | 메시지 GET | 비고 |
  |---|---|---|---|
  | 11-20 | `4308373d…` | 396 | |
  | 11-24 | `ac858592…` | 339 | |
  | 11-25 | `e565a4f4…` | 225 | |
  | 11-26 | `0bbd2940…` | 865 | bootstrap 540 별도 |
  | 11-26 | `e6807e2f…` | 210 | |

  11-26 두 방은 새 메시지가 각 1건이다. 상세는 `realtime-ios-retry-loop-2026-11-26.md`.

**코드 증거**

1. 재시도 루프가 5종이고, 최대 횟수·공통 차단기가 없다.
   - `subscribe-with-retry.ts:474-519`: 5번 연속 실패 시 10~30초 쉼(`cm-rt-loop-guard.ts:5,76-86`). 그 뒤 끝없이 재시도한다. 상태는 채널 이름별이다.
   - `presence-user-broadcast-client.ts:70`, `cm-read-ack-broadcast-client.ts:101`: 1/2/5/10초 뒤 10초 반복, 끝없음.
   - `lib/chats/use-chat-room-realtime.ts:96`: 380ms×2ⁿ, 최대 22초, 끝없음.
   - 래퍼 없는 채널 약 20개는 라이브러리 자체 재가입에 맡긴다.
2. 재시도 장치가 이중이다.
   - 실패 시 realtime-js가 스스로 재가입한다(`node_modules/@supabase/realtime-js/dist/main/RealtimeChannel.js:103-109` `rejoinTimer`).
   - 동시에 `subscribeWithRetry`가 채널을 지우고 새로 가입한다.
   - 그래서 실패 1번에 가입이 2번 갈 수 있다.
3. 서버 거절 이유를 버린다.
   - `subscribe-with-retry.ts:560 channel.subscribe((status) => …)` 는 오류 인자를 받지 않는다.
   - 소켓 상태 처리(`realtime.onOpen/onClose/onError`)가 코드 어디에도 없다.
   - 그래서 「가입 너무 많음」 거절도 짧은 재시도로 되받는다. 거절이 스스로 유지되는 반복이 된다.
4. 재연결 1번이 HTTP 여러 개로 퍼진다.
   - 한 사용자가 같은 소켓에 여는 채널: 홈 meta, rooms-in×N, 방 묶음×N, 알림, 안읽음 소리, 친구요청, 거래 노출.
   - 재가입 성공(SUBSCRIBED)마다 각자 HTTP를 다시 부른다.
     - 홈 → 목록 확인
     - 방 → `onRefresh` = 메시지 `after=` GET, 새 것 없으면 bootstrap GET (`use-messenger-room-client-phase1.ts:1523-1536`)
     - 알림 → 배지
     - 친구요청 → 목록, 처음 연결 때 포함 (`use-global-friend-request-feed.ts:180-184`)
   - 방 묶음은 **실패할 때마다**(2번째부터) 열린 방 전부에 HTTP 따라잡기를 건다(`global-messenger-room-bundle-channel.ts:574-579`, 120ms 디바운스).
5. 같은 데이터를 두 번 가입한다.
   - 참여자 `user_id=eq` 를 홈 meta(`community-messenger-home-realtime-channels.ts:156-162`)와 안읽음 소리(`use-cm-participants-hub-sync.ts:131-137`)가 따로 가입한다.
   - 방 묶음은 방 목록이 바뀔 때마다 모든 조각을 새 토픽(`:g{n}`)으로 다시 가입한다(`global-messenger-room-bundle-channel.ts:507-520,549`).

## 5. 통합 설계 — 공통 장치 4개 + 기존 설계 완료

### D1 실시간 연결 관리자 (S1 근본)

새 파일 `lib/realtime/realtime-connection-supervisor.ts` 하나가 **소켓 단위 상태**를 갖는다. 모든 채널 가입은 이 관리자를 거친다.

| 규칙 | 내용 |
|---|---|
| 재가입 주체 1개 | 라이브러리 자체 재가입과 래퍼 재생성 중 하나만 쓴다. 채널 실패 시 라이브러리 재가입은 끄고(재가입 타이머 무력화 또는 실패 즉시 leave) 관리자가 결정한다. |
| 거절 이유 분류 | `subscribe((status, err) => …)` 의 `err` 와 소켓 `onError/onClose` 를 읽는다. `SocketJoinRateLimitReached`·`TooManyChannels`·`TooManyJoins` 는 **소켓 전체 정지 → 긴 대기(30초→60초→5분)**. 대기 뒤 채널을 순서대로(간격 두고) 다시 가입한다. |
| 소켓 차단기 | 소켓의 모든 채널 실패를 합산한다. 예: 2분 안에 실패 10회 → 열림. 열린 동안 가입 0. 반만 열림 상태에서 1개 채널로 시험하고, 성공하면 나머지를 순차 가입한다. |
| 끝 있는 재시도 | 채널별 최대 재시도 N회. 넘으면 그 채널을 「끊김」으로 두고 화면 복귀·온라인 때만 다시 시도한다. presence·read-ack·구 채팅방 자체 루프 3종을 관리자로 옮긴다. |
| 중복 가입 제거 | 참여자 `user_id=eq` 를 홈 meta 1개로 합치고, 안읽음 소리는 같은 이벤트를 받아 쓴다. 방 묶음 재바인드는 바뀐 조각만 다시 가입한다. |
| 감시 | 소켓 상태 전환·차단기 열림·거절 이유를 앱 감시로 보낸다(지금 5분 묶음 그대로). |

### D2 재동기화 단일화 (S1 증폭 차단)

| 규칙 | 내용 |
|---|---|
| 소켓 재연결 1번 = 재동기화 1번 | 채널마다 SUBSCRIBED 를 따로 처리하지 않는다. 관리자가 「소켓이 끊겼다 붙었다」를 1번 알리고, 받는 쪽은 `app-resume-coordinator` 하나로 모은다. |
| 끊긴 동안 변화가 있을 때만 | 재동기화는 「마지막으로 본 시각 이후 바뀐 것이 있나」를 먼저 1번 묻고, 있을 때만 화면별로 조회한다. 기존 F4 `/api/app/resume?since=` 를 이 용도로 만든다. |
| 실패마다 폴백 금지 | 방 묶음 `onAfterSubscribeFailure` 의 방별 폴백을 없앤다. 차단기가 열린 동안은 **화면이 보일 때만, 방당 60초에 1번** 폴백 조회한다(상한). |
| 방 `onRefresh` 의 2단 조회 | `after=` 에서 새 것이 없을 때 bootstrap 을 다시 받는 것은 「읽음·참가자 변화 신호가 있었을 때만」으로 제한한다. |

### D3 앱 요청 관리자 (S2 근본 — 설계만 하고 안 만든 K4 실현)

새 파일 `lib/runtime/periodic-task.ts` 와 `lib/runtime/resource-fetch-governor.ts`.
- 모든 주기 조회·복귀 재조회는 이 관리자에 **자원 이름**으로 등록한다.
- 공통 규칙:
  - 화면 숨김·유휴 시 멈춤
  - 자원별 최소 간격
  - 동시 1개(single-flight)
  - 오류 시 지수 늘림(2초→30초)
  - 429 는 Retry-After
- 복귀 리스너 10여 곳은 coordinator 1곳으로 옮긴다.
- **세션 상한(안전망)**: 같은 자원 요청이 분당 상한을 넘으면 그 자원을 늦춘다(예: 메시지 GET 같은 방 분당 6회 초과 → 60초 늦춤). 늦췄다는 사실을 감시로 보낸다. 무한 반복이 어떤 경로에서 생겨도 상한에서 멈춘다.
- 통화 폴링(0.5초·1초·심박·수신 백업 2종 동시)은 이 관리자로 옮기는 것이 맞다. 하지만 **통화 변경 규정 대상**이라 D3 1차 범위에서 빼고, 통화 영향 분석서를 따로 쓴다.
