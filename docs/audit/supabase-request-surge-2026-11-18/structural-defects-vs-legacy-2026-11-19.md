## 0. 먼저 정직하게: F1(#483)은 구조 개선이 아니다

F1 은 「켜 두고 방치한 기기」의 누수를 막는다(효과는 크고 기능 손상은 없다). 그러나 **「접속 상태를 클라이언트가 12초마다 DB 에 써서 서버가 읽는다」는 구조 자체는 그대로다.** 활동 중인 회원 수 × 시간만큼 여전히 늘어난다. 최종 구조는 아래 D1 이다. F1 은 D1 완료 전까지의 누수 차단이며, D1 이 끝나면 하트비트 자체가 사라진다.

## 1. 판정 기준 — 회원이 늘어도 터지지 않는 앱(레거시)의 공통 원칙

카카오톡·텔레그램류 메신저, 당근·배민류 커머스 앱이 공통으로 따르는 구조 원칙(공개된 아키텍처 일반론 — 특정 사내 구현을 단정하지 않음):

| # | 원칙 | 뜻 |
|---|---|---|
| L1 | **연결이 곧 접속** | 앱이 열려 있는지는 지속 연결(소켓)이 안다. 주기적으로 DB 에 「나 살아 있음」을 쓰지 않는다. last_seen 은 연결이 끊길 때 1번 쓴다 |
| L2 | **연결로 전달, 없을 때만 푸시** | 앱이 연결돼 있으면 메시지는 연결로 가고, 표시 여부(알림 억제)는 **앱이 스스로** 판단한다. 서버가 DB 신선도로 추측하지 않는다 |
| L3 | **쓸 때 계산, 읽을 때 1번** | 안 읽음·배지 같은 숫자는 쓰기 시점에 카운터를 갱신하고, 읽기는 카운터 1행 |
| L4 | **변경분 동기화** | 앱 복귀·재연결 시 「마지막으로 본 버전 이후 바뀐 것만」 한 번에 받는다. 화면마다 전부 다시 받지 않는다 |
| L5 | **화면 1개 = 요청 1개** | 화면이 필요한 데이터를 서버가 한 번에 조립 |
| L6 | **세션은 한 번 검증** | 요청마다 회원 상태를 DB 에서 다시 읽지 않는다(토큰 클레임·세션 무효화로 반영) |
| L7 | **변하지 않는 데이터는 캐시** | 카테고리·설정·이미지는 CDN·앱 캐시. 매 실행 원본 조회 없음 |
| L8 | **시간 기반 작업은 DB/큐가 예약** | 외부 cron 이 1~5분마다 「할 일 있나」 묻지 않는다 |

## 2. DIBAY 구조 결함 (원칙별 · 증거 · 회원 증가 시 커지는 방식)

### D1. 접속 상태 = 클라이언트 12초 DB 쓰기 (L1·L2 위반) — **가장 큼**
- CODE: `use-community-messenger-presence-runtime.ts:29,325` 12초 HTTP → `presence_snapshots` upsert.
- 이 쓰기가 필요한 이유가 구조 결함: 서버가 **푸시를 보낼지**를 DB `last_ping_at` 15초 신선도로 판단한다(`notification-presence-policy.ts:5,52-63`). 그래서 12초를 늘릴 수 없다.
- Realtime presence(`channel.track`)로 같은 정보를 이미 보내고 있다(`:347`) — **이중 경로**.
- PROD: presence 요청 11,394건/일(대부분 기기 4대). 9시간 무활동 하트비트 사례.
- 증가: **활성 기기 수 × 켜 둔 시간** (선형, 상한 없음).
- 구조 목표: ① 상대 접속 표시 = Realtime presence 만(이미 권위 — `use-community-messenger-peer-presence.ts:87-91`). ② 푸시 억제 = **앱이 판단**: 앱이 앞화면이고 그 방을 보고 있으면 받은 알림을 띄우지 않음(Android FCM 수신 처리·iOS `willPresent`), 서버는 항상 보낸다. ③ 자동 읽음 = 방을 보고 있는 앱이 읽음 처리(이미 방 진입 mark_read 경로 있음). ④ DB last_seen 은 앱 종료·백그라운드 전환 때 1회.
- 결과: 하트비트 0. 회원 수와 무관.
- 규정: 푸시 파이프라인은 통화 푸시와 공유 → **통화 변경 규정**(영향 분석·승인·실기 행렬).

### D2. 안 읽음·배지 = 읽을 때마다 원본 재집계 (L3 위반)
- CODE: `lib/notifications/pipeline/build-domain-badge-authority-http.ts:186-194` — 요청마다 participants·rooms·notification_events·부재중 통화·벨 이벤트·사장님 운영 사실 **6갈래 집계**.
- PROD: `badge-count` 1회당 7.6, 하루 10,980건. `room-read` 19, `rooms/[roomId]` 15.4 도 같은 표들을 다시 읽음.
- 호출 시점: 실행·앱 복귀·읽음 처리마다.
- 증가: **(실행+복귀+읽음) × 회원 × 6~19**.
- 구조 목표: 메시지·알림·주문 쓰기 트랜잭션에서 회원별 카운터 1행(`hub_badge_user_unread_counters` 확장)을 갱신(트리거). 읽기는 1행. 변경 시 Realtime 으로 숫자만 전달 → 앱 복귀 때 다시 묻지 않음.

### D3. 실행·복귀 = 화면마다 전부 다시 받기 (L4·L7 위반)
- CODE(조사): 콜드 스타트 시작 API 약 20개가 각각 따로(startup-config·app-settings·main-bottom-nav·notification-sound-ssot·launch-intro·platform-popup·address-gate·me/settings·profile×2·badge·hub-badge·notification-settings·favorites·moim…). 복귀마다 badge·friend-requests·hub-badge·주소 확인·홈 목록 확인 등 15~25건.
- 이 중 **모든 회원에게 같은 값**(설정·하단 메뉴·소리·인트로·카테고리)이 CDN 캐시 없이 매번 서버·DB.
- PROD: startup-config·app-settings·main-bottom-nav 각 약 830건/일 = 실행 수와 같음(캐시 0).
- 증가: **(실행+복귀) × 회원 × 20**.
- 구조 목표: ① 공통 설정 = 버전 붙은 정적 응답(CDN, 어드민 저장 시 버전 증가) → Supabase 0. ② 회원별 상태 = **`sync` 1회**: 「내가 가진 버전」을 보내면 바뀐 도메인만 돌려줌(배지·친구요청·주소·알림설정…). 바뀐 게 없으면 1건으로 끝.

### D4. 화면 1개 = API 여러 개 × API 1개 = Supabase 여러 번 (L5 위반)
- PROD 1회당: home-feed 17.6 · community-messenger/bootstrap 11.9 · messages 11.2 · trade-chat-list-meta 14.9 · neighborhood-feed 7.2. 홈 진입 약 35, 방 진입 약 33.
- 같은 요청 안에서 같은 표를 반복 조회(home-feed `admin_settings` 2.68회·wave RPC 4.37회, bootstrap 스냅샷 3.55회).
- 구조 목표: 화면별 DB RPC 1개(서버 조립). **운영 DB 적용을 먼저 하고 확인한 뒤 코드 병합**(B1·B3 실패 재발 방지).

### D5. 요청마다 회원 상태 재확인 + 공유 캐시 없음 (L6 위반 · 인프라 결함)
- CODE: `/api` GET 마다 profiles `status,deleted_at`(5초 · **서버 인스턴스별** 메모리), 쓰기마다 `member_write_gate_snapshot` RPC(캐시 없음). 신원 캐시 3갈래.
- 인프라: Vercel 서버리스 + **공유 캐시(Redis) 없음** → 인스턴스 메모리 캐시는 인스턴스가 늘수록 적중률이 떨어진다. 회원이 늘면 인스턴스도 늘어 **캐시가 더 안 맞는다**(역방향 확장).
- PROD: `profiles` 25,779건/일(1위), proxy 16,323.
- 구조 목표: 차단·탈퇴를 **토큰 클레임**(Supabase Custom Access Token Hook)으로 + 차단 시 세션 강제 만료. 요청마다 DB 확인 0. 쓰기 게이트는 쓰기 RPC 안에서 확인. (Auth HARD LOCK — 별도 설계)

### D6. 그룹방 새 메시지 → 받는 사람마다 HTTP 재조회 (L2 위반 · 그룹 크기에 비례)
- CODE/문서: `docs/messenger-realtime-policy.md` — 텍스트·스티커는 bump 스냅샷으로 바로 병합하지만 **이미지·파일·음성·통화 기록·반응·수정·삭제는 받는 기기마다 `messages/{id}` HTTP 정합**. `postgres_changes` 도 병행 구독.
- 증가: **그룹 인원 × 미디어/반응 메시지 수**. 100명 방에서 사진 1장 = 최대 100 요청.
- 구조 목표: 모든 메시지 종류를 검증 가능한 스냅샷으로 실어 보냄(미디어는 경로·크기 메타, 반응은 집계 + 각자 `mine` 은 클라 계산). 재조회는 끊김 복구 때만. 이중 구독(`postgres_changes`) 정리.

### D7. 앱이 Supabase 를 직접 부를 때 요청 2배 + 정적 데이터 매번 조회 (L7 위반)
- PROD(앱 직접 24h): REST 2,705 + **CORS 사전 요청 1,897** · 인증 915 + 사전 요청 743. `categories` GET 2,287 + OPTIONS 1,559 — **거의 안 바뀌는 카테고리를 앱이 매번 직접 조회**.
- 구조 목표: 정적 표는 버전 붙은 캐시 응답(D3 ①)으로. 앱 직접 REST 는 같은 출처 서버 경유로 모아 사전 요청 제거.

### D8. 시간 기반 작업 = 외부 cron 폴링 (L8 위반 · 고정 바닥)
- CODE(조사): Vercel cron 23개, 유휴 약 1.35만 건/일. 단일 RPC 만 부르는 cron·pg_cron 과 중복 실행 존재.
- 증가: 회원과 무관(고정). 우선순위 낮음.
- 구조 목표: DB 측 예약(pg_cron)·이벤트 트리거로. 푸시·통화 cron 은 규정 대상.

### D9. 같은 이미지를 반복 다운로드 (원인 NOT_PROVEN)
- PROD: 저장소 요청 14,475건/일(CDN 적중 96%), 이미지 1장이 하루 약 200~300회.
- 앱 캐시가 이미지를 유지하지 못하는 것으로 보이나 원인(응답 Cache-Control·WebView 캐시·URL 변형)은 **미확인** — 확인 후 판정.

## 4. 구조 개선 순서 (회원 증가 시 영향 큰 순 · 각 단계 설계 승인 → 구현 → 운영 전후 실측)

| 순서 | 결함 | 왜 먼저 | 규정 |
|---|---|---|---|
| 1 | **D1** 접속·푸시 억제 → 연결·앱 판단 | 상한 없는 선형 증가, 하트비트 자체 제거 | 통화 변경 규정 (푸시 공유) |
| 2 | **D2** 배지 쓰기 시 카운터 | 실행·복귀·읽음 모두에 곱해짐 | 메신저·알림 hard-lock, 운영 DB 적용 승인 |
| 3 | **D3** 공통 설정 캐시 + sync 1회 | 실행·복귀 20배 → 1~2 | 앱 실행 경로 실기 |
| 4 | **D6** 메시지 스냅샷 전 종류 | 그룹 크기에 비례 | 메신저 hard-lock |
| 5 | **D4** 화면 RPC | 단가 | 도메인별, DB 먼저 |
| 6 | **D5** 토큰 클레임 | 인스턴스 증가 시 악화 | Auth HARD LOCK |
| 7 | D7·D8·D9 | 고정·부수 | — |

각 단계 「완료」 = 코드 PASS + 운영에서 해당 경로 요청 수·1회당 Supabase 전후 비교 + (통화·푸시면) 실기 행렬 PASS. 추정만으로 완료라고 쓰지 않는다.
