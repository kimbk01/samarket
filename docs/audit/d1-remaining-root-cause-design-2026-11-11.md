### 1-2. 원인 A — `html:has(…)`·`body:has(…)` CSS 규칙이 문서 전체 스타일 재계산을 부른다 (**확정**)
- 타임라인 무효화 기록: 머리글에 요소가 들어갈 때마다 `HTML: Affected by :has()` → `Invalidation set invalidates subtree (allDescendantsMightBeInvalid)` — 문서 전체가 다시 계산 대상.
- **실험**: 앱 시작 시 `html/body/:root` 를 주어로 한 `:has()` 규칙 14개를 지운 상태로 다시 불러온 뒤 같은 이동 측정.
  | | 누름 처리 재계산 | 전환 후반 재계산 | 전환 작업 |
  |---|---|---|---|
  | 지금 | 598개 33ms | 986개 45~48ms | 203ms |
  | 규칙 제거 | **12개 5.7~6.3ms** | **53개 5.5~5.8ms** | **162ms** |
- 해당 규칙(17줄, 운영 화면 기능 6가지):
  - 하단 탭 유무·모양: `app/app-shell.css:215`(거래 허브 하단 여백), `app/app-bottom-nav.css:567·571`(배달 하단 탭·궤도 아이콘), `app/dibay-overlay.css:1047`(하단 탭 없을 때 토스트 위치)
  - 데스크톱 세로 레일: `app/app-desktop-side-nav.css:18·27·32·117·123`
  - 공유 시트 위치: `app/community-share-sheet.css:20·27·31`
  - 배달 당겨서 새로고침 영역: `app/delivery-components.css:1785·1789`
  - 어드민: `app/globals.css:352`, `app/dibay-overlay.css:1014·1015`
- 부정된 가설: 「`:has` 를 지우면 숨김 해제 재계산(888개)도 준다」 → 실험상 변화 없음(82→80~86ms). 원인 A 는 **추가 두 번**에만 해당.

### 1-3. 원인 B — 숨김(`display:none`)을 풀면 그 화면 요소 전체를 스타일 다시 계산 (**확정**, 구조상 필연)
- React `Activity` 는 숨길 때 `display:none !important` 를 건다 → 브라우저는 숨긴 요소의 계산된 스타일을 버린다 → 보일 때 전부 다시 계산(커뮤니티 888개 75~83ms · 홈 551개 73ms · 배달 556개 64ms · 내정보 268개 47ms).
- **실험**: 커뮤니티 피드 글 칸(`li` 24개)에 `content-visibility:auto; contain-intrinsic-size:auto 140px` 를 넣고 같은 측정 →
  | | 숨김 해제 재계산 | 다음 그리기 재계산 | 배치 | 전환 작업 |
  |---|---|---|---|---|
  | `:has` 제거만 | 888개 80ms | — | 20ms | 162ms |
  | + 글 칸 `content-visibility` | **146개 23ms** | 313개 17ms | 8ms | **90ms** |
- 부정된 가설 ①: 「사용자 정의 CSS 변수 수(요소마다 803개)가 원인」 → 루트 변수 467개를 지워 420개로 줄여도 75~78ms → 71~78ms, 변화 없음.
- 부정된 가설 ②: 「선택자가 비싸서」 → 선택자 통계상 일치 검사 합계 약 25ms(가장 비싼 선택자 1ms), 재계산의 일부일 뿐.
- 원인 B 의 남은 부분: 화면에 보이는 요소의 재계산은 숨김 방식을 쓰는 한 없어지지 않는다.

### 1-4. 원인 C — 다시 보일 때 React 가 그 화면의 효과를 모두 다시 붙인다 (측정, 약 50ms)
- CPU 프로파일: 전환 작업 중 강제 스타일·배치 계산을 뺀 React 작업 약 50ms, 가장 큰 단일 함수 6ms 이하로 **여러 효과에 흩어져 있음**(한 군데 원인 없음). `Activity` 의 정해진 동작이라 이번 수정 범위에서 줄이지 않는다.

### 1-5. 수정안 (P1)
| 항목 | 바꾸는 것 | 영향받는 화면·호출처 | 깨질 수 있는 것 → 같은 단계 처리 |
|---|---|---|---|
| F1 `:has` 제거 | 위 17줄을 `<html>` 속성 선택자로 교체: `html[data-bottom-nav]`, `html[data-bottom-nav-variant="delivery\|side-rail"]`, `html[data-bottom-nav-scroll-hidden]`, `html[data-bottom-nav-domain-orbit]`, `html[data-stores-home-hub]`, `html[data-stores-browse-ptr-hint]`, `html[data-overlay-open]`, `html[data-admin-console="v2"]`. 속성은 그 요소를 그리는 컴포넌트(하단 탭·배달 홈·오버레이 루트·어드민 콘솔)가 마운트/해제 때 1곳에서 붙이고 뗀다 | 하단 탭 있는 모든 화면, 데스크톱 레일, 공유 시트, 토스트, 배달 당겨서 새로고침, 어드민 표 | ① 첫 그림에서 속성이 없어 여백이 튐 → 하단 탭은 서버 셸(C 단계)이 그리므로 서버 HTML 의 `<html>` 에도 같은 속성을 넣는다 ② 두 컴포넌트가 같은 속성을 다툼 → 속성별 소유 컴포넌트 1개로 고정, 계약 테스트 ③ `:has` 미지원 구형 WebView 에서 지금 안 되던 것이 되기 시작 — 같은 모양이 나오는지 6가지 화면 실기 확인 |

## 5. 남은 위험 (전부)
1. **50ms 기준**: F1·F2 후에도 보장 못 함(§1-5). 수정 후 운영 녹화로 판정.
2. **60초 안 옛 값**: 다른 화면에서 좋아요·댓글을 바꾸고 60초 안에 돌아오면 목록 숫자가 이전 값일 수 있음(설계상 동작). 세대 올림은 글 쓰기·피드 캐시 비우기·주소·프로필·언어·앱 복귀에만 연결.
3. **두 화면 연출(D 방식)**: 이 연출이 일어나면 보관대가 다시 만들어져 보관 화면이 사라짐(새로 그림 = 예전 동작, 회귀 아님).
4. **Next 내부 API 의존**: `LayoutRouterContext`·`PathnameContext` 등 Next 내부 모듈을 직접 사용 — Next 버전을 올리면 동작이 바뀔 수 있음. 버전 올릴 때 보관대 계약 테스트·실기 필수.
5. **메모리**: 삼성 렌더러 +25.7%(기준 30% 이하). 허브 화면이 커지면 기준을 넘을 수 있음 — 탭 10회 순회 측정을 배포 확인 항목으로 유지.
6. **비회원 내정보·배달 깜빡임**: 비회원은 탭 이동마다 회원 상태가 「확인 중→비회원」으로 바뀌어 화면을 다시 만듦(D1 이전부터, 이번 범위 밖) — 별도 항목.
7. **F1 위험**: `:has` 를 속성으로 바꾸는 순간 6가지 화면의 여백·위치가 달라질 수 있음 → 화면별 실기 대조 필수(첫 그림 튐 포함).
8. **F2 위험**: 스크롤 복원 위치 오차·광고 노출 집계 — 각각 실기·테스트로 확인 전에는 NOT_PROVEN.
