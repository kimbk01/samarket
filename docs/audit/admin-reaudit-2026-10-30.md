## 5. 수정 범위 제안 — Owner 승인 요청

원칙
- 덧붙이기(땜빵)가 아니라 공통·도메인 구조를 한 번에 맞춘다.
- 원장(데이터)과 URL 은 유지한다. 진입점은 여러 개 허용하되 워크스페이스가 바뀌지 않게 한다.
- 권한은 「같은 업무 = 같은 키」로 맞춘다.
- 운영 확인은 199개 전수 + 데이터 변경 CTA 를 QA 데이터로 확인한다.

- G-02 배달 주문 API 에 `business` 적용

- E-7 support POST·summary 에 `support` 적용

### B. 광고·프로모션 구조 (E-1 · G-05 · G-06)

광고·배너 워크스페이스를 「광고·프로모션 통합 관리」로 정리한다.

```
광고 운영   전체 광고·승인·노출 관리·상위노출·노출 위치·상품/가격·이력
배너        배너 현황·프로모션·마이페이지·피드·배달 홈
팝업·이벤트  팝업·당겨서 새로고침·이벤트·사장님 이벤트 신청
앱 시작 화면  OS 시작·인트로·앱 첫 진입
홍보 발송    푸시 캠페인 진입
```

- 같은 화면을 플랫폼 운영·알림에도 그대로 둔다 (진입점 복수 허용).
- 배달·거래·커뮤니티 워크스페이스에 「우리 도메인 광고·배너·팝업·이벤트」 진입점을 둔다. 팝업·이벤트 목록 API 에 기존 표면(도메인) 값으로 거르는 조건을 추가한다 (원장 변경 없음).
- 진입점 방식 (E-8 해결): `?from=` 쿼리를 버린다. 워크스페이스 판정에 「진입 워크스페이스 기억(세션)」을 쓴다. 상세·편집·페이지 이동에서도 유지되게 하고, 테스트와 운영으로 확인한다.
