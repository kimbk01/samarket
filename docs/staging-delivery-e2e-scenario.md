## dibaY 배달 — 스테이징 실전 E2E 시나리오 (운영자용)

목표: 운영자가 **그대로 따라 하면** 배달 시스템의 핵심 흐름(정상/예외/보안/정산/Release Gate)을 스테이징에서 최종 검증한다.

제약:
- **기능 수정 금지**
- **신규 API 추가 금지**
- **상태 머신 변경 금지**

## 테스트 계정

아래 4계정이 준비되어야 한다.

### 주문자 계정 (Buyer)

- **권한 확인**
  - `/api/me` 또는 주문/프로필 페이지에서 로그인 상태 확인
  - 주문 생성 가능해야 함

### 매장 오너 계정 (Store Owner)

- **권한 확인**
  - 오너 전용 주문 화면 접근 가능: `/admin/stores/orders` 또는 오너 전용 주문 페이지
  - 해당 스테이징 매장의 `owner_user_id`가 이 계정이어야 함

### 라이더 계정 (Rider)

- **권한 확인**
  - `/rider` 진입 가능
  - 온라인 전환 가능
  - 배정된 주문 조회 가능

### 플랫폼 관리자 계정 (Admin)

- **권한 확인**
  - `/admin/access-check`가 `ok=true` 이어야 함
  - `/admin/ops-console`, `/admin/runtime-health`, `/admin/delivery-release-gate` 접근 가능

## 사전 준비

### 스테이징 환경 정보 기록

- **환경 URL**: 예) `http://<staging-host>:3000`
- **테스트 매장**: store_id / store_name 기록
- **테스트 라이더**: rider_id / 표시명 기록

### 필수 데이터 준비

- **매장 승인 상태**
  - `/stores`에서 노출되는지 확인(승인된 매장만 노출되어야 함)
- **메뉴 1개 이상**
  - 해당 매장에서 구매자가 1개 이상 상품을 담을 수 있어야 함
- **라이더 온라인 가능**
  - 라이더 계정에서 온라인 전환이 막히면 진행 불가

### 운영 인프라 준비(필수 확인)

- **Runtime Health**
  - `/admin/runtime-health` 진입
  - PG version 표시 확인
  - capability mismatch 경고가 있다면 기록(운영 허용/불가 판단에 필요)
- **Storage(POD)**
  - `delivery-proofs` 버킷이 private 이어야 함(Release Gate 자동 검사에서도 확인)
- **Release Gate 페이지**
  - `/admin/delivery-release-gate` 접속 가능해야 함

## 정상 흐름 시나리오 (주문 → 배달 완료)

### 1) 주문자: 주문 생성

- `/stores` 진입
- 승인 매장만 노출되는지 확인
- 매장 선택 → 메뉴 선택 → 장바구니 이동
- 주문 생성(결제/주문 생성 완료)
- 주문 상세로 이동
- 주문 상세 화면에서 다음을 확인
  - ETA 영역 표시(오너 입력 후 반영)
  - 라이더 상태 표시(배정/픽업/배송중/완료 단계 반영)

### 2) 매장 오너: 주문 수락 + ETA

- 오너 계정으로 주문 목록 확인
- 해당 주문 **접수확인(accepted)** 처리
- ETA(예상 준비시간) 입력
- 상태 전환
  - 조리중
  - 포장완료

### 3) 플랫폼 관리자: 라이더 배정

- 관리자 계정으로 `/admin/ops-console` 또는 배달 주문 상세 진입
- 해당 주문에 라이더 배정(배정 대상 라이더 확인)

### 4) 라이더: 수락 → 픽업 → 도착 → POD → 완료

- 라이더 계정으로 `/rider` 진입
- 온라인 전환
- 배정 주문 확인
- **수락**
- **픽업 완료**
- **고객 도착**
- **POD 업로드**
  - 업로드 성공(경로/URL이 라이더 UI에 노출되는지 확인)
- **배달 완료**
- 라이더 목록/완료 탭 반영 확인

### 5) 주문자: 실시간 상태 반영 및 완료 확인

- 주문자 주문 상세에서 다음이 **실시간 반영**되는지 확인
  - 오너 accepted 반영
  - 라이더 배정/픽업/배송중/완료 반영
- delivered 후 완료 표시 확인

## 예외 흐름 시나리오 (필수)

### A) 라이더 거절

- 라이더가 배정된 주문을 **거절**
- 관리자/오너 화면에서 미배차 또는 재배정 필요 상태가 즉시 반영되는지 확인

### B) 재배정(라이더 변경)

- 관리자 `/admin/ops-console`에서 **Reassign** 실행(라이더 선택 UI)
- 다음 확인
  - 동일 라이더 선택 불가
  - 오프라인 허용 OFF일 때 오프라인 라이더가 선택 목록에 안 뜨는지
  - paused/suspended 라이더는 선택 불가인지

### C) 실패 보고(라이더)

- 라이더가 배송 실패 보고(사유/메모/증빙 이미지 포함 가능)
- 오너/주문자 화면에는 **이미지 URL이 노출되지 않아야 함**
- 관리자 화면에는 실패 텍스트/상태가 보이는지 확인

### D) 관리자 delivery_failed 확정

- 관리자 경로로 실패 확정 전이를 수행(제품 운영 규칙에 따라)
- 관련 알림/큐 정리가 정상인지 확인

### E) 환불 요청 → 환불 완료 → 정산 held

- 주문자(또는 관리자) 환불 요청 흐름 수행
- 관리자 환불 완료 처리
- 정산이 held 또는 보류 상태로 반영되는지 확인(운영 정책에 따라)

### F) 자동 액션 pending approval

- `/admin/delivery-auto-actions` 또는 `/admin/ops-console` 자동 액션 탭에서
  - pending approval 항목 확인
  - approve/reject 수행(모달 note 포함)
  - 처리 후 즉시 갱신되는지 확인

### G) recovery 실행

- `/admin/ops-console` 빠른 액션에서 recovery 실행
  - SLA 스캔 / 알림 동기화 / 자동 액션 러너 등
- 실행 후 Ops Console KPI/큐 변화 확인

## 보안 체크 (필수)

### 1) 구매자 WS payload 증빙 미노출

- 구매자 계정으로 브라우저 DevTools → Network → WS(웹소켓) 선택
- Supabase Realtime `postgres_changes` payload에서 아래 키가 **존재하지 않는지** 확인
  - `delivered_proof_image_path`
  - `failure_proof_image_path`
  - `delivered_proof_image_url`
  - `failure_proof_image_url`
- 결과를 스크린샷으로 남기고, Release Gate 수동 체크에 기록

### 2) 오너 WS payload 증빙 미노출

- 오너 계정으로 동일하게 확인 및 기록

### 3) 관리자만 signedUrl 확인 가능

- 관리자 주문 상세(배달 POD 표시 화면)에서 이미지는 **signedUrl로만** 로드되는지 확인
- signedUrl 만료(5~10분) 후 새로고침 시 재발급/재로딩 동작 확인

---

## 정산 체크 (필수)

- delivered/completed 후 정산 생성 여부 확인
- 수수료 차감 반영 확인(정산 금액 계산)
- 오너/업체 정산 화면 반영 확인
- 관리자 정산센터 반영 확인
- paid 처리 수행(관리자)
- 환불 후 held 처리 확인(운영 정책 기준)

---

## Release Gate 체크 (마지막 단계)

### 1) 자동 검사

- `/admin/delivery-release-gate`에서
  - `fail`이 없는지 확인
  - `warn`/`needs_check`는 사유를 기록

### 2) 수동 체크 6개 완료

수동 체크 항목을 모두 체크하고 메모를 남긴다:
- 구매자 WS 증빙 비노출
- 오너 WS 증빙 비노출
- 4역할 E2E
- signedUrl 만료
- 정산 paid
- 환불 후 held

### 3) 최종 상태 READY

- 최종 Overall이 **READY**인지 확인
- READY가 아니면(= WARNING/BLOCKED) 원인을 기록하고 배포 보류

## 최종 배포 판정

### 판정 결과 (선택)

- **GO**: 필수 항목이 모두 pass, Release Gate가 READY, 수동 체크 6개 완료.
- **GO WITH WARNING**: 핵심 흐름은 pass이나, 운영 상 수용 가능한 warn(예: backlog 소량, pg_cron 미지원이지만 운영 fallback 확정)만 남음.
- **BLOCKED**: fail/blocked 항목 존재 또는 보안/정산/Realtime 핵심 항목 미확인.

### 판정 근거(필수)

- Release Gate Overall:
- 자동 검사 fail 여부:
- 수동 체크 6개 완료 여부:
- 남은 warn 목록(있으면):
- 운영 수용 사유(있으면):
